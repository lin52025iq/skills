---
name: code-migration
description: 用于将一个或多个现有项目中的功能、业务规则和用户能力迁移、融合或重构到目标项目。适用于前端项目迁入新仓库、跨框架或技术栈重实现、多个旧项目能力合并、模块整合、功能删改融合、目标架构适配与渐进切流。迁移以源行为证据、目标期望行为和目标项目原生架构为中心，先建立可追踪的源行为契约和功能台账，再按切片 / 工作流实施、验证与清理；默认不按源文件、目录、组件或状态结构一比一翻译，并支持通过安全检查后的多 Agent 受控并行迁移。
---

# Code Migration

把代码迁移视为 **“业务能力在新上下文中的受控重建”**，不是文件搬运或旧架构复制。

```text
源证据
→ 源行为契约
→ 目标期望行为
→ 目标原生设计
→ 模块 / 功能 / 功能子项台账
→ 切片 / 受控工作流
→ 实施 / 验证 / 集成
→ 切流 / 清理
```

## 1. 核心原则

1. **迁移的是能力，不是文件。** 源文件只是证据，不是迁移边界。
2. **源项目是事实，不是目标规范。** 它说明旧系统实际做了什么。
3. **关键源行为必须可追踪。** 每条关键行为决定“保持 / 目标修改 / 不迁移 / 未知”。
4. **用户意图与目标产品决定目标行为。** 必须保留的 Invariant 不得因技术迁移丢失。
5. **目标项目决定实现形状。** 路由、状态、数据层、组件、目录、错误和测试遵循目标仓库惯例。
6. **功能台账维护完整范围。** 执行队列只负责调度。
7. **每个工作流单焦点，全局可安全并行。** 独立功能通过并行安全检查后可由不同实施负责人同时开发。
8. **状态实时更新。** 功能、功能子项、源行为都必须直接显示当前状态。
9. **用户规则是执行约束。** 每个切片 / 工作流开始前检查生效规则。
10. **验证面向目标行为。** 保持项验证不回归，批准变化验证新行为正确。
11. **治理强度按风险自适应。** 低风险任务不机械承担高风险任务的全部文档与 Gate。
12. **迁移完成还包括集成、切流和遗留清理。**

## 2. 启动方式

先识别源项目、目标项目、迁移目标、用户约束和目标技术栈，再检查目标仓库根目录 `.code-migration/`。

### 已有工作区

按顺序恢复：

1. `00-迁移状态总览.md`；
2. 活跃工作流、负责人、输入基线；
3. `06-迁移约束与开发规则.md`；
4. `02-迁移模块功能点清单.md`；
5. `07-源行为与目标对齐清单.md` 或模块行为文档；
6. 迁移决策、执行计划；
7. Git、代码和测试状态。

不一致时先最小范围重新校准，不重新扫描全部源项目。

### 新工作区

长周期迁移按需创建：

```text
.code-migration/
├── 00-迁移状态总览.md
├── 01-迁移任务上下文.md
├── 02-迁移模块功能点清单.md
├── 03-功能融合映射.md
├── 04-迁移决策记录.md
├── 05-迁移执行计划.md
├── 06-迁移约束与开发规则.md
├── 07-源行为与目标对齐清单.md
└── modules/<module>/
```

小任务不机械生成全部文档。

## 3. 迁移决策与处理方式

功能迁移决策统一使用中文：

```text
保留 / 适配 / 合并 / 拆分 / 移除
替换 / 复用目标 / 新增 / 延后 / 未知
```

每个功能 / 功能子项同时记录 **处理方式**：

```text
新实现 / 修改现有 / 复用已有 / 移除已有 / 无需实施 / 待决定
```

处理方式用于解决“是否真的需要写代码”的问题：

- `保留 / 适配 / 合并 / 拆分 / 替换 / 新增`：通常是 `新实现` 或 `修改现有`；
- `复用目标`：通常是 `复用已有`，允许不产生新代码，但必须验证目标已有能力确实满足目标行为；
- `移除`：通常是 `移除已有`，完成标准是旧入口/调用/依赖安全退出并通过验证；
- `延后`：当前阶段不进入完成 Gate；
- `未知`：`待决定`，影响当前方向时必须阻塞；
- 明确没有代码动作但需要确认行为时可使用 `无需实施`。

**不得为了满足状态表而把“复用已有 / 无需实施”伪造成“已实施”。**

源行为决策使用：

```text
保持 / 目标修改 / 不迁移 / 未知
```

重大移除、合并、替换、Invariant 变化或高风险产品变化应记录迁移决策。

## 4. 运行时状态

### **当前状态**

所有可开发或验证的功能子项、源行为必须显式展示：

```text
未开始 / 开发中 / 待验证 / 验证中 / 验证失败
已完成 / 已阻塞 / 已延后 / 不适用
```

当前状态由详细状态和处理方式推导：

```text
阻塞状态=已阻塞                              → 已阻塞
范围状态=延后                                → 已延后
范围外 / 明确不迁移                          → 不适用
验证状态=失败                                → 验证失败
实施状态=实施中                              → 开发中
新实现/修改现有 + 实施状态=未开始             → 未开始
新实现/修改现有 + 已实施 + 未验证              → 待验证
复用已有/无需实施 + 验证状态=未验证            → 待验证
验证状态=验证中                              → 验证中
实施要求满足 + 验证状态=通过/不适用            → 已完成
复用已有/无需实施 + 验证状态=通过/不适用       → 已完成
移除已有 + 移除动作完成 + 验证通过/不适用       → 已完成
```

详细状态保留：

```text
范围状态：范围内 / 延后 / 范围外
处理方式：新实现 / 修改现有 / 复用已有 / 移除已有 / 无需实施 / 待决定
实施状态：未开始 / 实施中 / 已实施 / 不适用
验证状态：未验证 / 验证中 / 通过 / 失败 / 不适用
阻塞状态：未阻塞 / 已阻塞
是否必需：是 / 否
```

**不得让“当前状态”与详细状态矛盾。**

### 功能生命周期

功能层优先使用生命周期表达迁移阶段：

```text
已发现 → 已设计 → 实施中 → 验证中 → 已迁移 → 已清理
```

功能子项的“已完成”不自动等于整个功能“已迁移”。功能只有在所有范围内必需子项满足其处理方式的完成规则、源行为覆盖通过、必要验证通过后，才进入“已迁移”。

执行队列：

```text
待执行 / 当前执行 / 已阻塞 / 验证中 / 已完成
```

## 5. 风险分级与治理强度

开始迁移前给当前功能 / 工作流评估治理级别：

```text
低风险 / 中风险 / 高风险
```

### 低风险

适用于边界小、行为简单、目标仓库已有稳定同类模式、无关键权限/金额/状态机/数据契约变化的迁移。

默认要求：

- 功能台账与当前状态；
- 关键目标行为；
- 最小必要验证；
- 不强制独立 `07`、输入基线或多 Agent 编排。

### 中风险

适用于多个用户状态、较多源行为、权限/错误/导航/数据契约需要对齐，或需要跨会话推进的功能。

默认要求：

- 功能子项台账；
- 关键源行为 ID 和覆盖检查；
- 工作流 / 负责人；
- 子项级验证；
- 长任务维护输入基线。

### 高风险

适用于资金、权限、状态机、不可逆操作、多源冲突、跨技术栈大改、多人/多 Agent 并行、共享契约或高风险切流。

默认要求完整治理：

- 源行为契约与覆盖检查；
- 输入基线；
- 独立验证负责人或等价独立验证；
- 并行安全和工作区隔离；
- 工作流验证；
- 必要集成验证；
- 决策记录、回滚和清理条件。

**风险升级时立即补齐更高等级要求；风险降低不能用来跳过已经发现的关键问题。**

## 6. 证据与源行为

证据等级：

```text
C3 运行证据
C2 契约证据
C1 静态证据
C0 未知
```

关键功能应提取用户可观察行为，例如：入口、加载/空/错误/成功状态、字段显隐与格式、权限、校验、导航、状态流转、数据契约、集成、响应式、无障碍。

复杂功能为关键行为建立稳定 ID，例如 `SB-ORDER-001`。

每条源行为建议记录：

```text
源行为
当前状态
证据
目标决策
目标期望行为
关联功能子项
验证状态
阻塞状态
验证方式
```

**实施状态的权威源在 `02-迁移模块功能点清单.md`。** `07-源行为与目标对齐清单.md` 默认引用关联功能子项的实施状态，不重复维护实施事实；`07` 主要维护源行为决策、覆盖、验证状态、目标实际行为与验证证据。

## 7. 八阶段迁移流程

### Phase 1 — 意图、范围、风险和长期规则

明确保留/修改/删除/新增能力、非功能要求、发布/回滚、用户开发约束和风险级别。

### Phase 2 — 恢复源项目真实能力

从真实入口出发，结合调用链、权限、功能开关、测试、配置和运行证据恢复功能。**代码存在不等于现役。**

### Phase 3 — 建立必要强度的源行为契约

中/高风险功能必须为关键行为建立稳定 ID；低风险功能可以只记录少量关键行为，不机械展开完整矩阵。

### Phase 4 — 形成目标期望行为

多源先归一化：

```text
源项目 A/B/C → 统一功能 / 领域模型 → 目标期望行为
```

决策顺序：用户意图 → 目标产品 → Invariant → 目标项目稳定约束 → C3/C2 → C1 → 推断。

### Phase 5 — 目标原生设计

研究目标项目稳定相似实现和公共能力，决定模块、路由、数据、状态、界面、权限和测试。已有能力优先使用迁移决策 **“复用目标”**。

### Phase 6 — 功能台账和依赖

范围整理为：

```text
模块 → 功能 → 功能子项
```

至少维护：迁移决策、处理方式、当前状态、范围、是否必需、实施/验证/阻塞状态、源行为 ID，以及中/高风险时的工作流与负责人。

### Phase 7 — 切片 / 工作流实施

中/高风险工作流开始前通过 **源行为覆盖检查门槛**。低风险任务只检查与其风险相称的关键行为，不为形式补齐所有维度。

单工作流内只保持一个主要实施焦点；多个独立功能通过 **并行安全检查** 后可以并行。

### Phase 8 — 验证、集成、切流与清理

验证分为：

```text
子项验证 → 工作流验证 → 必要的集成验证
```

低风险单一工作流通常可在子项/功能验证后结束；中/高风险或存在共享运行边界时执行工作流验证和必要集成验证。

**必要的集成验证未通过时，不得宣布并行批次最终完成。**

## 8. 工作流输入基线

中/高风险长任务或多 Agent 工作流开始前冻结：

```text
源行为 / 证据版本
目标期望行为版本
迁移决策 / 用户规则版本
目标落点基线
开始时 Git 提交
```

关键输入变化影响当前实现时：

```text
已阻塞 → 更新输入基线 → 重新检查开始条件 → 再继续
```

## 9. 并行安全检查

并行前检查：相同生产文件/组件、路由/布局/状态/查询所有权、API/数据契约/共享类型、权限模型/状态机/Invariant、公共基础/抽象/Adapter/Feature Flag、lockfile、注册表、生成文件、共享脚本和明确先后依赖。

独立性必须同时覆盖：

```text
代码边界 + 数据/契约 + 业务语义 + 发布/合并路径
```

有高风险重叠时拆公共基础、指定唯一负责人或退回串行。

如果当前环境不支持创建子 Agent、独立 branch/worktree 或隔离工作区，**不得伪造并行能力**：保留工作流模型并由当前 Agent 串行执行；共享 working tree 无法安全隔离时退回串行。

## 10. 负责人和状态写入

- 同一功能子项同时只能有一个生产代码负责人；
- 共享契约 / 公共基础必须唯一负责人；
- 实施负责人更新 `02` 中自己拥有的子项实施状态和当前状态；
- 验证负责人更新验证状态、验证结果和当前状态；
- 分析 Agent 更新分析输出和源行为，不写生产代码；
- 协调 Agent 汇总活跃工作流、跨工作流依赖/冲突和 `00-迁移状态总览.md`。

## 11. 工作流开始条件

按风险级别确认必要项：

- 目标期望行为、迁移决策、处理方式和功能子项明确；
- 当前状态已初始化；
- 中/高风险时源行为覆盖检查通过；
- 中/高风险长任务时输入基线已记录；
- 目标落点、依赖、验证方式存在；
- 生效用户规则检查通过；
- 并行时并行安全、工作区隔离和负责人明确。

## 12. 完成条件与集成验证

切片 / 工作流完成至少满足：

- 功能子项当前状态与实际代码一致；
- 所有范围内必需子项按各自处理方式达到完成条件；
- 源行为映射无遗漏；
- 要求的验证通过；
- 新发现源行为 / 子项已写回；
- 输入基线无未处理漂移；
- 业务规则、Invariant、权限、数据契约、错误路径已覆盖；
- 未违反生效用户规则。

以下任一情况存在时，合并后 **强制执行集成验证**：

- 共享路由 / 布局；
- 共享 API / 查询 / 状态；
- 共享权限模型；
- 共享依赖 / lockfile；
- 共享设计系统 / 全局样式；
- 共享注册表 / codegen / generated 文件；
- 同一个发布批次或切流批次。

## 13. 澄清循环

```text
必须询问 / 可推断 / 可延后
```

只有证据不足且会实质改变目标行为或不可逆方向时才“必须询问”。目标仓库稳定工程惯例优先“可推断”。

## 14. 用户规则

规则结构：`作用域 + 触发条件 + 强度 + 动作/约束`。

强度：`必须 / 禁止 / 必须询问 / 建议`；状态：`生效中 / 已暂停 / 已失效`。

必须工具不可用时不得静默替代，相关操作标记“已阻塞”，由用户决定启用、替代、改规则或延后。

## 15. 跨会话恢复

新对话恢复：总体状态和活跃工作流 → 生效用户规则 → 功能台账 → 源行为/迁移决策/输入基线 → 执行计划 → Git/working tree/代码/测试 → 必要时最小重新校准。

## 16. 禁止方式

- 不按文件或源目录树一一迁移；
- 不机械复制旧 Store/API/组件层；
- 不因为代码存在就恢复废弃能力；
- 不用执行队列代替功能台账；
- 不让切片“已完成”掩盖未完成子项；
- 不让验证失败项没有明确当前状态；
- 不让当前状态与详细状态矛盾；
- 不把复用目标/无需实施伪造成写过代码；
- 不让 `02` 与 `07` 双写同一实施事实；
- 不让低风险任务机械承担高风险治理成本；
- 不在关键源行为未覆盖时大规模实施；
- 不让多个 Agent 并行写同一子项、共享契约或无法隔离的工作区；
- 不因各工作流单独通过就跳过强制集成验证；
- 不在输入基线过期后继续开发；
- 不静默违反用户规则。

## 17. 结束报告

至少说明：目标与完成能力、功能/子项/源行为当前状态、迁移决策与处理方式、风险级别、源行为覆盖、工作流/负责人/输入基线、验证/集成验证、阻塞/延后/澄清、关键用户规则、下一动作和 `.code-migration/` 同步状态。
