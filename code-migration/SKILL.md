---
name: code-migration
description: 用于将一个或多个现有项目中的功能、业务规则和用户能力迁移、融合或重构到目标项目。适用于跨仓库、跨框架、多项目融合、前端页面重建、功能删改融合和渐进切流。迁移以真实源证据、功能发现真实性、目标期望行为、交互语义、页面结构和目标原生架构为中心；按合理功能层级拆分，以原子功能项作为完成事实源，并支持批量开发、批量验证、风险治理、跨会话恢复和受控多 Agent 并行。

# Code Migration

把代码迁移视为 **业务能力在新上下文中的受控重建**，不是文件搬运或旧架构复制。

```text
源证据
→ 功能发现覆盖 + 来源真实性
→ 源行为 / 交互 / 页面结构契约
→ 用户新方案 + 目标产品要求
→ 目标原生设计
→ 模块 / 功能 / 功能项组 / 原子功能项
→ 批量实施 + 批量验证
→ 功能 / 模块派生完成
→ 集成 / 切流 / 清理
```

## 1. 核心原则

1. **迁移的是能力，不是文件。**
2. **Source 是事实，不是 Target 规范。**
3. **既防漏功能，也防幻觉新增。** 正式范围必须有来源证明。
4. **拆分粒度与执行粒度分离。** 原子项可以一起开发、一起验证，但状态逐项落账。
5. **原子功能项才是完成事实源。** 组、功能、模块状态只能向上派生。
6. **交互语义必须显式。** 不能把复杂交互简化成“触发 API”。
7. **页面结构必须显式。** 复杂页面验证区域关系、响应式和空间结构，不只验证元素存在。
8. **用户的新迁移方案决定目标变化。** 新 UX / 布局 / 交互方案优先于 Source 旧形态。
9. **Target 决定实现形状。** 遵循目标仓库稳定架构和 Design System。
10. **治理强度按风险自适应。**
11. **状态实时更新。** 不先批量开发完再补台账。
12. **迁移完成包括验证、集成、切流和清理。**

## 2. 工作区

已有 `.code-migration/` 时恢复顺序：

1. `00-迁移状态总览.md`；
2. 用户新方案、生效规则、活跃工作流、输入基线；
3. `02-迁移模块功能点清单.md`；
4. 中/高风险的 `07-源行为与目标对齐清单.md`；
5. 复杂前端的 `08-页面结构与交互对齐清单.md`；
6. `05-迁移执行计划.md`；
7. Git、代码和测试。

长周期迁移按需创建：

```text
.code-migration/
├── 00-迁移状态总览.md
├── 01-迁移任务上下文.md
├── 02-迁移模块功能点清单.md
├── 03-功能融合映射.md
├── 04-迁移决策记录.md
├── 05-迁移执行计划.md
├── 06-迁移约束与开发规则.md
├── 07-源行为与目标对齐清单.md
├── 08-页面结构与交互对齐清单.md
└── modules/<module>/
```

小任务不机械创建全部文档。

## 3. 功能发现与来源真实性

中/高风险同时执行：

```text
正向：入口 → 行为 → 状态/数据 → API → 副作用 → 用户结果
反向：API/Mutation/状态/Event → 调用方 → 条件/权限/Flag → 用户场景
```

检查入口、次级操作、Role、状态分支、Feature Flag、API 调用方、轮询/Event、Storage/Cache、错误恢复、URL/Back、测试隐含规则和跨模块副作用。

正式功能 / 原子项来源类型：

```text
源系统证据
用户明确新增
目标产品要求
目标项目强制约束
推断候选
未知
```

`推断候选 / 未知` 不得静默进入 `范围内 + 必需=是`。

以下不能单独证明需要新增产品能力：

```text
行业惯例
Agent 建议
目标项目其他页面有
目标仓库有现成组件
```

目标已有能力只能决定 **如果需要，如何实现**，不能决定产品范围。

## 4. 合理功能层级

统一使用：

```text
模块
└─ 功能
   ├─ 功能项组 / 场景组（可选）
   │  ├─ 原子功能项
   │  └─ 原子功能项
   └─ 原子功能项
```

### 模块

稳定业务边界或页面能力集合，例如订单中心。模块不按源码目录机械拆分。

### 功能

用户可独立描述的完整能力，例如“发起退款”。功能必须有完整 Done Gate。

### 功能项组 / 场景组

用于聚合强关联原子项，适合一起开发或在同一用户场景下一起验证。它是组织 / 调度层，不是独立完成事实源。

### 原子功能项

最小实施 / 验证单元，满足：

```text
一个主要目标
+ 清晰触发 / 条件
+ 可判断实施完成
+ 可判断验证通过
```

如果一个条目中的多个点能够独立遗漏、独立失败、独立验证或被用户单独保留/移除，就必须拆分。

不要把：

```text
退款支持金额校验、重复提交、409 恢复、成功刷新
```

当成一个原子项。应放进同一“退款提交”组，拆成多个可验证原子项。

也不要拆到 DOM、函数、变量级。

## 5. 开发批次与验证批次

**原子拆分不代表必须一个个串行做。**

```text
I01 ─┐
I02 ─┼→ DEV-001 一起开发
I03 ─┘

I01 ─┐
I02 ─┼→ VER-001 同一用户场景一起验证
I03 ─┘
```

规则：

- 开发批次减少上下文切换，不改变原子项独立状态；
- 一次开发完成后逐原子项更新实施状态；
- 验证可以一次准备环境 / 数据并覆盖多个项；
- 每个原子项仍有独立验证结论和证据；
- 批次通过不能覆盖单项失败；
- 批次完成不能直接让功能或模块完成。

## 6. 迁移决策与状态

迁移决策：

```text
保留 / 适配 / 合并 / 拆分 / 移除
替换 / 复用目标 / 新增 / 延后 / 未知
```

处理方式：

```text
新实现 / 修改现有 / 复用已有 / 移除已有 / 无需实施 / 待决定
```

`复用目标 / 无需实施` 不要求伪造“已实施”，但必须验证。

原子功能项当前状态：

```text
未开始 / 开发中 / 待验证 / 验证中 / 验证失败
已完成 / 已阻塞 / 已延后 / 不适用
```

详细状态：

```text
范围：范围内 / 延后 / 范围外
实施：未开始 / 实施中 / 已实施 / 不适用
验证：未验证 / 验证中 / 通过 / 失败 / 不适用
阻塞：未阻塞 / 已阻塞
必需：是 / 否
```

`验证状态=失败 → 当前状态=验证失败`；只有真实阻塞时才为 `已阻塞`。

## 7. 向上派生完成状态

### 功能项组

完全由组内范围内必需原子项派生：阻塞优先，其次验证失败、开发中、待验证/验证中，全部完成才是 `已完成`。

### 功能

生命周期：

```text
已发现 → 已设计 → 实施中 → 验证中 → 已迁移 → 已清理
```

只有全部范围内必需原子项完成、要求的发现/行为/交互/结构验证通过、必要集成验证通过，才可 `已迁移`。

**完成一个原子项、一个组或一个开发批次，都不能直接把功能标为已迁移。**

### 模块

模块只能在：

- 所有范围内必需功能达到目标生命周期；
- 无必需功能验证失败 / 阻塞 / 未完成；
- 模块共享 Route/API/State/Permission/Style 的必要集成验证通过；
- 模块级用户目标与新方案成立；

之后标为 `已完成`。

## 8. 风险治理

### 低风险

功能台账、来源真实性、目标行为、合理拆分、最小验证。

### 中风险

增加功能发现覆盖、关键源行为、复杂交互、主要页面结构、子项验证和长任务输入基线。

### 高风险

增加完整触点/反向追踪、完整源行为契约、`08`、C3 页面/交互证据、独立验证、并行安全、工作流/集成验证、回滚和清理。

风险升级立即补齐高一级要求。

## 9. 源行为契约

证据等级：

```text
C3 运行证据
C2 契约 / 设计 / 视觉测试证据
C1 静态代码证据
C0 未知
```

`02` 是范围、分组、原子项、处理方式和实施状态的权威源；`07` 维护源行为决策、覆盖、目标实际表现和验证证据。

## 10. 交互语义

复杂交互至少恢复：

```text
前置条件
→ 触发方式
→ 即时反馈
→ 中间状态
→ 数据操作
→ 成功 / 失败
→ 副作用
→ 交互收尾
```

检查隐藏/禁用、Modal/Drawer/Page、Loading/Optimistic、重复提交、Cancel/debounce、输入保留、Retry、URL/Back、Focus/Keyboard、Scroll。

交互决策：

```text
保持交互 / 目标适配 / 按新方案重构
合并 / 拆分 / 移除 / 新增 / 复用目标交互 / 未知
```

用户批准的新交互方案按新方案验证。

## 11. 页面结构与视觉

中/高风险复杂前端使用 `08-页面结构与交互对齐清单.md`。

恢复用户感知区域树，并记录父区域、排列、宽度/比例、对齐、Gap/Padding、Scroll Owner、Sticky/Fixed、显隐和响应式变化。

结构决策：

```text
保持结构 / 目标适配 / 按新方案重构
合并区域 / 拆分区域 / 移除区域
新增区域 / 复用目标结构 / 未知
```

目标结构优先级：用户新方案 → 目标产品 → 布局/交互 Invariant → Target 稳定模式 → Source C3/C2 → C1 → 推断。

## 12. Ready Gate

工作流开始前按风险确认：

```text
合理拆分 / 原子性
+ 来源真实性
+ 功能发现覆盖
+ 源行为覆盖
+ 交互语义覆盖
+ 页面结构覆盖
```

并确认验证方式、用户规则、目标落点、依赖和输入基线（如要求）。

## 13. 实施与验证

推荐循环：

```text
选择强关联原子项
→ DEV 批次一起开发
→ 逐项更新实施状态
→ VER 批次一起跑完整用户场景
→ 逐项写验证结论
→ 派生功能项组状态
→ 派生功能生命周期
→ 派生模块状态
```

开发中发现新能力：先登记候选 → 来源/范围 → 原子拆分 → 契约 → 再决定是否加入当前 DEV/VER 批次。

## 14. 并行与集成

同一原子项只能有一个生产代码负责人。共享契约 / 公共基础必须唯一负责人。

并行前检查共享文件、Route/Layout/State/Query ownership、API/契约、权限/状态机、公共基础、lockfile、registry、generated、全局样式和先后依赖。

环境不支持子 Agent / worktree 时不得伪造并行，保留批次模型并串行执行。

共享 Route/Layout、API/State、权限、依赖/lockfile、Design System/全局样式、registry/generated 或同一发布批次时，合并后强制集成验证。

## 15. 澄清与用户规则

```text
必须询问 / 可推断 / 可延后
```

只有证据不足且会改变产品行为、权限、数据、范围、交互/页面目标或不可逆方向时才必须询问。

用户规则：`作用域 + 触发条件 + 强度 + 动作/约束`。必须工具不可用时不得静默替代。

## 16. 禁止方式

- 不按文件/目录树迁移；
- 不只从 UI 单向扫描；
- 不把推断/行业惯例/Agent 建议当正式需求；
- 不因为 Target 有组件就自动新增功能；
- 不把复合功能点当原子项；
- 不把原子项拆到代码实现细节；
- 不因一个原子项完成就标整个组/功能/模块完成；
- 不因 DEV/VER 批次完成就覆盖逐项状态；
- 不把用户批准的新 UX 修回 Source；
- 不把复杂交互简化成 API 调用；
- 不把元素存在当结构验证通过；
- 不跳过验证失败、阻塞或强制集成验证。

## 17. 结束报告

至少说明：模块/功能/功能项组/原子项完成度、DEV/VER 批次、功能发现和来源真实性、源行为、用户新 UX、交互/结构验证、验证失败/阻塞、集成验证和下一动作。
