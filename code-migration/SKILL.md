---
name: code-migration
description: 用于将一个或多个现有项目中的功能、业务规则和用户能力迁移、融合或重构到目标项目。适用于前端项目迁入新仓库、跨框架或技术栈重实现、多个旧项目能力合并、模块整合、功能删改融合、目标架构适配与渐进切流。迁移以源行为证据、目标期望行为和目标项目原生架构为中心，先建立可追踪的源行为契约和功能台账，再按切片 / 工作流实施、验证与清理；默认不按源文件、目录、组件或状态结构一比一翻译，并支持通过安全检查后的多 Agent 受控并行迁移。
---

# Code Migration

把代码迁移视为 **“业务能力在新上下文中的受控重建”**，不是文件搬运或旧架构复制。

```text
源证据
→ 源行为契约
→ 目标期望行为
→ 目标原生设计
→ 模块 / 功能 / 功能子项台账
→ 切片 / 受控工作流
→ 实施 / 验证 / 集成
→ 切流 / 清理
```

## 1. 核心原则

1. **迁移的是能力，不是文件。** 源文件只是证据，不是迁移边界。
2. **源项目是事实，不是目标规范。** 它说明旧系统实际做了什么。
3. **关键源行为必须可追踪。** 每条关键行为决定“保持 / 目标修改 / 不迁移 / 未知”。
4. **用户意图与目标产品决定目标行为。** 必须保留的 Invariant 不得因技术迁移丢失。
5. **目标项目决定实现形状。** 路由、状态、数据层、组件、目录、错误和测试遵循目标仓库惯例。
6. **功能台账维护完整范围。** 执行队列只负责调度。
7. **每个工作流单焦点，全局可安全并行。** 独立功能通过并行安全检查后可由不同实施负责人同时开发。
8. **状态实时更新。** 功能、功能子项、源行为都必须直接显示当前状态。
9. **用户规则是执行约束。** 每个切片 / 工作流开始前检查生效规则。
10. **验证面向目标行为。** 保持项验证不回归，批准变化验证新行为正确。
11. **机械变化自动化，语义变化分析，产品变化显式决策。**
12. **迁移完成还包括集成、切流和遗留清理。**

## 2. 启动方式

先识别源项目、目标项目、迁移目标、用户约束和目标技术栈，再检查目标仓库根目录 `.code-migration/`。

### 已有工作区

按顺序恢复：

1. `00-迁移状态总览.md`；
2. 活跃工作流、负责人、输入基线；
3. `06-迁移约束与开发规则.md`；
4. `02-迁移模块功能点清单.md`；
5. `07-源行为与目标对齐清单.md` 或模块行为文档；
6. 迁移决策、执行计划；
7. Git、代码和测试状态。

不一致时先最小范围重新校准，不重新扫描全部源项目。

### 新工作区

长周期迁移按需创建：

```text
.code-migration/
├── 00-迁移状态总览.md
├── 01-迁移任务上下文.md
├── 02-迁移模块功能点清单.md
├── 03-功能融合映射.md
├── 04-迁移决策记录.md
├── 05-迁移执行计划.md
├── 06-迁移约束与开发规则.md
├── 07-源行为与目标对齐清单.md
└── modules/<module>/
```

小任务不机械生成全部文档。

## 3. 迁移决策

功能迁移决策统一使用中文：

```text
保留 / 适配 / 合并 / 拆分 / 移除
替换 / 复用目标 / 新增 / 延后 / 未知
```

- `保留`：目标继续保留能力和关键行为，实现方式可以变化；
- `适配`：能力保留，但按目标要求调整行为或实现；
- `合并`：多个来源融合为一个目标能力；
- `拆分`：一个源能力拆为多个目标能力；
- `移除`：目标明确不需要；
- `替换`：由新的产品能力或实现取代；
- `复用目标`：目标仓库已有能力可直接复用；
- `新增`：迁移范围内明确新增；
- `延后`：相关但当前阶段不处理；
- `未知`：证据不足，尚不能安全决策。

源行为决策使用：

```text
保持 / 目标修改 / 不迁移 / 未知
```

重大移除、合并、替换、Invariant 变化或高风险产品变化应记录迁移决策。

## 4. 运行时状态

### **当前状态**

所有可开发或验证的功能、功能子项、源行为必须显式展示：

```text
未开始 / 开发中 / 待验证 / 验证中 / 已完成 / 已阻塞 / 已延后 / 不适用
```

当前状态由详细状态推导：

```text
阻塞状态=已阻塞                         → 已阻塞
范围状态=延后                           → 已延后
范围外 / 明确不迁移                     → 不适用
实施状态=未开始                         → 未开始
实施状态=实施中                         → 开发中
实施状态=已实施 + 验证状态=未验证       → 待验证
验证状态=验证中                         → 验证中
实施状态=已实施 + 验证状态=通过/不适用  → 已完成
```

详细状态保留：

```text
范围状态：范围内 / 延后 / 范围外
实施状态：未开始 / 实施中 / 已实施
验证状态：未验证 / 验证中 / 通过 / 失败 / 不适用
阻塞状态：未阻塞 / 已阻塞
是否必需：是 / 否
```

**不得让“当前状态”与详细状态矛盾。**

### 功能生命周期

```text
已发现 → 已设计 → 实施中 → 验证中 → 已迁移 → 已清理
```

执行队列：

```text
待执行 / 当前执行 / 已阻塞 / 验证中 / 已完成
```

## 5. 证据与源行为

证据等级：

```text
C3 运行证据
C2 契约证据
C1 静态证据
C0 未知
```

关键功能应提取用户可观察行为，例如：入口、加载/空/错误/成功状态、字段显隐与格式、权限、校验、导航、状态流转、数据契约、集成、响应式、无障碍。

复杂功能为关键行为建立稳定 ID，例如：

```text
SB-ORDER-001
```

每条源行为建议记录：

```text
源行为
当前状态
证据
目标决策
目标期望行为
关联功能子项
实施状态
验证状态
阻塞状态
验证方式
```

详见 `references/11-源行为契约与开发对齐.md`。

## 6. 八阶段迁移流程

### Phase 1 — 意图、范围和长期规则

明确保留/修改/删除/新增能力、非功能要求、发布/回滚和用户开发约束。

长期规则写入 `06-迁移约束与开发规则.md`。

### Phase 2 — 恢复源项目真实能力

从真实入口出发，结合调用链、权限、功能开关、测试、配置和运行证据恢复功能。**代码存在不等于现役。**

### Phase 3 — 建立源行为契约

所有“保持”行为必须映射至少一个范围内功能子项；所有“目标修改”必须写明新的目标期望行为。

### Phase 4 — 形成目标期望行为

多源先归一化：

```text
源项目 A/B/C → 统一功能 / 领域模型 → 目标期望行为
```

决策顺序：用户意图 → 目标产品 → Invariant → 目标项目稳定约束 → C3/C2 → C1 → 推断。

关键冲突无法安全决定时进入澄清循环。

### Phase 5 — 目标原生设计

研究目标项目稳定相似实现和公共能力，决定模块、路由、数据、状态、界面、权限和测试。已有能力优先使用迁移决策 **“复用目标”**。

### Phase 6 — 功能台账和依赖

范围整理为：

```text
模块 → 功能 → 功能子项
```

功能 / 子项至少维护：

```text
迁移决策
当前状态
范围状态
是否必需
实施状态
验证状态
阻塞状态
源行为 ID
工作流 / 实施负责人 / 验证负责人
```

### Phase 7 — 切片 / 工作流实施

开始前通过 **源行为覆盖检查门槛**：

- 关键源行为已盘点并有 ID；
- 每条行为已决定“保持 / 目标修改 / 不迁移 / 未知”；
- 每条范围内行为已初始化当前状态和详细状态；
- 所有“保持”行为已映射范围内功能子项；
- 所有“目标修改”有明确目标期望行为；
- 权限、状态、错误、加载、空状态、导航、数据契约等适用维度已覆盖；
- 不存在会改变方向的关键“未知”。

再检查用户规则、目标项目准备度和依赖。

单工作流内只保持一个主要实施焦点；多个独立功能通过 **并行安全检查** 后可以并行。

### Phase 8 — 验证、集成、切流与清理

验证分为：

```text
工作流验证 → 集成验证门槛
```

工作流验证逐项验证当前功能子项与源行为/目标行为，并同步当前状态。

多个工作流合并后，按风险执行集成验证：构建、类型检查、共享测试、路由/权限、共享状态/查询/API、端到端测试、样式/包体积、用户规则等。

**必要的集成验证未通过时，不得宣布并行批次最终完成。**

## 7. 工作流输入基线

实施工作流开始前冻结：

```text
源行为 / 证据版本
目标期望行为版本
迁移决策 / 用户规则版本
目标落点基线
开始时 Git 提交
```

关键输入变化影响当前实现时：

```text
已阻塞 → 更新输入基线 → 重新检查开始条件 → 再继续
```

不得按过期行为模型继续开发。

## 8. 并行安全检查

并行前检查：

- 相同生产文件/组件；
- 路由 / 布局 / 状态 / 查询所有权；
- API / 数据契约 / 共享类型；
- 权限模型、状态机、Invariant；
- 未完成公共基础；
- 公共抽象 / Adapter / Feature Flag；
- package manifest / lockfile；
- barrel/index、路由/导航/权限注册表；
- codegen/schema/generated/i18n 聚合文件；
- 共享生成器/脚本；
- 明确先后依赖。

独立性必须同时覆盖：

```text
代码边界 + 数据/契约 + 业务语义 + 发布/合并路径
```

有高风险重叠时拆公共基础、指定唯一负责人或退回串行。

并行写代码优先独立 branch / worktree / isolated workspace；共享 working tree 无法可靠隔离时退回串行。

## 9. 负责人和状态写入

- 同一功能子项同时只能有一个生产代码负责人；
- 共享契约 / 公共基础必须唯一负责人；
- 实施负责人更新自己拥有的子项实施状态和当前状态；
- 验证负责人更新验证状态、验证结果和当前状态；
- 分析 Agent 更新分析输出和源行为，不写生产代码；
- 协调 Agent 汇总活跃工作流、跨工作流依赖/冲突和 `00-迁移状态总览.md`。

协调 Agent 不是所有细粒度状态的唯一写入者，但同一状态块同时只能有一个负责人。

## 10. 工作流开始条件

实施前确认：

- 源行为覆盖检查已通过；
- 目标期望行为、迁移决策和功能子项已明确；
- 每个范围内子项 / 行为已初始化当前状态；
- 输入基线已记录；
- 目标落点、依赖、验证方式存在；
- 生效用户规则检查通过；
- 并行时已确认并行安全、工作区隔离和负责人。

规则处理：

```text
必须未满足 → 不开始
违反禁止 → 改方案
必须询问未确认 → 已阻塞
偏离建议 → 记录原因
```

## 11. 完成条件与集成验证

切片 / 工作流完成至少满足：

- 功能子项 / 源行为当前状态与实际代码一致；
- 所有范围内必需子项当前状态达到“已完成”；
- 源行为映射无遗漏；
- 工作流验证通过；
- 新发现源行为 / 子项已写回；
- 输入基线无未处理漂移；
- 业务规则、Invariant、权限、数据契约、错误路径已覆盖；
- 未违反生效用户规则。

存在共享运行边界的多个工作流合并后必须再通过集成验证门槛。

## 12. 澄清循环

```text
必须询问 / 可推断 / 可延后
```

只有证据不足且会实质改变目标行为或不可逆方向时才“必须询问”。目标仓库稳定工程惯例优先“可推断”。

## 13. 用户规则

规则结构：

```text
作用域 + 触发条件 + 强度 + 动作/约束
```

强度：`必须 / 禁止 / 必须询问 / 建议`；状态：`生效中 / 已暂停 / 已失效`。

必须工具不可用时不得静默替代，相关操作标记“已阻塞”，由用户决定启用、替代、改规则或延后。

## 14. 跨会话恢复

新对话恢复：

1. 总体状态和活跃工作流；
2. 生效用户规则；
3. 功能 / 功能子项台账及当前状态；
4. 源行为 / 迁移决策 / 输入基线及当前状态；
5. 执行计划；
6. Git、working tree、代码和测试；
7. 不一致时最小重新校准。

## 15. 禁止方式

- 不按文件或源目录树一一迁移；
- 不机械复制旧 Store/API/组件层；
- 不因为代码存在就恢复废弃能力；
- 不用执行队列代替功能台账；
- 不让切片“已完成”掩盖未完成子项；
- 不让功能子项 / 源行为缺失 **当前状态**；
- 不让当前状态与实施/验证/阻塞详细状态矛盾；
- 不在关键源行为未覆盖时大规模实施；
- 不让多个 Agent 并行写同一子项、共享契约或无法隔离的工作区；
- 不因各工作流单独通过就跳过必要集成验证；
- 不在输入基线过期后继续开发；
- 不静默违反用户规则；
- 不通过放宽测试阈值或删除断言证明成功。

## 16. 结束报告

至少说明：目标与完成能力、功能/子项/源行为当前状态、源行为覆盖、工作流/负责人/输入基线、工作流验证/集成验证、阻塞/延后/澄清、关键用户规则、下一动作和 `.code-migration/` 同步状态。
