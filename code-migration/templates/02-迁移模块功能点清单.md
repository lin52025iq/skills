# 迁移模块功能点清单

> 这是迁移范围与完成度的权威台账。**范围要合理拆分，完成状态必须由最小可验证功能项向上汇总，禁止因为完成某个局部点就把整个功能或模块标为完成。**

## 层级模型

```text
模块
└─ 功能
   ├─ 功能项组 / 场景组（可选）
   │  ├─ 原子功能项
   │  └─ 原子功能项
   └─ 原子功能项
```

### 模块

代表稳定的业务边界、页面区域或用户能力集合，例如“订单中心”“用户管理”。不要按源码目录机械拆模块。

### 功能

代表一个用户能够独立描述的目标能力，例如“查看订单详情”“发起退款”。功能必须能够定义完整完成条件。

### 功能项组 / 场景组

只在以下情况使用：

- 多个原子功能项属于同一用户场景；
- 多个项共享实现上下文，适合一起开发；
- 多个项需要在同一运行场景下一起验证；
- 直接把所有原子项平铺会明显降低可读性。

功能项组是 **聚合与调度视图**，不拥有独立的“手工完成”事实；其状态由组内必需原子项派生。

### 原子功能项

原子功能项是最小实施 / 验证单元，必须满足：

```text
一个主要目标
+ 清晰触发 / 条件
+ 可判断是否实施
+ 可判断是否验证通过
```

如果一个条目同时包含多个可以独立失败、独立遗漏或独立验证的结果，应拆分。

例如不要写：

```text
退款弹窗支持金额校验、重复提交保护、409 恢复、成功刷新列表
```

应合理拆成同一个“退款提交”功能项组下的原子项：

```text
I01 金额校验
I02 重复提交保护
I03 409 冲突恢复并保留输入
I04 成功后关闭弹窗并刷新相关数据
```

但不要继续拆成 div、函数、变量或每一行代码。

## 拆分判断规则

优先按照 **用户场景 + 独立失败边界 + 独立验证边界** 拆分，而不是按文件数量拆分。

需要拆分的信号：

- 有不同权限 / Feature Flag / 状态前置条件；
- 成功 / 失败后果不同；
- 一个点可以完成而另一个仍未实现；
- 一个点验证失败不代表另一个失败；
- 有不同数据契约、副作用、导航或交互收尾；
- 用户可能单独保留、修改、移除其中一个点。

可以放在同一原子项的情况：

- 它们共同组成一个不可再分的业务动作；
- 拆开后无法独立定义用户结果；
- 必须在同一个事务 / 状态转换中一起成立。

## 开发批次与验证批次

**拆分粒度不等于执行粒度。** 多个原子功能项可以一起开发、一起验证。

```text
原子功能项 A ─┐
原子功能项 B ─┼→ 开发批次 DEV-001
原子功能项 C ─┘

原子功能项 A ─┐
原子功能项 B ─┼→ 验证批次 VER-001
原子功能项 C ─┘
```

规则：

1. 开发批次用于减少上下文切换，不改变原子项的独立状态；
2. 一次开发可以完成多个原子项，完成后逐项更新实施状态；
3. 验证可以按场景批量执行，但每个原子项仍必须有明确验证结论；
4. 批次“通过”不能覆盖某个原子项的失败；
5. 功能项组“完成”只表示组内所有范围内必需原子项达到完成条件；
6. 功能“已迁移”只由全部必需原子项、覆盖 Gate 和必要集成验证共同推导；
7. 模块“已完成”只由全部范围内必需功能达到目标生命周期并通过模块级集成条件推导。

## 来源类型

```text
源系统证据
用户明确新增
目标产品要求
目标项目强制约束
推断候选
未知
```

**只有前四类可以直接进入正式范围。** `推断候选 / 未知` 不能静默成为 `范围内 + 必需=是`。

## 迁移决策与处理方式

迁移决策：

```text
保留 / 适配 / 合并 / 拆分 / 移除
替换 / 复用目标 / 新增 / 延后 / 未知
```

处理方式：

```text
新实现 / 修改现有 / 复用已有 / 移除已有 / 无需实施 / 待决定
```

## 原子功能项状态

### 当前状态

```text
未开始 / 开发中 / 待验证 / 验证中 / 验证失败
已完成 / 已阻塞 / 已延后 / 不适用
```

详细状态：

```text
范围状态：范围内 / 延后 / 范围外
处理方式：新实现 / 修改现有 / 复用已有 / 移除已有 / 无需实施 / 待决定
实施状态：未开始 / 实施中 / 已实施 / 不适用
验证状态：未验证 / 验证中 / 通过 / 失败 / 不适用
阻塞状态：未阻塞 / 已阻塞
是否必需：是 / 否
```

推导原则：

- `验证状态=失败` → `验证失败`；
- `实施状态=实施中` → `开发中`；
- 处理动作满足但未验证 → `待验证`；
- 验证中 → `验证中`；
- 处理动作满足且验证通过 / 不适用 → `已完成`；
- 存在真实阻塞 → `已阻塞`。

## 功能生命周期

```text
已发现 → 已设计 → 实施中 → 验证中 → 已迁移 → 已清理
```

**功能层不使用某一个原子项的状态代替自身生命周期。**

- `已发现`：范围、来源或目标行为仍不完整；
- `已设计`：必需原子项、分组、来源、目标行为和必要 Gate 已明确；
- `实施中`：至少一个范围内必需原子项尚未满足处理要求；
- `验证中`：所有处理要求已满足，但仍存在未验证 / 验证中 / 验证失败；
- `已迁移`：全部范围内必需原子项已完成，并通过要求的发现 / 行为 / 交互 / 结构 / 集成验证；
- `已清理`：目标能力稳定且旧入口 / 临时结构已安全退出。

### 模块完成规则

模块只能在以下条件同时满足时标为 `已完成`：

- [ ] 所有范围内必需功能均达到 `已迁移 / 已清理` 中要求的目标状态；
- [ ] 不存在必需功能处于实施中、验证失败或已阻塞；
- [ ] 模块共享路由 / 状态 / API / 权限 / 样式等必要集成验证通过；
- [ ] 模块级用户目标和用户新方案已满足；
- [ ] 没有被单个功能“完成”掩盖的未迁移能力。

### 原子性检查

- [ ] 每个原子项只有一个主要用户 / 业务目标；
- [ ] 每个原子项可以明确判断实施完成与否；
- [ ] 每个原子项可以明确判断验证通过与否；
- [ ] 不存在“完成其中一个点就会误标整个条目完成”的复合条目；
- [ ] 没有拆到 DOM / 函数 / 变量等无业务意义粒度；
- [ ] 强关联项已经按场景合理放入功能项组。

### 功能发现与真实性检查

- [ ] 用户可达入口、主要/次级操作已检查；
- [ ] 权限 / Role / Flag / 状态分支已检查；
- [ ] API / Mutation / 状态转换已反向查调用方；
- [ ] 自动行为、副作用、异常恢复、URL / Storage / Cache 已检查；
- [ ] 每个正式原子项有合法来源；
- [ ] 推断候选 / 未知没有静默进入必需范围。

### 前端结构 / 交互检查

复杂中/高风险前端页面：

- [ ] 用户新的 UX / 布局方案已进入目标决策；
- [ ] 关键交互语义、页面区域树、响应式和布局不变量已明确；
- [ ] `08` 已建立或明确不要求。

### 功能完成检查门槛

- [ ] 所有范围内必需原子功能项已识别；
- [ ] 所有复合条目已按独立失败 / 验证边界合理拆分；
- [ ] 每个功能项组内所有范围内必需原子项均达到完成条件；
- [ ] 所有范围内必需原子项均为 `已完成`；
- [ ] 不存在验证失败 / 已阻塞的必需原子项；
- [ ] 要求的功能发现 / 源行为 / 页面结构 / 交互验证已通过；
- [ ] 批量验证结果已经逐项回写，没有用“批次通过”覆盖单项遗漏；
- [ ] 必要集成验证已通过；
- [ ] 功能生命周期按全部原子项重新计算。

## 开发与验证纪律

```text
选择一个或多个强关联原子项
→ 建立开发批次
→ 一起开发
→ 逐项更新实施状态
→ 建立验证批次
→ 在同一用户场景下一起验证
→ 每个原子项分别记录验证结论
→ 汇总功能项组状态
→ 汇总功能生命周期
→ 汇总模块状态
```

**开发批次 / 验证批次是效率工具，不是完成事实源。**

开发中发现新能力时，先作为候选加入对应功能 / 功能项组，判断来源、是否必需和原子拆分，再决定是否进入当前开发批次。
