# 迁移模块功能点清单

> 这是迁移范围与完成度的功能级台账，独立于 Slice Queue。Slice Queue 负责“现在做什么”，本文件负责“完整有哪些模块、功能、子功能项，以及每一项做到什么程度”。开发过程中必须持续更新，不能等一个大 Feature 结束后才补记录。

## 层级模型

```text
Module
  └─ Feature
       └─ Feature Item / 子功能项
```

- **Module**：业务或页面区域，例如“订单中心”“Dashboard”。
- **Feature**：可独立描述用户目标的能力，例如“订单详情”“退款审批”。
- **Feature Item**：Feature 内需要实现或验证的具体细项，例如“基础信息展示”“403 权限处理”“加载状态”“退款原因校验”。
- **Slice**：执行调度单位，可以覆盖一个完整 Feature，也可以只覆盖一个 Feature 中明确的一组 Feature Items；Slice 本身不是功能范围的唯一事实源。

## 使用规则

1. 业务模块、跨页面迁移、多项目融合和长周期迁移默认创建本文件；单组件或很小的单次任务可省略。
2. 在大规模开发前先完成第一版 Module → Feature → Feature Item 盘点；允许随着理解加深增删或拆分，但需要同步依据。
3. 每个 Feature 必须有稳定 Feature ID；重要 Feature Item 也应有稳定 Item ID，便于跨会话引用。
4. Slice Queue 不能替代本清单。即使当前没有安排开发，也要保留未开始、延后、不迁移、复用目标能力等功能项。
5. 开始开发某个 Feature Item 时立即更新其实施状态；不要等 Slice 完成后批量补状态。
6. 一个 Feature 只有在其所有“范围内 + 必需”的 Feature Items 都达到对应完成标准后，才能进入“已迁移”。
7. 不迁移、延后、复用目标能力等不产生新代码的能力也保留在清单中，并记录决策与依据。
8. 完成一个功能开发或验证动作后，同时更新：Feature Item → Feature 汇总 → Module 汇总 → 当前执行计划；长周期任务再同步 `00-迁移状态总览.md`。
9. 不允许使用一个模糊的“完成”状态同时代表范围、开发、验证和阻塞；这些维度必须分开记录。

## 状态维度

### 范围状态

```text
范围内 / 延后 / 范围外
```

- `范围内`：本次迁移需要处理；
- `延后`：明确延后，不计入当前 Feature 完成 Gate；
- `范围外`：明确不属于本次迁移。

### 实施状态

```text
未开始 → 实施中 → 已实施
```

- `未开始`：尚未开始开发；
- `实施中`：正在修改目标代码；
- `已实施`：当前 Item 的代码实现已完成，但不代表验证通过。

### 验证状态

```text
未验证 → 验证中 → 通过 / 失败
```

并允许 `不适用`。

- `未验证`：尚未执行要求的验证；
- `验证中`：正在验证；
- `通过`：要求的验证已通过；
- `失败`：验证失败，必须处理或形成明确 Decision；
- `不适用`：该 Item 不需要独立验证，并记录原因。

### 阻塞状态

```text
未阻塞 / 已阻塞
```

`已阻塞` 必须同时记录阻塞原因和解除条件。阻塞是独立维度，不覆盖实施或验证状态。

### 是否必需

```text
是 / 否
```

只有“范围内 + 必需=是”的 Item 才是 Feature“已迁移”的强制完成项。“必需=否”仍应记录状态，但不会单独阻塞 Feature Done Gate。

## Feature 生命周期

```text
已发现 → 已设计 → 实施中 → 验证中 → 已迁移 → 已清理
```

Feature 生命周期应尽量由 Feature Items 的真实状态推导：

- `已发现`：功能已识别，但目标行为或 Items 尚不完整；
- `已设计`：必需 Items、Desired Target Behavior、Target Mapping 和验证方式已明确；
- `实施中`：至少一个必需 Item 为“实施中”，或仍有必需 Item 未实施；
- `验证中`：所有必需 Items 已“已实施”，但仍有要求验证的 Item 未“通过/不适用”；
- `已迁移`：所有“范围内 + 必需=是”Items 都“已实施”，且要求的验证均“通过/不适用”，并满足 Feature Done Gate；
- `已清理`：目标能力完成且旧实现、入口和临时结构已安全退出。

不要手工把 Feature 标成“已迁移”来绕过未完成 Item。

Feature Item 应覆盖实际会影响功能完整性的内容。前端常见拆法包括：

- 主要展示区域；
- 核心用户操作；
- Data Query / Mutation；
- Loading / Empty / Error / Success；
- 权限与 Disabled；
- 表单校验与错误恢复；
- Route / Deep Link / Back-forward；
- Modal / Drawer / Toast；
- 响应式与关键视觉状态；
- Accessibility；
- 埋点 / Analytics；
- 必需的集成或副作用。

不要为了“清单细”把每个 div、函数、变量都拆成 Item。Feature Item 应对应可以判断“是否实现、是否验证”的产品或工程行为。

#### Feature 完成 Gate

- [ ] 所有必需 Feature Items 已识别
- [ ] 所有“范围内 + 必需=是”Items 的实施状态均为“已实施”
- [ ] 所有需要验证的必需 Items 的验证状态均为“通过 / 不适用”
- [ ] 不存在“阻塞状态=已阻塞”的必需 Item
- [ ] Business Rule / Invariant 已验证
- [ ] Permission / Data Contract / Error Path 已覆盖
- [ ] APPROVED_CHANGE 已记录且验证的是目标行为
- [ ] 不存在被 Slice“已完成”掩盖的未完成 Item
- [ ] Feature 生命周期状态已按 Item 状态重新计算

## 开发时同步更新纪律

开发不是“先写代码，最后补清单”。每次实际工作按以下循环：

```text
选择 Slice / Feature Items
→ 再确认范围状态 / 是否必需
→ 开始开发：实施状态 = 实施中
→ 代码主体完成：实施状态 = 已实施
→ 开始验证：验证状态 = 验证中
→ 验证结束：验证状态 = 通过 / 失败 / 不适用
→ 如有阻塞：阻塞状态 = 已阻塞 + 原因 + 解除条件
→ 重新计算 Feature 生命周期
→ 更新 Module 汇总计数
→ 更新 Slice Queue
→ 长周期任务同步 00-迁移状态总览
→ 选择下一批 Feature Items
```

如果开发中发现新的必要子功能：

1. 立即加入对应 Feature 的 Item 清单；
2. 判断范围状态和是否必需；
3. 初始化实施状态、验证状态、阻塞状态；
4. 判断是否影响当前 Slice 和 Definition of Done；
5. 不得因为最初清单漏写而静默忽略。

如果实际代码状态与本清单冲突，以已确认 Decision、真实代码/Git/Runtime/Test 为依据，先 Reconcile 清单再继续开发。
