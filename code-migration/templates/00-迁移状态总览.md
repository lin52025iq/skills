规则：

- `必须询问`：现有证据不足，且答案会实质改变产品行为、关键业务规则、权限/数据语义、范围取舍或不可安全推断的不可逆方向；
- `可推断`：目标仓库已有稳定惯例、高等级证据或低风险默认值可安全推断；

- 普通命名、目录、组件选择、已有成熟工程范例不默认询问用户；
- 可以多轮澄清，每轮优先最阻塞当前 Slice 的少量问题；
- 用户回答后同步相关 Feature、Decision 和 Ready Gate；
- 新对话禁止重复询问已有明确答案的问题。

## 事实源优先级

冲突时按以下顺序核对：

1. 用户最近一次明确且仍有效的迁移意图与开发约束；
2. 仍生效的用户规则和已确认 Decision / 目标产品契约；
3. 当前真实代码、Git、Runtime 和测试结果；
4. 模块功能点清单、详细功能清单和执行计划；
5. 本状态总览。

不要拿过期的状态总览覆盖真实代码、用户规则或已确认 Decision。高优先级来源之间冲突时进入 Reconcile / Clarification。

## 新对话恢复步骤

1. 先读取本文件，不要直接重新扫描所有源项目；
2. 恢复总体目标、Desired Target Behavior、当前 Slice、Decision、Invariant 和已回答问题；
3. 读取 `06-迁移约束与开发规则.md`，恢复所有“生效中”规则，并筛选当前 Module / Feature / Slice 相关约束；
4. 读取 `02-迁移模块功能点清单.md`，确认本次涉及哪些模块、各 Feature 当前生命周期状态以及哪些已经完成；
5. 根据索引读取当前模块的详细功能文档与执行计划；
6. 检查 Git branch、最近相关 commit、working tree 和当前 Slice 实际代码；
7. 若状态一致且规则检查通过，从下一推荐动作续接；
8. 若不一致，只对当前相关范围 Reconcile，并更新功能点台账和状态总览后再写新代码；
9. 不重复开发“已迁移 / 已清理”项，不重复询问已有答案，也不得忽略已有“生效中”规则。

更详细的交接、Reconcile、版本控制、敏感信息和多 Agent 协作规则由 `$code-migration` Skill 的“迁移状态与跨会话协作”规范提供；运行时文档不依赖 Skill 安装目录的相对路径。
