## 待澄清问题

不清晰的问题先分类，再决定是否询问用户：

| ID | 问题 | 类型 | 影响范围 | 状态 | 用户回答/结论 |
|---|---|---|---|---|---|
| Q-001 |  | `MUST_ASK / CAN_INFER / CAN_DEFER` |  | `OPEN / ANSWERED / DEFERRED` |  |

规则：

- `MUST_ASK`：答案会改变当前 Slice 的产品行为、业务规则、范围、数据语义、权限、目标架构或不可逆实现方向；当前 Slice 在回答前通常保持 `BLOCKED`。
- `CAN_INFER`：可以依据目标项目惯例、高等级证据或明确默认值安全推断；必须记录推断和证据，必要时告知用户。
- `CAN_DEFER`：不影响当前 Slice，可以进入 Deferred，之后再确认。
- 可以进行多轮澄清。每轮优先询问最阻塞当前迁移的少量问题，用户回答后立即更新本表、相关 Decision/功能清单和 Ready Gate，再判断是否需要下一轮。
- 不重复询问已经有明确答案的问题；新对话开始时先读取本表恢复已问问题和用户结论。

## 新对话恢复步骤

新的 Agent / 新对话开始继续迁移时：

1. 先读取本文件，不要直接重新扫描所有源项目；
2. 检查 `State Freshness`、Git Branch、Last Related Commit 和 Working Tree；
3. 读取 `01-迁移任务上下文.md`，确认总体目标、范围和目标架构没有变化；
4. 检查“待澄清问题”，恢复哪些已经回答、哪些仍然阻塞，禁止重复询问已有答案；
5. 根据 `Current Module / Region` 读取对应 `modules/<module>/`；
6. 读取当前 Slice 相关的功能清单、执行计划和 Decision；
7. 核对目标仓库当前 Git 状态、最近相关提交和当前 Slice 代码，确认本文件没有落后于真实实现；
8. 用一句话复述 Overall Goal、Current Slice、Done 条件、Blocked/Unknown、已确认用户决策和下一步；
9. 若状态一致，按 `Recommended Next Action` 续接；
10. 若不一致，先执行 Reconcile，不要直接写新代码。
