# 08 验证切流与遗留清理

## 目标

证明迁移后的能力正确，并让旧实现能够安全退出。新代码可运行不代表迁移完成。

## 验证维度

按风险组合：

- 业务主流程与 Invariant；
- Loading / Empty / Error / Success；
- 权限、Feature Flag、Deep Link；
- API、数据、枚举、时间、金额和错误契约；
- unit / component / integration / E2E；
- 视觉、响应式、键盘、focus、Accessibility；
- SSR/hydration、console、network、runtime；
- 性能、bundle、SEO、安全、Analytics 和监控。

无法运行源系统时允许使用降级证据，但必须标记置信度，不能声称已证明完整等价。

## 差异分类

发现差异时分类：

- `MUST_FIX`
- `APPROVED_CHANGE`
- `ENVIRONMENT_NOISE`
- `UNKNOWN`

不要通过放宽截图阈值、跳过测试或删除断言把回归变成“通过”。

## 状态

建议使用：

```text
DISCOVERED → DESIGNED → MIGRATED → ELIMINATED
```

`MIGRATED`：目标实现已完成并通过当前 Gate。

`ELIMINATED`：流量/入口已切换，旧 Route、旧实现、Adapter、Feature Flag、重复依赖、临时数据路径和相关测试/文档已经按计划清理。

## Cutover

高风险迁移应明确：

- 切流单位和时间；
- cohort / feature flag / route switch；
- 观测指标；
- 回滚动作；
- 回滚所需数据兼容性；
- 负责人和判断条件。

## Elimination Gate

删除旧实现前确认：

- 新入口稳定；
- 没有仍在使用的调用方；
- 回滚窗口要求已满足；
- 临时 Adapter/Flag 的删除条件已达成；
- 旧依赖和资源可安全移除；
- 文档、测试和监控已指向目标实现。

迁移报告应区分“已迁移”和“已消除遗留”，不要把二者混为一谈。
