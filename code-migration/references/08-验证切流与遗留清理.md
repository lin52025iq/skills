# 08 验证切流与遗留清理

## 目标

证明迁移后的目标能力正确，并让旧实现能够安全退出。验证对象是 **Desired Target Behavior**，不是默认要求新系统逐项复刻旧系统。

## 验证基准

先根据迁移决策确定“什么叫正确”：

- `KEEP`：关键旧能力、Business Rule 和 Invariant 未丢失；
- `ADAPT`：保留部分旧语义，同时验证批准后的目标调整；
- `MERGE`：验证统一后的目标语义，不要求同时保留多个来源的冲突行为；
- `REPLACE / NEW`：验证新的目标契约；
- `REMOVE`：验证旧入口/调用方被安全移除且没有误伤需要保留的能力；
- `REUSE_TARGET`：验证目标已有能力满足当前 Feature 契约。

已确认的产品变化应标为 `APPROVED_CHANGE`，不要把它当成回归修回旧行为。

## 验证维度

按风险组合：

- 业务主流程与 Invariant；
- Loading / Empty / Error / Success；
- 权限、Feature Flag、Deep Link；
- API、数据、枚举、时间、金额和错误契约；
- unit / component / integration / E2E；
- 视觉、响应式、键盘、focus、Accessibility；
- SSR/hydration、console、network、runtime；
- 性能、bundle、SEO、安全、Analytics 和监控。

无法运行源系统时允许使用降级证据，但只能降低对“旧行为理解”的置信度；如果目标行为已经由明确产品契约定义，仍可据此验证目标实现。

## 差异分类

发现差异时分类：

- `MUST_FIX`：偏离 Desired Target Behavior；
- `APPROVED_CHANGE`：已明确接受的目标变化；
- `ENVIRONMENT_NOISE`：与迁移语义无关的环境差异；
- `UNKNOWN`：尚不能判断是否正确。

不要通过放宽截图阈值、跳过测试或删除断言把真实回归变成“通过”。

## 生命周期状态

建议使用：

```text
DISCOVERED → DESIGNED → IMPLEMENTING → VERIFYING → MIGRATED → ELIMINATED
```

- `IMPLEMENTING`：正在开发，不能视为完成；
- `VERIFYING`：主要实现已完成，但验证 Gate 尚未满足；
- `MIGRATED`：目标实现已完成，并已证明满足当前 Desired Target Behavior；
- `ELIMINATED`：流量/入口已切换，旧 Route、旧实现、Adapter、Feature Flag、重复依赖、临时数据路径和相关测试/文档已经按计划清理。

`BLOCKED` 是附加状态，不替代生命周期。

## Cutover

高风险迁移应明确：

- 切流单位和时间；
- cohort / feature flag / route switch；
- 观测指标；
- 回滚动作；
- 回滚所需数据兼容性；
- 负责人和判断条件。

## Elimination Gate

删除旧实现前确认：

- 新入口满足目标行为并稳定；
- 没有仍在使用的调用方；
- 回滚窗口要求已满足；
- 临时 Adapter/Flag 的删除条件已达成；
- 旧依赖和资源可安全移除；
- 文档、测试和监控已指向目标实现。

迁移报告应区分 `VERIFYING / MIGRATED / ELIMINATED`，不要把“代码基本写完”混同为迁移完成。
