# 03 多项目融合与冲突决策

## 目标

多个源项目迁入同一目标时，先统一业务语义，再设计目标实现；不要把 A/B/C 三套实现分别搬过去。

## Canonical Feature Model

```text
Source A ─┐
Source B ─┼→ Canonical Feature Model → Target
Source C ─┘
```

对相似功能建立统一 Feature ID、领域概念和目标语义。源命名不同不代表业务不同；同名也不代表语义相同。

## 冲突类型

至少检查：

- Naming Conflict
- Data Model Conflict
- Business Rule Conflict
- Lifecycle Conflict
- Permission Conflict
- UX Conflict
- Integration Conflict
- Architecture Conflict

## 决策优先级

1. 用户明确迁移意图；
2. 目标产品/业务要求；
3. 目标项目稳定架构与契约；
4. C3/C2 源行为证据；
5. 静态代码与历史；
6. 推断。

仍无法判断时保持 `UNKNOWN`，不要随机选择“代码更多”或“实现更复杂”的来源。

## 目标决策

使用 `KEEP / ADAPT / MERGE / SPLIT / REMOVE / REPLACE / REUSE_TARGET / NEW / DEFER / UNKNOWN`。

多源重复能力默认先考虑 `MERGE` 或 `REUSE_TARGET`，避免在目标仓库形成第二套相似能力。

## 何时需要用户决策

以下情况应显式记录并在必要时请求确认：

- 两个来源存在互斥业务规则；
- 删除或恢复可能影响真实用户的能力；
- 合并会改变权限、数据含义或关键 UX；
- 目标项目没有足够证据决定唯一实现。

## 输出

使用 `../templates/03-功能融合映射.md` 维护 Source → Canonical → Target 映射；重大冲突写入 `../templates/04-迁移决策记录.md`。
