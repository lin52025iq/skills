# 03 多项目融合与冲突决策

## 目标

多个源项目迁入同一目标时，先统一业务语义，再确定目标系统真正需要的能力；不要把 A/B/C 三套实现分别搬过去，也不要把 Canonical Model 误当成必须保留全部旧行为的合集。

## Canonical Feature Model

```text
Source A ─┐
Source B ─┼→ Canonical Feature / Domain Model
Source C ─┘
                  ↓
         Desired Target Behavior
```

Canonical Model 用来消除命名和实现差异、看清多个来源之间的业务关系；最终目标行为仍由用户意图、目标产品要求和必须保留的 Invariant 决定。

对相似功能建立统一 Feature ID、领域概念和语义。源命名不同不代表业务不同；同名也不代表语义相同。

## 冲突类型

至少检查：

- Naming Conflict
- Data Model Conflict
- Business Rule Conflict
- Lifecycle Conflict
- Permission Conflict
- UX Conflict
- Integration Conflict
- Architecture Conflict

其中 Architecture Conflict 通常优先通过目标仓库既有模式解决；只有会造成重大产品/长期架构后果且目标证据不足时才需要用户决策。

## 决策优先级

1. 用户最近一次明确迁移意图；
2. 目标产品/业务要求；
3. 必须保留且有证据的 Invariant；
4. 目标项目稳定架构与契约；
5. C3/C2 源行为证据；
6. C1 静态代码与历史；
7. 推断。

这个顺序表示“如何形成目标行为”，不是说低优先级证据可以被忽略。例如用户要求改变旧流程时，仍需理解原流程的 Invariant 和影响，再实施变化。

仍无法判断时保持 `UNKNOWN`，不要随机选择“代码更多”“更复杂”或“看起来更新”的来源。

## 目标决策

使用 `KEEP / ADAPT / MERGE / SPLIT / REMOVE / REPLACE / REUSE_TARGET / NEW / DEFER / UNKNOWN`。

多源重复能力默认先考虑 `MERGE` 或 `REUSE_TARGET`，但“重复”必须基于语义判断，不只看页面名称或接口名。

## 何时需要用户决策

只有当现有证据不足，并且不同答案会实质改变以下内容时，才优先进入 `MUST_ASK`：

- 高风险或不可逆业务规则；
- 权限、资金、数据含义或状态生命周期；
- 明确的功能范围取舍；
- 用户可观察产品行为；
- 无法从目标仓库稳定惯例推断的重大长期架构方向。

普通命名、目录、组件选择和目标仓库已有成熟模式的技术实现不应默认打断用户。

## 输出

使用 `../templates/03-功能融合映射.md` 维护 Source → Canonical → Desired Target 映射；重大冲突写入 `../templates/04-迁移决策记录.md`。
