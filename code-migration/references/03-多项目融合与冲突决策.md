# 03 多项目融合与冲突决策

## 目标

多个源项目迁入同一目标时，先统一业务语义，再确定目标系统真正需要的能力；不要把 A/B/C 三套实现分别搬过去，也不要把统一模型误当成必须保留全部旧行为的合集。

## 统一功能模型

```text
来源 A ─┐
来源 B ─┼→ 统一功能 / 领域模型
来源 C ─┘
                  ↓
              目标期望行为
```

统一模型用于消除命名和实现差异；最终目标行为仍由用户意图、目标产品要求和必须保持的 Invariant 决定。

## 冲突类型

至少检查：

- 命名冲突；
- 数据模型冲突；
- 业务规则冲突；
- 生命周期冲突；
- 权限冲突；
- 交互冲突；
- 集成冲突；
- 架构冲突。

架构冲突通常优先通过目标仓库既有模式解决；只有会造成重大产品或长期架构后果且证据不足时才需要用户决策。

## 决策优先级

1. 用户最近一次明确迁移意图；
2. 目标产品 / 业务要求；
3. 必须保持且有证据的 Invariant；
4. 目标项目稳定架构与契约；
5. C3/C2 源行为证据；
6. C1 静态代码与历史；
7. 推断。

仍无法判断时保持 **“未知”**，不要随机选择代码更多、更复杂或看起来更新的来源。

## 迁移决策

统一使用：

```text
保留 / 适配 / 合并 / 拆分 / 移除
替换 / 复用目标 / 新增 / 延后 / 未知
```

多源重复能力默认先考虑 **“合并”** 或 **“复用目标”**，但重复必须基于语义判断。

## 何时需要用户决策

只有证据不足，并且不同答案会实质改变以下内容时，才优先进入 **“必须询问”**：

- 高风险或不可逆业务规则；
- 权限、资金、数据含义或状态生命周期；
- 明确功能范围取舍；
- 用户可观察产品行为；
- 无法从目标仓库稳定惯例推断的重大长期架构方向。

普通命名、目录、组件选择和已有成熟模式的技术实现不应默认打断用户。

## 输出

使用 `../templates/03-功能融合映射.md` 维护 **来源 → 统一模型 → 目标期望行为** 映射；重大冲突写入 `../templates/04-迁移决策记录.md`。
