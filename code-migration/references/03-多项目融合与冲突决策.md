# 03 多项目融合与冲突决策

## 目标

多个 Source 迁入同一 Target 时，先统一业务语义，再确定目标系统真正需要的能力；不要把 A/B/C 三套实现分别搬过去，也不要把统一模型误当成必须保留全部旧行为的合集。

## 统一功能模型

```text
来源 A ─┐
来源 B ─┼→ 统一功能 / 领域模型
来源 C ─┘
                  ↓
              Target Behavior
```

统一模型用于消除命名和实现差异；最终 Target Behavior 仍由用户意图、目标产品要求和必须保持的 Invariant 决定。

## 冲突类型

至少检查：命名、数据模型、业务规则、生命周期、权限、交互、集成和架构冲突。

架构冲突通常优先通过 Target 既有模式解决；只有会造成重大产品或长期架构后果且证据不足时才需要用户决策。

## 决策优先级

1. 用户最新明确迁移意图；
2. Target 产品 / 业务要求；
3. 必须保持且有证据的 Invariant；
4. Target 稳定架构与契约；
5. C3/C2 Source Behavior；
6. C1 静态代码与历史；
7. 推断。

仍无法判断时保持 `未知`。

## 迁移决策

```text
保留 / 适配 / 合并 / 拆分 / 移除
替换 / 复用目标 / 新增 / 延后 / 未知
```

多源重复能力优先考虑 `合并` 或 `复用目标`，但重复必须基于语义判断。

## 何时需要用户决策

只有证据不足且不同答案会实质改变高风险业务规则、权限/资金/数据含义、状态生命周期、功能范围、用户可观察行为或重大长期架构方向时，才进入 `必须询问`。

## 输出

使用 `../templates/07-功能融合映射.md` 维护 **来源 → 统一模型 → Target Behavior** 映射；重大冲突或已批准目标变化写入 `../templates/08-迁移决策记录.md`。
