# 05 迁移设计与策略选择

## 目标

把已理解的功能语义映射到目标架构，并选择风险最小、可验证、可退出的迁移策略。

## 策略候选

- **直接重写（Direct Rewrite）**：边界小、依赖清晰、验证充分；
- **绞杀者模式（Strangler）**：旧系统长期存在，按路由 / 功能渐进切流；
- **抽象分支（Branch by Abstraction）**：调用方多、无法直接切换；
- **适配器 / 防腐层**：新旧模型或接口差异明显；
- **并行 / 影子运行**：需要新旧结果对照；
- **增量升级**：框架 / 运行时有连续升级路径；
- **Codemod 辅助**：大量机械变化，但语义仍需单独处理。

不要为了“架构漂亮”引入比迁移问题更复杂的临时系统。

## 目标落点

对每个功能明确：

```text
功能 ID
→ 目标模块 / 区域
→ 路由 / 入口
→ 数据契约
→ 状态所有权
→ 界面 / 设计系统
→ 权限 / 集成
→ 验证方式
```

目标落点从业务能力和目标范例推导，不从源文件树推导。

## 临时架构

新旧共存需要 Adapter、Bridge、Flag 或双路由时，至少记录：

- **目的**；
- **负责人**；
- **引入时间 / 提交**；
- **删除条件**；
- **删除依赖**；
- **回滚路径**。

**临时结构没有退出条件，则设计未完成。**

## 依赖与顺序

先处理能解除多个功能阻塞的最小基础能力，再按功能切片推进。避免先造完整“新平台层”再等业务接入。

## 决策检查

方案必须能回答：

- 为什么选此策略；
- 最大风险是什么；
- 如何验证；
- 如何回滚；
- 旧实现何时可以删除。
