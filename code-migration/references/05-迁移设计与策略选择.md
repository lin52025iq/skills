# 05 迁移设计与策略选择

## 目标

把已理解的功能语义映射到目标架构，并选择风险最小、可验证、可退出的迁移策略。

## 策略候选

- `Direct Rewrite`：边界小、依赖清晰、验证充分；
- `Strangler`：旧系统长期存在，按 Route/Feature 渐进切流；
- `Branch by Abstraction`：调用方多、无法直接路由切换；
- `Adapter / Anti-Corruption Layer`：新旧模型或接口差异明显；
- `Parallel / Shadow`：需要新旧结果对照；
- `Incremental Upgrade`：框架/运行时有连续升级路径；
- `Codemod-assisted`：大量机械变化但语义仍需单独处理。

不要为了“架构漂亮”引入比迁移问题更复杂的临时系统。

## Target Mapping

对每个 Feature 明确：

```text
Feature ID
→ Target Module / Region
→ Route / Entry
→ Data Contract
→ State Ownership
→ UI / Design System
→ Permission / Integration
→ Validation
```

目标映射从业务能力和目标范例推导，不从源文件树推导。

## Temporary Architecture

新旧共存需要 Adapter、Bridge、Flag 或双路由时，记录：

- Purpose
- Owner
- Introduced At
- Removal Condition
- Removal Dependency
- Rollback Path

临时结构没有退出条件则设计未完成。

## 依赖与顺序

先处理能解除多个 Feature 阻塞的最小基础能力，再按功能切片推进。避免先造完整“新平台层”再等业务接入。

## 决策检查

方案必须能回答：

- 为什么选此策略；
- 最大风险是什么；
- 如何验证；
- 如何回滚；
- 旧实现何时可以删除。
