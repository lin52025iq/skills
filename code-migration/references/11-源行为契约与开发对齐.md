# 11 源行为契约与开发对齐

## 目标

减少“文档理解正确，但开发过程中细节逐渐偏离源项目”的问题，同时明确源行为、功能实施、交互语义和页面结构之间的职责边界。

核心链路：

```text
源证据
→ 功能发现覆盖
→ 源行为
→ 目标决策
→ 功能子项
→ 实施
→ 行为 / 交互 / 结构验证证据
```

## 什么是源行为

源行为是用户、外部系统或业务流程可观察到的行为，不是文件、函数或框架机制。

常见维度包括：入口/前置条件、加载/空/错误/成功状态、字段显隐与格式、权限、校验、导航、状态流转、数据契约、自动副作用和集成。

## 源行为之前先确认“有没有漏”和“是不是事实”

中/高风险功能不应直接从一个粗粒度 Feature 描述进入 Source Behavior。先检查：

1. **功能发现覆盖**：入口、条件分支、权限、Flag、API 反向调用、自动行为、测试、异常恢复是否已经检查；
2. **来源真实性**：正式功能 / 子项是否有源证据、用户明确新增、目标产品要求或目标强制约束。

`推断候选` 和 `未知` 不得静默升级成范围内必需功能。

## 行为决策

```text
保持 / 目标修改 / 不迁移 / 未知
```

- `保持`：目标保留该可观察语义，实现方式可以目标原生；
- `目标修改`：必须记录批准后的目标期望行为；
- `不迁移`：记录依据；
- `未知`：影响当前方向时进入“必须询问”或阻塞。

## 与功能子项的权威边界

- `02-迁移模块功能点清单.md`：功能子项 **来源、处理方式、实施状态、当前状态** 的权威源；
- `07-源行为与目标对齐清单.md`：源行为 **目标决策、覆盖、目标实际表现、验证状态、验证证据** 的权威源；
- `08-页面结构与交互对齐清单.md`：前端页面 **结构、交互、响应式、用户新 UX / 布局方案及其验证** 的权威源。

**不要在 `07` 中复制功能子项实施状态，也不要用 `07` 代替复杂页面的结构 / 交互契约。**

## 源行为覆盖检查门槛

中/高风险功能实施前检查：

- [ ] 功能发现覆盖达到当前证据下可接受水平；
- [ ] 正式功能 / 子项有合法来源；
- [ ] 关键源行为已盘点且有稳定 ID；
- [ ] 每条关键行为已有“保持 / 目标修改 / 不迁移 / 未知”决策；
- [ ] 所有“保持”行为至少映射一个范围内功能子项；
- [ ] 所有“目标修改”有明确目标期望行为；
- [ ] 权限、状态、错误、导航、数据契约、自动副作用等关键维度已覆盖；
- [ ] 不存在会改变当前实现方向的关键“未知”。

## 与功能子项的映射

例如：

```text
F-ORDER-I07
功能子项：返回订单列表后保留筛选条件
来源类型：源系统证据
处理方式：修改现有
关联源行为：SB-ORDER-014
```

规则：

- “保持”行为没有功能子项 → 迁移遗漏；
- 功能子项没有源行为，也不是明确新增 → 检查来源依据；
- 一个源行为可映射多个强关联子项；
- 一个功能子项可覆盖多个紧密相关行为。

## 交互语义不是普通 Source Behavior 的一句话备注

以下情况应进入 `08` 的交互语义清单，而不是只写“点击后提交”：

- Modal / Drawer / Page / Popover 形态本身影响体验；
- 有复杂 Loading / Optimistic / Disabled；
- 重复提交、并发或取消有语义；
- 失败后需要保留输入 / 回滚 / Retry；
- URL / Back / Focus / Keyboard / Scroll 有明确行为；
- 用户提出新的交互迁移方案。

交互可以“目标修改”而仍保留业务能力。例如从“跳转详情页”重构为“打开右侧 Drawer”。验证应面向用户批准的新交互，不应修回 Source 旧交互。

## 页面结构不是普通 Source Behavior

以下内容进入 `08`：

- 页面区域树；
- 区域父子关系；
- 单栏 / 双栏 / Grid / Overlay；
- 关键宽度 / 比例 / 对齐；
- Scroll Owner、Sticky、Fixed；
- Modal / Drawer / Overlay；
- 响应式结构；
- 布局不变量；
- 用户新的布局方案和目标区域树。

高风险页面源系统可运行时，优先使用 C3 运行页面和多 Viewport 证据，不只依赖 DOM/CSS 猜布局。

## 开发中对齐

开发过程以功能子项为实施单位：

```text
02：确认来源 / 功能子项实施
→ 满足处理要求
→ 07：源行为验证
→ 08：复杂前端交互 / 页面结构验证
→ 汇总功能完成状态
```

不要等整个页面全部做完后才一次性对照 Source。

## 新发现能力

开发中发现新的功能 / 行为时：

1. 记录候选；
2. 判断来源类型；
3. 检查它是否真的属于范围内；
4. 若纳入，补功能子项并递归检查其条件、权限、异常和副作用；
5. 重新评估功能发现覆盖和风险级别；
6. 必要时更新输入基线。

**不能因为实现过程中“顺手发现一个好点子”就直接新增产品能力。**

## 验证失败

当 `验证状态=失败`，源行为当前状态为 `验证失败`；只有同时存在真实流程阻塞时才覆盖为 `已阻塞`。

## 工作流输入基线

中/高风险长任务或多 Agent 工作流应记录源行为 / 目标期望行为基线。若功能发现、用户新方案或目标产品方案发生会改变当前实现的变化，受影响工作流必须先阻塞、更新基线再继续。

## 验证负责人职责

验证负责人至少能回答：

- 有没有无来源依据的功能被误加入；
- 有没有明显未检查的隐藏入口 / 条件能力 / 副作用；
- 保持行为是否真的存在于目标；
- 目标修改是否符合批准后的行为；
- 复杂交互是否按目标交互语义执行；
- 页面结构是否按目标结构和用户新方案实现；
- 是否存在未覆盖的关键源行为。

## 运行时产物

```text
低风险：02 + 最小必要验证
中风险：02 + 关键 07；前端复杂交互/布局按需 08
高风险：02 + 完整 07 + 前端页面 08 + 独立验证
```
