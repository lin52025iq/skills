# 11 源行为契约与开发对齐

## 目标

减少“文档理解正确，但开发过程中细节逐渐偏离 Source”的问题。

核心链路：

```text
Source Evidence
→ Source Behavior
→ Target Decision
→ Feature Item
→ Implementation
→ Validation Evidence
```

任何关键“保持”行为如果在链路中断开，都可能成为迁移遗漏。

## 什么是 Source Behavior

Source Behavior 是用户、外部系统或业务流程可观察到的行为，不是文件、函数或框架机制。

常见维度：

- Entry / Precondition；
- Loading / Empty / Error / Success；
- 字段显示、隐藏、格式化；
- Permission / Disabled / Hidden；
- 表单校验和错误恢复；
- Navigation / Deep Link / Back-forward；
- 状态流转和副作用；
- API / Data Contract；
- Modal / Drawer / Toast；
- Responsive / Accessibility；
- Analytics / Integration。

例如：

```text
SB-ORDER-014
行为：从订单详情返回列表后保留筛选条件
证据：C3 Runtime
```

比“订单列表支持筛选”更适合直接约束迁移开发。

## 行为决策

每条关键 Source Behavior 使用：

```text
保持 / 目标修改 / 不迁移 / 未知
```

### 保持

目标必须保留该可观察语义，但实现方式可以 Target-native。

### 目标修改

用户或目标产品明确允许/要求改变。必须记录批准后的 Desired Target Behavior。

### 不迁移

目标明确不需要。应记录依据，不能因为暂时没实现就默认为不迁移。

### 未知

当前证据不足。会影响当前方向时进入“必须询问”或阻塞。

## Source Coverage Gate

Feature 从“已设计”进入“实施中”前，对当前范围检查：

- [ ] 关键 Source Behavior 已盘点；
- [ ] 每条关键行为有稳定 ID；
- [ ] 每条关键行为已有“保持 / 目标修改 / 不迁移 / 未知”决策；
- [ ] 所有“保持”行为至少映射一个范围内 Feature Item；
- [ ] 所有“目标修改”有明确 Desired Target Behavior；
- [ ] 所有“不迁移”有明确依据；
- [ ] 权限、状态、错误、Loading/Empty、Navigation、数据契约等关键维度已覆盖；
- [ ] 不存在会改变当前实现方向的关键“未知”。

Source Coverage Gate 不是要求穷举所有 UI 像素，而是防止用户可观察细节在实现前丢失。

## 与 Feature Item 的映射

Feature Item 应能够引用：

```text
Source Behavior IDs
```

例如：

```text
F-ORDER-I07
功能项：返回订单列表后保留筛选条件
关联源行为：SB-ORDER-014
目标决策：保持
```

规则：

- “保持”行为没有 Feature Item → 迁移遗漏；
- Feature Item 没有 Source Behavior 也不是 `NEW` / 明确目标新增 → 检查是否缺少来源依据；
- 一个 Source Behavior 可以映射多个强关联 Item；
- 一个 Feature Item 也可以覆盖多个紧密相关 Behavior。

不要为了形式强行一对一。

## 开发中对齐

不要等整个 Feature 完成后再一次性对照 Source。

建议循环：

```text
选择 Feature Item
→ 确认关联 Source Behavior / Target Behavior
→ 实施
→ 立即执行 Item 级验证
→ 写入验证证据
→ 再进入下一 Item
```

如果实现过程中发现新的 Source 细节：

1. 新增 Source Behavior；
2. 判断行为决策；
3. 更新 Feature Item；
4. 判断是否影响当前 Workstream Input Baseline；
5. 影响时暂停相关 Item 并重新检查开始条件。

## Presentation Contract

前端复杂页面可以为重要视觉/结构行为补充 Presentation Contract，例如：

- 信息层级；
- 区域顺序；
- 主次操作；
- 显示/隐藏/Disabled；
- Page / Modal / Drawer 形态；
- 响应式结构；
- 关键视觉状态。

Presentation Contract 用于保护用户可感知结构，不要求像素级复制。目标 Design System、spacing、字体等可以按 Target-native 方式实现，除非用户明确要求视觉等价。

## 行为差异分类

开发或验证发现 Source/Target 差异时，使用：

```text
必须修复 / 已批准变化 / Target-native 差异 / 环境噪声 / 未知
```

不要把已批准变化修回 Source，也不要把真实行为回归误标成 Target-native 差异。

## Workstream Input Baseline

实施 Workstream 开始时，应记录其依赖的 Source Behavior / Desired Target Behavior 基线。

如果 Analyst 在 Workstream 运行中更新了关键行为：

```text
变化不影响当前 Items → 记录后继续
变化影响当前 Items → 已阻塞 → 更新基线 → 重新检查
```

这用于避免不同 Agent 基于不同版本的“正确文档”同时工作。

## 验证者职责

Verifier 应从 Source Behavior / Target Decision 出发独立验证，不以 Implementer 的实现说明作为唯一依据。

至少能回答：

- 保持行为是否真的存在于 Target；
- 目标修改是否符合批准后的行为；
- 不迁移行为是否确实没有被错误恢复；
- Feature Item 状态是否与实际代码/运行一致；
- 是否存在清单未覆盖的关键 Source Behavior。

## 运行时产物

复杂 Feature / 模块按需使用：

```text
.code-migration/07-源行为与目标对齐清单.md
```

小 Feature 可把 Source Behavior 直接写入模块功能语义文档，不机械增加文档。
