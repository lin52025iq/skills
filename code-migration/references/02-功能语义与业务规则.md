# 02 功能语义与业务规则

## 目标

把 Source 证据转换成与技术栈无关的业务语义，同时严格区分：

```text
源系统事实
目标需求
设计建议
```

本 Reference 只解释“如何理解能力”，不承担迁移进度或完成状态。

## 功能语义模型

关键能力至少回答：

```text
角色
入口
前置条件
动作
业务规则
数据
副作用
结果
失败
生命周期
证据
来源类型
```

文件、Hook、Store、组件只是实现证据，不是业务能力本身。

## 来源与事实边界

正式功能 / 原子功能项来源：

```text
源系统证据
用户明确新增
目标产品要求
目标项目强制约束
推断候选
未知
```

`推断候选 / 未知` 不能静默进入必需迁移范围。

以下只属于设计建议，不能单独证明产品需要新增能力：

- 行业惯例；
- Agent 认为体验更好；
- Target 其他页面存在类似功能；
- Target 已有现成组件。

## 业务语义分类

阅读 Source 时按需要识别：

- **领域规则**：业务成立条件；
- **用户可观察行为**：用户能直接感知的结果；
- **交互语义**：触发、中间状态、反馈、恢复和收尾；
- **集成契约**：API、事件、SDK；
- **自动行为 / 副作用**：轮询、缓存失效、事件、Storage、刷新、跳转；
- **历史兼容 / Bug 兼容**：可能仍被依赖；
- **技术债 / 无效代码**：不默认复制；
- **未知**：证据不足。

## Invariant

重点提取技术栈变化后仍必须成立的条件，例如：

- 权限不足不能审批；
- 状态不能非法跳转；
- 金额以服务端最终结果为准；
- 一个实体只能存在一个有效进行中流程。

Invariant 应进入源行为验证或测试。

## 数据契约与副作用

按适用项记录：输入、输出、枚举、分页、时间、金额、错误码、权限字段，以及 Mutation 后的：

- Query / Cache 失效；
- 跨模块刷新；
- Event / Analytics；
- Storage 写入；
- 轮询 / WebSocket 启停；
- 导航和局部状态变化。

## 交互语义边界

业务层只记录 **WHAT**，例如：

```text
返回订单列表后必须保留用户上下文
409 后必须允许用户恢复操作
```

具体用户如何体验该行为，例如分页、滚动、Focus、Drawer、Keyboard、Loading 时序，记录在 `08-页面结构与交互对齐清单.md`。

因此：

```text
07 / 功能语义 = WHAT
08 = HOW USER EXPERIENCES IT + WHERE
```
