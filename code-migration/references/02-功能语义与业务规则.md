# 02 功能语义与业务规则

## 目标

把源代码转换为与技术栈无关的功能语义，恢复用户真正依赖的能力、规则和不可破坏条件。

## 功能模型

每个关键功能至少回答：

```text
角色
入口
前置条件
动作
业务规则
数据
副作用
结果
失败
生命周期
证据
```

不要把文件、Hook、Store 当作功能；它们只是实现证据。

## 逻辑分类

阅读旧代码时，将重要逻辑归类为：

- **领域规则**：核心业务规则；
- **用户可观察行为**：用户能直接感知的行为；
- **集成契约**：API、事件、SDK 等契约；
- **框架机制**：由框架要求产生；
- **基础设施机制**：构建、缓存、环境等机制；
- **历史兼容 / 临时修复**：旧约束下的折中；
- **Bug 兼容行为**：看似 Bug 但可能被依赖；
- **技术债**：可识别但不应默认复制；
- **无效代码**：有证据证明不再使用；
- **未知**：证据不足。

**不要默认复制历史兼容和技术债，也不要在缺少证据时删除可能被依赖的行为。**

## Invariant

重点提取无论技术栈如何变化都必须成立的条件，例如：

- 权限不足不能执行审批；
- 某状态不能跳过中间状态；
- 金额以服务端最终计算结果为准；
- 一个实体只能存在一个有效进行中流程。

Invariant 应优先进入测试或运行验证。

## 生命周期

源能力使用中文标记：

```text
现役 / 条件启用 / 已废弃 / 已移除 / 未知
```

代码存在不是“现役”的充分条件。

## 数据契约

记录输入、输出、枚举、分页、时间、金额、错误码、权限字段和副作用。多项目迁移中这些是最常见的语义冲突来源。

## 输出

复杂模块使用 `../templates/02-功能清单.md`。同一个业务规则只维护在一个功能的权威条目中，其他文档引用功能 ID。
