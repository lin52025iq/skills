# 02 功能语义与业务规则

## 目标

把源代码转换为与技术栈无关的功能语义，恢复用户真正依赖的能力、规则和不可破坏条件。

## 功能模型

每个关键 Feature 至少回答：

```text
Actor
Entry
Precondition
Action
Business Rule
Data
Side Effect
Result
Failure
Lifecycle
Evidence
```

不要把 `OrderPage.tsx`、`useOrderQuery`、`orderStore` 当作 Feature；它们只是实现证据。

## 逻辑分类

阅读旧代码时，将重要逻辑归类为：

- `DOMAIN_RULE`：领域/业务规则；
- `USER_OBSERVED_BEHAVIOR`：用户可观察行为；
- `INTEGRATION_CONTRACT`：API、事件、SDK 等契约；
- `FRAMEWORK_MECHANISM`：框架要求；
- `INFRASTRUCTURE_MECHANISM`：构建、缓存、环境等机制；
- `WORKAROUND`：历史兼容或临时修复；
- `BUG_COMPATIBILITY`：看似 Bug 但可能被依赖的行为；
- `TECH_DEBT`：技术债；
- `DEAD_CODE`：有证据证明不再使用；
- `UNKNOWN`：证据不足。

不要默认复制 `WORKAROUND` / `TECH_DEBT`，也不要在没有证据时删除 `BUG_COMPATIBILITY` / `UNKNOWN`。

## Invariant

重点提取无论技术栈如何变化都必须成立的条件，例如：

- 权限不足不能执行审批；
- 某状态不能跳过中间状态；
- 金额以服务端最终计算结果为准；
- 一个实体只能存在一个有效进行中流程。

Invariant 应优先进入测试或运行验证。

## 生命周期

能力至少标记为：`Active`、`Conditional`、`Deprecated`、`Removed`、`Unknown`。代码存在不是 `Active` 的充分条件。

## 数据契约

记录输入、输出、枚举、分页、时间、金额、错误码、权限字段和副作用。多项目迁移中这些是最常见的语义冲突来源。

## 输出

复杂模块使用 `../templates/02-功能清单.md`。同一个业务规则只维护在一个 Feature 的权威条目中，其他文档引用 Feature ID。
