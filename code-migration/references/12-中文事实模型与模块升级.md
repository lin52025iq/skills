# 中文事实模型与模块升级

本文定义 `code-migration` 工作区中稳定的中文字段、枚举、权威事实边界，以及模块从顶层内联升级为独立目录的规则。

## 1. 原则

1. 状态、枚举和值优先使用中文，避免同一概念出现多套近义表达。
2. 规范只定义字段和值，不另建 JSON/YAML 状态文件；真实迁移事实仍维护在对应 Markdown 权威文件中。
3. 同一详细事实只维护一处。摘要、Checklist 和进度表均为派生视图。
4. 模块目录是承载方式，不是模块身份。模块、功能、原子功能项编号在迁移过程中保持稳定。
5. 小模块允许先在顶层 `03` 内联维护，复杂度上升后再迁入独立模块目录。
6. 公共模块只承载跨业务模块复用、具有业务或用户可观察语义、可独立实施和验证的公共能力。

## 2. 实体层级

```text
模块
└─ 功能
   ├─ 功能组 / 场景组（可选）
   │  ├─ 原子功能项
   │  └─ 原子功能项
   └─ 原子功能项
```

公共模块使用相同的“功能 → 原子功能项”模型，只是由多个业务模块引用。

## 3. 模块规范

建议字段：

```text
模块编号
模块名称
承载方式
风险级别
模块状态
用户目标
用户新方案
权威位置
当前功能
下一安全动作
```

枚举：

```text
承载方式：顶层内联 / 独立模块 / 公共模块
风险级别：低风险 / 中风险 / 高风险
模块状态：未开始 / 进行中 / 验证中 / 已完成 / 已阻塞
```

推荐独立模块目录：

```text
modules/M-001-订单中心/
modules/M-002-用户管理/
```

编号提供稳定身份，中文名称提供可读性。

## 4. 功能规范

建议字段：

```text
功能编号
功能名称
用户目标
目标行为
风险级别
来源类型
来源依据
迁移决策
发现状态
源行为契约
页面结构与交互契约
完成定义
生命周期
```

枚举：

```text
生命周期：已发现 / 已设计 / 实施中 / 验证中 / 已迁移 / 已清理
发现状态：未检查 / 部分通过 / 通过 / 未通过 / 不要求
```

## 5. 原子功能项规范

必需字段优先保持简洁；只有复杂、失败、阻塞或需要审计的项才展开全部字段。

建议字段：

```text
原子功能项编号
名称
当前状态
范围状态
是否必需
来源类型
来源依据
迁移决策
处理方式
实施状态
验证状态
阻塞状态
关联源行为
关联页面体验
关联集成验证
验证方式 / 证据
失败原因 / 下一动作
```

统一枚举：

```text
当前状态：
未开始 / 开发中 / 待验证 / 验证中 / 验证失败 / 已完成 / 已阻塞 / 已延后 / 不适用

范围状态：
范围内 / 范围外 / 待确认

是否必需：
是 / 否

来源类型：
源系统证据 / 用户明确新增 / 目标产品要求 / 目标项目强制约束 / 推断候选 / 未知

迁移决策：
保留 / 修改 / 替换 / 新增 / 删除 / 合并 / 待决定

处理方式：
新增实现 / 修改现有 / 复用已有 / 无需实施 / 删除旧实现

实施状态：
未实施 / 实施中 / 已实施 / 无需实施

验证状态：
未验证 / 验证中 / 通过 / 失败 / 不要求

阻塞状态：
未阻塞 / 已阻塞
```

不要使用“差不多完成”“基本完成”“等待看看”等非规范状态。

## 6. 状态派生

详细字段是事实，当前状态和上层状态是受约束的综合结果。

```text
原子功能项详细事实
→ 原子功能项当前状态
→ 功能生命周期
→ 模块状态
→ Checklist / 进度摘要
```

Checkbox 只能由真实状态派生：

```text
原子功能项当前状态 = 已完成       → [x]
功能生命周期 = 已迁移 / 已清理     → [x]
模块状态 = 已完成                  → [x]
其他                               → [ ]
```

若派生视图和权威事实冲突，先修正权威事实确认无误，再由下向上修正所有派生视图。

## 7. 三种承载方式

### 顶层内联

适合低风险、小体量、没有独立维护价值的模块。

```text
03-迁移模块索引与进度.md
└─ M-008 通知设置
   └─ F-001 邮件通知
      ├─ F-001-I01
      └─ F-001-I02
```

该模块对应章节就是详细权威事实源。

### 独立模块

适合跨会话、多个功能、独立验证或独立工作流的模块。

```text
modules/M-008-通知设置/
├── 00-模块总览.md
├── 01-模块功能点.md
├── 02-功能语义.md          # 按需
├── 03-源行为对齐.md        # 按需
└── 04-页面结构与交互.md    # 按需
```

其中 `01-模块功能点.md` 是详细功能和原子功能项的权威事实源。

### 公共模块

```text
modules/shared/
├── 00-公共模块总览.md
└── 01-公共功能点.md
```

公共功能必须同时满足：

- 被两个或以上业务模块实际依赖，或明确预期作为跨模块能力；
- 有独立业务或用户可观察语义；
- 能独立判断实施和验证。

普通 UI 组件、工具函数、Hook、样式和纯工程基础设施不登记为公共功能点。

## 8. 模块升级规则

模块从顶层内联升级成独立模块时：

```text
承载位置变化
≠ 模块身份变化
≠ 功能重建模
```

必须保持：

```text
模块编号不变
功能编号不变
原子功能项编号不变
已确认的来源和迁移决策不变
历史验证和决策引用仍可追踪
```

推荐步骤：

1. 创建 `modules/M-xxx-模块名称/00-模块总览.md` 和 `01-模块功能点.md`。
2. 原样迁移详细功能、原子功能项和真实状态。
3. 检查所有编号和语义未变化。
4. 更新 `09`、决策、验证证据中的路径引用。
5. 将顶层 `03` 中详细内容删除，只保留模块派生摘要和真实入口链接。
6. 检查不存在两份同时可写的详细事实。

## 9. 升级触发条件

不设置机械的固定数量阈值。以下任一情况成立时优先升级：

- 多个功能需要独立追踪；
- 原子功能项平铺后明显影响顶层可读性；
- 需要跨会话持续推进；
- 需要独立工作流或并行边界；
- 需要模块私有功能语义、源行为或页面结构/交互契约；
- 风险较高，需要独立验证或集成结论；
- 多人或多个 Agent 会持续修改；
- 顶层章节已经明显干扰其他模块浏览。

## 10. 公共功能引用

业务模块只保存依赖关系，不复制公共功能详细状态。例如：

```text
公共功能依赖：
- 公共-PERM-001 权限校验
- 公共-NOTIFY-002 操作结果通知
```

公共功能的实施和验证状态只在 `modules/shared/01-公共功能点.md` 更新。业务模块需要记录的是“该公共依赖是否满足当前功能完成条件”，而不是复制公共功能内部状态表。
