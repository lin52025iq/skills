# 07 自动化与增量实施

## 目标

让自动化服务于迁移，而不是让 Codemod 或批量生成替代语义判断。

## 自动化边界

只有满足以下条件的变化默认适合批量自动化：

- 输入模式稳定；
- 输出形状唯一；
- 不涉及业务规则解释；
- 不改变权限、状态语义和用户可观察行为；
- 有可运行的验证方式。

典型适用：import 重写、API 重命名、确定的语法升级、简单组件 API 迁移。

## 不适合机械转换

遇到以下情况停止批量转换：

- 一个源实现存在多个合理目标实现；
- 状态所有权需要重新设计；
- 业务规则、权限、生命周期或数据枚举变化；
- 旧抽象由框架限制或历史兼容产生；
- 多项目需要合并；
- 用户明确要求调整功能。

## 小批次原则

先在代表性样本执行，并明确：

```text
做什么
为什么
证据
范围
预期变化
验证方式
回滚方式
```

通过后再扩大同类批次。若同一种失败重复出现，先修迁移规则，不要继续生成更多错误代码。

## 增量提交

优先让每个提交对应一个可解释的迁移切片或必要公共基础，避免把格式化、依赖升级、无关重构和多个业务能力混在一个大提交中。

## 技术债处理

- 旧技术债仅因实现机制而存在：不要复制；
- 修复会改变行为：记录迁移决策；
- 与当前切片无关：标记“已延后”；
- 阻塞目标实现：做最小必要修复并说明原因。
