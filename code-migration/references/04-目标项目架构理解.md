# 04 目标项目架构理解

## 目标

在迁移编码前理解目标仓库已经形成的稳定惯例。目标项目决定代码形状，源项目只提供功能语义和约束。

## 优先寻找相似实现

选择 2～5 个维护良好、测试充分、与待迁能力相似的目标模块，研究：

- Router 与页面/模块注册方式；
- Server state、Client state、URL state 的所有权；
- API client、Query/cache、错误和重试；
- Form、Validation、权限与 Feature Flag；
- Design System、Token、布局和响应式；
- Analytics、日志、监控；
- unit/component/integration/E2E；
- 目录、命名、依赖方向、SSR/构建边界。

核心问题：

> 如果这个功能不是迁移而是今天新开发，目标项目原维护者会怎样实现？

## Target Existing Capability

迁移前主动查找目标已有：Auth、Permission、API Client、Table、Form、Modal、Date、Upload、Analytics、Error Boundary、Query、Layout 等能力。

能满足需求时优先 `REUSE_TARGET`，不要为了“保持旧实现”复制第二套基础设施。

## 架构适配

典型映射应基于语义，而非技术名词：

```text
旧 Server State Store → 目标 Query Cache（若语义适合）
旧表单 Store → 目标 Form 方案
旧 UI Wrapper → 目标 Design System
旧 Axios Layer → 目标 API Client
```

不要假设每个旧 abstraction 都需要一个新 abstraction。

## 缺口处理

目标项目确实缺少迁移必需能力时，只建立最小必要 Foundation，并明确其服务范围。不要借机重建整个基础层。
