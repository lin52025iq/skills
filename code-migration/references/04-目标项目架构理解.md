# 04 目标项目架构理解

## 目标

在迁移编码前理解目标仓库已经形成的稳定惯例。目标项目决定“如何实现已经确定的目标行为”，源项目只提供旧能力的事实证据和约束。

不要用目标架构反向覆盖用户已经明确的产品意图，也不要因为源项目已有某种抽象，就要求目标项目复制同样结构。

## 优先寻找相似实现

选择 2～5 个维护良好、测试充分、与待迁能力相似的目标模块，研究：

- 路由与页面 / 模块注册方式；
- 服务端状态、客户端状态、URL 状态的所有权；
- API Client、查询 / 缓存、错误和重试；
- 表单、校验、权限与功能开关；
- 设计系统、Token、布局和响应式；
- 埋点、日志、监控；
- 单元 / 组件 / 集成 / 端到端测试；
- 目录、命名、依赖方向、SSR / 构建边界。

核心问题：

> 按照已经确定的 **目标期望行为**，如果今天在这个仓库中原生开发，它应该怎样实现？

## 目标已有能力

迁移前主动查找目标已有：认证、权限、API Client、表格、表单、弹窗、日期、上传、埋点、错误边界、查询层、布局等能力。

能满足目标行为时优先使用迁移决策 **“复用目标”**，不要复制第二套基础设施。

如果目标已有能力只能满足部分需求，优先判断能否 **“适配”** 或扩展已有能力。

## 架构适配

典型映射应基于语义，而非技术名词：

```text
旧服务端状态 Store → 目标查询缓存（语义适合时）
旧表单 Store → 目标表单方案
旧界面 Wrapper → 目标设计系统
旧 Axios Layer → 目标 API Client
```

不要假设每个旧抽象都需要一个新抽象。

## 哪些技术问题不需要问用户

当目标仓库存在清晰、稳定、低风险的工程惯例时，以下问题通常应直接依据代码证据决定：

- 文件和目录组织；
- 组件命名；
- 使用现有 API Client / 查询层 / 表单 / 设计系统；
- 测试文件位置；
- 与现有模块一致的错误处理模式。

只有多个候选方案都会显著改变产品行为、公共架构或产生难以回退的长期影响，且仓库证据不足时，才需要向用户澄清。

## 缺口处理

目标项目确实缺少迁移必需能力时，只建立最小必要公共基础，不借机重建整个基础层。

新增公共抽象前至少确认：

- 当前迁移确实需要；
- 目标项目已有模式无法合理承载；
- 不只是为复制源项目结构；
- 接口范围足够小；
- 有明确验证方式。
