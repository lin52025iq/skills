# 04 目标项目架构理解

## 目标

在迁移编码前理解目标仓库已经形成的稳定惯例。目标项目决定“如何实现已经确定的目标行为”，源项目只提供旧能力的事实证据和约束。

不要把目标架构分析用于反向覆盖用户已经明确的产品意图；也不要因为源项目已有某种抽象，就要求目标项目复制同样结构。

## 优先寻找相似实现

选择 2～5 个维护良好、测试充分、与待迁能力相似的目标模块，研究：

- Router 与页面/模块注册方式；
- Server state、Client state、URL state 的所有权；
- API client、Query/cache、错误和重试；
- Form、Validation、权限与 Feature Flag；
- Design System、Token、布局和响应式；
- Analytics、日志、监控；
- unit/component/integration/E2E；
- 目录、命名、依赖方向、SSR/构建边界。

核心问题：

> 按照已经确定的 Desired Target Behavior，如果今天在这个仓库中原生开发，它应该怎样实现？

## Target Existing Capability

迁移前主动查找目标已有：Auth、Permission、API Client、Table、Form、Modal、Date、Upload、Analytics、Error Boundary、Query、Layout 等能力。

能满足目标行为时优先 `REUSE_TARGET`，不要为了“保持旧实现”复制第二套基础设施。

如果目标已有能力只能满足部分需求，优先判断能否 `ADAPT` 或扩展已有能力，而不是立即迁入源项目 abstraction。

## 架构适配

典型映射应基于语义，而非技术名词：

```text
旧 Server State Store → 目标 Query Cache（若语义适合）
旧表单 Store → 目标 Form 方案
旧 UI Wrapper → 目标 Design System
旧 Axios Layer → 目标 API Client
```

不要假设每个旧 abstraction 都需要一个新 abstraction。

## 哪些技术问题不需要问用户

当目标仓库已经存在清晰、稳定、低风险的工程惯例时，以下问题通常应由 Agent 依据代码证据决定，而不是进入 `MUST_ASK`：

- 文件和目录组织；
- 组件命名；
- 使用现有 API client / Query / Form / Design System；
- 测试文件位置；
- 与现有模块一致的错误处理模式。

只有当多个候选方案都会显著改变产品行为、公共架构或产生难以回退的长期影响，且仓库证据不足时，才需要向用户澄清。

## 缺口处理

目标项目确实缺少迁移必需能力时，只建立最小必要 Foundation，并明确其服务范围。不要借机重建整个基础层。

新增公共抽象前至少确认：

- 当前迁移确实需要；
- 目标项目已有模式无法合理承载；
- 不只是为复制源项目结构；
- 接口范围足够小；
- 有明确验证方式。
