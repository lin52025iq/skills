# 06 分阶段迁移与功能切片

## 目标

在**不过度建模**的前提下，把能力拆到足以避免假完成的粒度，并允许强关联项一起开发、一起验证。

## 长期层级

```text
Module
└─ Feature
   ├─ Feature Group / Scenario Group（可选）
   │  ├─ Atomic Item
   │  └─ Atomic Item
   └─ Atomic Item
```

- Module：稳定业务边界；
- Feature：用户可独立描述的完整能力；
- Group：可选阅读/聚合层；
- Atomic Item：唯一细粒度实施/验证事实源。

## Atomic Item 原则

Atomic Item 至少满足：

```text
一个主要语义
+ 明确触发 / 条件
+ 可观察或可证明结果
+ 实施完成可判断
+ 验证结果可判断
```

如果不同点可以独立遗漏、失败、验证、保留/删除，或拥有不同权限、状态、错误、副作用，就拆分。

不要拆成纯实现步骤：

```text
✓ 提交中禁止重复提交
✓ 409 后保留用户输入
✓ Mobile Drawer 全屏

✗ setLoading(true)
✗ 调用 API
✗ 更新局部 state
```

## Group 何时使用

只在以下情况使用：

- 平铺 Atomic Item 明显难读；
- 多个项属于同一用户场景；
- 需要用一个业务名称聚合多个原子结果。

简单 Feature 直接挂 Atomic Item，不为了形式创建 Group。

## 执行粒度

```text
Workstream = ownership / isolation / parallel boundary
Batch = 临时一起实施或验证 Atomic Item
```

不再维护独立 Slice 状态实体。

简单任务不创建 Batch；直接实施/验证单个 Atomic Item。

### 临时 DEV Batch

多个强关联 Atomic Item 可一起开发，完成后逐项写实施状态。Batch 本身不是长期事实源。

### 临时 VER Batch

多个 Atomic Item 可在一个真实用户场景中一起验证，一次准备数据/页面，但逐项记录结论。

```text
I01 通过
I02 失败
I03 通过
```

不能用“整体场景大致正常”代替逐项结果。

## 风险控制建模深度

### 低风险

```text
Feature + Atomic Item
```

只维护必要来源、目标行为和最小验证。

### 中风险

按风险增加关键 Discovery、SB、INT、REG；只有提高可读性时才建 Group。

### 高风险

完整 Discovery、07/08、输入基线、独立验证和必要集成治理。

**ID 密度随迁移风险增加，不按文档模板机械创建。**

## Discovery 停止原则

Discovery 达到“足够进入实施”即可，不追求不可证明的 100% 完整：

- 主要入口已覆盖；
- 关键 API/State/Event 已做反向检查；
- 关键权限/Flag/状态分支已分类；
- 相关测试已检查；
- 新发现项都有来源/范围分类；
- 没有会改变当前实现方向的关键未知。

## 完成派生

Group 状态由必需 Atomic Item 派生。

Feature 生命周期：

```text
已发现 → 已设计 → 实施中 → 验证中 → 已迁移 → 已清理
```

Feature `已迁移` 要求：全部范围内必需 Atomic Item 完成、要求的 Discovery/07/08 验证通过、必要集成验证通过。

Module 只维护派生摘要；全部范围内必需 Feature 达标且模块共享边界集成验证通过后才 `已完成`。

```text
Atomic Item 已完成
≠ Group 已完成
≠ Feature 已迁移
≠ Module 已完成
```

## 开发中新增能力

```text
发现候选
→ 证明来源
→ 判断 Feature
→ 做 Atomic 拆分
→ 判断是否加入当前临时 Batch
→ 实施 / 验证
```

不要为了省事把新能力塞进已完成的大条目。

## 前端边界

- `07`：WHAT，业务上必须发生什么；
- `08`：HOW / WHERE，用户如何体验、页面如何组织。

不要把同一交互时序在两个契约重复维护。
