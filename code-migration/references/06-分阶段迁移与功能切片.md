# 06 分阶段迁移与功能切片

## 目标

让 Agent 始终知道总体目标、当前阶段、当前功能、当前功能子项、完成标准和下一步，避免同时铺开大量半成品。

## 执行层级

按任务规模选用：

- `L0 上下文`：理解意图、源功能和目标约束；
- `L1 公共基础`：只做迁移必要的路由、权限、API / 类型等基础；
- `L2 结构`：页面骨架、布局区域、响应式骨架、设计系统基础；
- `L3 功能`：一个个完整用户能力；
- `L4 集成`：跨模块、埋点、URL、缓存、全局导航等；
- `L5 切流`：灰度、路由 / 功能开关切换；
- `L6 清理`：旧实现、Adapter、Flag、依赖清理。

简单组件无需机械经历所有层级。

## 两层切片

### 结构切片

只建立当前迁移范围必需的页面骨架、主要区域、布局、滚动归属、响应式和基础设计 Token。

### 功能切片

以可独立解释、实现和验证的用户能力为单位，例如“订单列表查询”而不是某个组件文件。紧密耦合的查询、分页、加载 / 错误可以作为一个切片。

## 执行队列与功能点清单必须分离

执行队列是 **调度视图**，回答：

```text
当前执行什么？
下一项是什么？
哪些已阻塞？
哪些已完成？
```

`02-迁移模块功能点清单.md` 是 **范围与完成度事实源**，回答：

```text
完整有哪些模块？
每个模块有哪些功能？
每个功能有哪些功能子项？
每一项当前状态是什么？
```

不得只维护执行队列而不维护功能点清单。

## 功能子项状态

功能子项必须直接维护：

```text
当前状态：未开始 / 开发中 / 待验证 / 验证中 / 已完成 / 已阻塞 / 已延后 / 不适用
范围状态：范围内 / 延后 / 范围外
是否必需：是 / 否
实施状态：未开始 / 实施中 / 已实施
验证状态：未验证 / 验证中 / 通过 / 失败 / 不适用
阻塞状态：未阻塞 / 已阻塞
```

一个切片可以覆盖多个功能子项，但切片“已完成”后必须逐项更新这些状态。

## 功能生命周期

```text
已发现 → 已设计 → 实施中 → 验证中 → 已迁移 → 已清理
```

`已阻塞` 是独立附加状态，不覆盖生命周期。

## 顺序模式

- **布局优先**：目标布局 / 设计体系差异大，多个功能依赖共同骨架；
- **功能优先**：目标页面已有，只迁某一能力；
- **代表性切片优先**：大型、高风险或跨技术栈迁移，先做一个代表性切片验证规则。

不要把布局优先误解为“先搭完整应用所有页面空壳”。

## 当前迁移焦点

每次实施必须维护：

```text
总体目标
当前阶段
当前模块 / 区域
当前切片
当前功能
当前功能子项
当前优先原因
依赖
禁止修改范围
完成定义
下一候选
```

单工作流内一次只有一个“当前执行”；全局可以有多个通过安全检查的独立工作流并行。

## 开始条件检查

开始切片前确认：

- 功能语义和目标期望行为足够明确；
- 当前功能 / 子项已登记在功能点清单；
- 当前状态、范围状态和是否必需已确定；
- 目标落点、依赖和验证方法明确；
- 不存在会改变当前实现方向的关键未知。

## 开发时同步更新

```text
选择切片 / 功能子项
→ 当前状态 = 开发中
→ 实施状态 = 实施中
→ 代码主体完成：实施状态 = 已实施，当前状态 = 待验证
→ 验证状态 = 验证中，当前状态 = 验证中
→ 验证结果 = 通过 / 失败 / 不适用
→ 同步当前状态
→ 如阻塞：阻塞状态 = 已阻塞
→ 重新计算功能生命周期
→ 更新模块汇总和执行队列
→ 再选择下一项
```

发现新的必要功能点时先补入功能清单、初始化状态，再决定是否纳入当前切片。

## 完成条件检查

切片完成至少确认：

- 覆盖的功能子项当前状态已更新；
- 计划内实施项已经“已实施”；
- 要求验证的项已经“通过 / 不适用”；
- 不存在被切片“已完成”掩盖的必需未完成项；
- 新发现的必要子项已补充；
- 当前功能生命周期已重新计算。

**切片已完成 ≠ 功能已迁移。**

## 选择下一切片

优先级：

1. 最大幅度降低未知风险；
2. 解除其他功能阻塞；
3. 用户明确优先；
4. 当前区域下一个完整能力或必要子项；
5. 最后才是单纯最容易。

## 学习循环

```text
理解 → 实施 → 验证 → 学习 → 更新模型 → 更新功能清单 → 下一切片
```
