# 06 分阶段迁移与功能切片

## 目标

让 Agent 始终知道总体目标、当前阶段、当前功能、当前子功能项、完成标准和下一步，避免同时铺开大量半成品。

## 执行层级

按任务规模选用：

- `L0 Context`：理解意图、源功能和目标约束；
- `L1 Foundation`：只做迁移必要的 Route、权限、API/类型等基础；
- `L2 Structure`：Page Shell、布局区域、响应式骨架、设计系统基础；
- `L3 Feature`：一个个完整用户能力；
- `L4 Integration`：跨模块、埋点、URL、缓存、全局导航等；
- `L5 Cutover`：切流、灰度、Route/Flag 切换；
- `L6 Cleanup`：旧实现、Adapter、Flag、依赖清理。

简单组件无需机械经历所有层级。

## 两层切片

### Structural Slice

只建立当前迁移范围必需的 Page Shell、主要 Region、Grid/Flex、Scroll owner、Responsive、基础 Token/Typography。

不要在结构阶段顺手实现所有业务细节。

### Functional Slice

以可独立解释、实现和验证的用户能力为单位，例如“订单列表查询”而不是“OrderTable.tsx”。紧密耦合的查询、分页、Loading/Error 可以作为一个 Slice。

## Slice Queue 与功能点清单必须分离

Slice Queue 是**调度视图**，负责回答：

```text
当前执行什么？
下一项是什么？
哪些已阻塞？
哪些已完成？
```

`02-迁移模块功能点清单.md` 是**范围与完成度事实源**，负责回答：

```text
完整有哪些 Module？
每个 Module 有哪些 Feature？
每个 Feature 有哪些 Feature Items？
每一项的实施、验证和阻塞状态是什么？
```

不得只维护 Slice Queue 而不维护功能点清单。

## Feature Item 状态

Feature Item 使用独立中文状态维度：

```text
范围状态：范围内 / 延后 / 范围外
是否必需：是 / 否
实施状态：未开始 / 实施中 / 已实施
验证状态：未验证 / 验证中 / 通过 / 失败 / 不适用
阻塞状态：未阻塞 / 已阻塞
```

一个 Slice 可以覆盖多个 Feature Items，但 Slice“已完成”后必须逐项更新这些状态。

## Feature 生命周期

```text
已发现 → 已设计 → 实施中 → 验证中 → 已迁移 → 已清理
```

- `已发现`：已识别能力，但目标行为或 Items 尚不完整；
- `已设计`：目标行为、必需 Items、Target Mapping 和验证方式已明确；
- `实施中`：存在必需 Item 未实施或正在实施；
- `验证中`：必需实现已完成，但仍有必要验证未完成；
- `已迁移`：所有“范围内 + 必需=是”Items 已实施且验证通过/不适用；
- `已清理`：旧入口、旧实现和临时结构已安全退出。

`已阻塞` 是独立附加状态，不覆盖生命周期。

## 顺序模式

- `Layout-first`：目标布局/设计体系差异大，多个功能依赖共同骨架；
- `Feature-first`：目标页面已有，只迁某一能力；
- `Representative-slice-first`：大型、高风险或跨技术栈迁移，先做一个代表性切片验证规则。

不要把 Layout-first 误解为“先搭完整应用所有页面空壳”。只建立当前范围所需最小完整结构。

## 当前迁移焦点

每次实施必须维护：

```text
总体目标
当前阶段
当前模块 / 区域
当前 Slice
当前 Feature
当前 Feature Items
当前优先原因
依赖
禁止修改范围
完成定义
下一候选
```

默认单 Agent 一次只有一个“当前执行”。其他 Slice 处于：

```text
待执行 / 已阻塞 / 已延后 / 已完成
```

## 开始条件检查

开始 Slice 前确认：

- 功能语义和 Desired Target Behavior 足够明确；
- 当前 Feature / Items 已登记在功能点清单；
- 范围状态和是否必需已确定；
- 目标落点、依赖和验证方法已经明确；
- 不存在会改变当前实现方向的关键 Unknown。

## 开发时同步更新

开发清单不是事后文档。执行时按以下循环：

```text
选择 Slice / Feature Items
→ 实施状态 = 实施中
→ 代码主体完成：实施状态 = 已实施
→ 验证状态 = 验证中
→ 验证结果 = 通过 / 失败 / 不适用
→ 如阻塞：阻塞状态 = 已阻塞，并记录原因和解除条件
→ 重新计算 Feature 生命周期
→ 更新 Module 汇总
→ 更新 Slice Queue
→ 再选择下一项
```

发现新的必要功能点时先补入功能清单、初始化状态，再决定是否纳入当前 Slice。

## 完成条件检查

Slice 完成至少确认：

- 当前 Slice 覆盖的 Feature Items 状态已更新；
- 计划内实施项已经“已实施”；
- 要求验证的项已经“通过 / 不适用”；
- 不存在被 Slice“已完成”掩盖的必需未完成项；
- 新发现的必要 Item 已补充；
- 当前 Feature 生命周期已按所有必需 Items 重新计算。

**Slice 已完成 ≠ Feature 已迁移。**

只有所有“范围内 + 必需=是”的 Feature Items 满足 Feature Done Gate 后，Feature 才能进入“已迁移”。

## 选择下一 Slice

优先级：

1. 最大幅度降低未知风险；
2. 解除其他 Feature 阻塞；
3. 用户明确优先；
4. 当前区域下一个完整能力或必要 Items；
5. 最后才是单纯最容易。

## Learning Loop

```text
理解 → 实施 → 验证 → 学习 → 更新模型 → 更新功能清单 → 下一 Slice
```

一个切片发现的通用规律，应先更新后续迁移方案和功能点清单，再扩大批次。
