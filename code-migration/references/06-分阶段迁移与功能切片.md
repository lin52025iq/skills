# 06 分阶段迁移与功能切片

## 目标

让 Agent 在合理粒度下拆分能力，既避免“一个大子项只完成一部分就误判完成”，也避免把业务能力拆成大量无意义碎点；同时允许强关联原子项一起开发、一起验证，提高效率。

## 风险分级

```text
低风险 / 中风险 / 高风险
```

风险决定发现、行为、交互、结构和验证治理强度，但 **不改变原子完成原则**。

## 层级与职责

```text
模块
└─ 功能
   ├─ 功能项组 / 场景组（可选）
   │  ├─ 原子功能项
   │  └─ 原子功能项
   └─ 原子功能项
```

- **模块**：稳定业务边界；
- **功能**：用户可独立描述的完整能力；
- **功能项组 / 场景组**：强关联原子项的组织和批量执行边界；
- **原子功能项**：最小实施 / 验证事实单元。

组是可选的。简单功能不为了形式创建组。

## 原子功能项判断

原子项至少满足：

```text
一个主要目标
+ 明确前置 / 触发
+ 实施完成可判断
+ 验证结果可判断
```

如果同一个条目里的不同点能够：

- 独立失败；
- 独立遗漏；
- 独立验证；
- 被用户单独保留 / 修改 / 删除；
- 有不同权限、状态、错误、副作用或导航结果；

则应拆分。

例如：

```text
退款提交支持金额校验、重复提交保护、409 恢复、成功刷新
```

不是一个合理原子项。应该建立“退款提交”组，并拆成多个原子项。

但以下不应继续拆：

- 同一不可分业务事务内必须同时成立的步骤；
- 拆开后无法定义独立用户结果；
- DOM、函数、变量、CSS class 等实现细节。

## 功能项组的使用

功能项组适合：

- 同一用户场景；
- 同一页面/弹层生命周期；
- 同一数据准备和测试环境；
- 共享实现上下文；
- 一起验证比逐个重新准备场景更高效。

例如：

```text
退款提交组
├─ 金额校验
├─ 重复提交保护
├─ 409 冲突恢复
└─ 成功后的关闭/刷新/Toast
```

组本身不拥有独立完成事实，状态由原子项派生。

## 拆分粒度 ≠ 执行粒度

合理拆细之后，不要求一个个串行开发。

### 开发批次

```text
I01 ─┐
I02 ─┼→ DEV-001
I03 ─┘
```

共享上下文的原子项可以一起实现。开发结束后必须逐项判断：

```text
I01 实施状态
I02 实施状态
I03 实施状态
```

不能因为代码批次结束就把全部项标完成。

### 验证批次

```text
I01 ─┐
I02 ─┼→ VER-001
I03 ─┘
```

可以在一个真实用户场景中一起验证：一次启动页面、一次准备数据、连续执行多个相关动作。

但最终仍逐项写：

```text
I01 验证通过
I02 验证失败
I03 验证通过
```

批次整体结果只是汇总。

## 批量验证的优势与边界

一起验证适合发现原子项之间的组合问题，例如：

```text
打开 Drawer
→ 修改字段
→ 触发校验
→ 提交
→ 遇到 409
→ 恢复输入
→ 再提交成功
→ 刷新数据
```

这个场景可以同时验证多个原子项，且更接近真实用户行为。

但：

- 某原子项失败不能把其他通过项一起标失败；
- 批次通过必须全部要求验证项通过 / 不适用；
- 验证中发现的新能力 / 新边界要补回台账；
- 不允许用“场景整体大致正常”代替逐项验证结论。

## 功能项组状态派生

组状态按范围内必需原子项计算：

1. 有阻塞 → `已阻塞`；
2. 有验证失败 → `验证失败`；
3. 有实施中 → `开发中`；
4. 实施要求已满足但存在未验证 → `待验证`；
5. 有验证中 → `验证中`；
6. 全部完成 → `已完成`。

禁止手工把部分完成组写成 `已完成`。

## 功能生命周期派生

```text
已发现 → 已设计 → 实施中 → 验证中 → 已迁移 → 已清理
```

功能进入 `已迁移` 必须满足：

- 全部范围内必需原子项已完成；
- 所有功能项组无未完成必需项；
- 无验证失败 / 阻塞；
- 要求的功能发现、来源真实性、源行为、交互、页面结构验证通过；
- 必要集成验证通过。

**一个原子项完成、一个组完成、一个 DEV 批次完成、一个 VER 批次完成，都不等于功能已迁移。**

## 模块完成派生

模块不是“最后一个 Feature 写完”就完成。

模块 `已完成` 要求：

- 所有范围内必需功能达到要求的目标生命周期；
- 无必需功能实施中、验证失败、阻塞；
- 模块共享 Route / API / State / Permission / Layout / Style 的必要集成验证通过；
- 模块整体用户目标和用户新方案成立。

## 前端四类覆盖

中/高风险前端功能按适用性检查：

```text
功能发现覆盖
+ 源行为覆盖
+ 交互语义覆盖
+ 页面结构覆盖
```

合理拆分后，源行为 / 交互 / 页面区域可以映射多个原子项；一个原子项也可覆盖多个紧密相关证据，但不要为了形式强制一对一。

## 开始条件

开始一个开发批次前：

- [ ] 模块 / 功能边界合理；
- [ ] 必要功能项组已建立；
- [ ] 原子性检查通过；
- [ ] 原子项来源真实性通过；
- [ ] 迁移决策 / 处理方式明确；
- [ ] 要求的发现 / 行为 / 交互 / 结构 Gate 已通过；
- [ ] 验证批次或验证方式已可描述。

## 实施循环

```text
选择强关联原子项
→ 建 DEV 批次
→ 一起开发
→ 逐项回写实施状态
→ 建 VER 批次
→ 一起执行真实场景验证
→ 逐项回写验证结果
→ 派生组状态
→ 派生功能生命周期
→ 派生模块状态
```

## 开发中新增能力

发现新能力时：

```text
先登记候选
→ 证明来源
→ 判断属于哪个功能 / 功能项组
→ 做原子性拆分
→ 判断是否影响当前 DEV / VER 批次
→ 再实施
```

禁止为了省事把新能力塞进一个已经存在的大条目，然后沿用该条目的“已完成”状态。

## 完成检查

切片 / 工作流完成至少确认：

- 所有覆盖原子项真实状态已更新；
- 开发批次没有掩盖未实施项；
- 验证批次已经逐项落账；
- 功能项组重新派生；
- 功能生命周期重新派生；
- 模块级状态没有被局部完成提前推进。

**切片已完成 ≠ 功能已迁移 ≠ 模块已完成。**
