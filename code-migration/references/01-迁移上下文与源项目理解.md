# 01 迁移上下文与源项目理解

## 目标

在写代码前建立足够可靠的迁移上下文，回答“为什么迁、迁什么、Source 真实是什么”。**不要把目录扫描等同于项目理解，也不要把 Agent 常识当成 Source 事实。**

复杂迁移的稳定事实默认写入 Target 根目录 `.code-migration/`，并把 `00-迁移状态总览.md` 作为跨对话恢复入口。

## 上下文盘点

至少确认：Source / Target 仓库与分支、技术栈、构建测试、Route / 权限 / Flag / 导航、State / Query / Form / Design System、API / SDK / 外部系统、用户明确保留/修改/删除/新增要求、用户新的 UX / 交互 / 页面布局方案，以及性能、无障碍、安全等非功能要求。

## 功能发现

正向：

```text
路由 / 导航 / 用户操作
→ 页面或容器
→ 状态 / 查询 / 表单
→ API / 缓存 / 副作用
→ 用户结果
```

反向：

```text
API / Mutation / State Transition / Event / Storage / Timer
→ 调用方
→ 条件 / 权限 / Feature Flag
→ 用户场景
```

代码存在不等于功能现役。检查隐藏入口、权限、Flag、调用方、替代实现、测试和历史证据。

## Discovery Gate

中/高风险默认检查主要入口、权限/Role、状态/枚举分支、Feature Flag、关键 API / Mutation / State 反向调用、轮询/Event/Storage/Cache、副作用、Loading/Empty/Error/Recovery、URL/Back/Deep Link 和相关测试。

不要求证明数学意义上的 100% 穷举；主要入口、关键反向调用、关键条件分支、相关测试和来源分类已覆盖，且没有会改变当前实现方向的关键未知，即足够进入实施。

## Provenance

正式 Feature / Atomic Item 来源：

```text
源系统证据 / 用户明确新增 / 目标产品要求
目标项目强制约束 / 推断候选 / 未知
```

`推断候选 / 未知` 不得静默成为必需范围。Target 已有组件不能反向决定产品需求。

## 标准迁移工作区

```text
<target-repo>/.code-migration/
├── 00-迁移状态总览.md
├── 01-迁移任务上下文.md
├── 02-迁移约束与开发规则.md
├── 03-迁移模块索引与进度.md
├── 04-功能语义.md                  # 全局/跨模块按需
├── 05-源行为与目标对齐清单.md      # 全局/跨模块按需
├── 06-页面结构与交互对齐清单.md    # 全局/跨模块按需
├── 07-功能融合映射.md              # 多来源按需
├── 08-迁移决策记录.md              # 重大决策按需
├── 09-迁移执行计划.md
└── modules/<module>/               # 复杂模块按需
```

模块目录按复杂度自适应：

```text
00-模块总览.md
01-模块功能点.md
02-功能语义.md           # 按需
03-源行为对齐.md         # 按需
04-页面结构与交互.md     # 按需
```

顶层 `03` 负责 Module 导航和派生进度；模块 `01` 才是该 Module 的 Feature / Atomic Item 权威源。简单低风险模块可以不拆目录。

## 模块拆分不是 Source 目录映射

`modules/<module>/` 按稳定业务边界、用户能力集合、维护价值和 Workstream 边界建立，不按 Source 文件夹机械一一创建。

## 导航与 Checkbox

模块化后顶层 `03` 通过相对链接进入模块 `00`；模块 `00` 再链接 `01` 和按需契约。Checkbox 只是完成投影，真实状态始终来自 Atomic Item / Feature / Module 状态模型。

## 基线与范围

记录 Git、构建、类型检查、测试、E2E 基线。发现额外问题时分类：`范围内 / 相关但延后 / 范围外`。不要因为 Target 技术债或现成组件自动扩大迁移范围。
