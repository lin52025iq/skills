# 01 迁移上下文与源项目理解

## 目标

在写代码前建立足够可靠的迁移上下文，回答“为什么迁、迁什么、Source 真实是什么”。**不要把目录扫描等同于项目理解，也不要把 Agent 常识当成 Source 事实。**

复杂迁移的稳定事实默认写入 Target 根目录 `.code-migration/`，并把 `00-迁移状态总览.md` 作为跨对话恢复入口。

## 上下文盘点

至少确认：Source / Target 仓库与分支、技术栈、构建测试、Route / 权限 / Flag / 导航、State / Query / Form / Design System、API / SDK / 外部系统、用户明确保留/修改/删除/新增要求、用户新的 UX / 交互 / 页面布局方案，以及性能、无障碍、安全等非功能要求。

## 功能发现不能只走一条调用链

正向追踪：

```text
路由 / 导航 / 用户操作
→ 页面或容器
→ 状态 / 查询 / 表单
→ API / 缓存 / 副作用
→ 用户结果
```

反向追踪：

```text
API / Mutation / State Transition / Event / Storage / Timer
→ 调用方
→ 条件 / 权限 / Feature Flag
→ 用户场景
```

代码存在不等于功能现役。检查隐藏入口、权限、Flag、调用方、替代实现、测试和历史证据。

## 功能触点图

中/高风险功能进入实施前，按适用项覆盖：入口、主要/次级操作、条件/权限能力、自动行为、副作用、URL / 状态恢复、Cache / Storage、异常恢复和测试隐含规则。

## Discovery Gate

中/高风险默认检查：主要入口、权限/Role、状态/枚举分支、Feature Flag、关键 API / Mutation / State 反向调用、轮询/Event/Storage/Cache、副作用、Loading/Empty/Error/Recovery、URL/Back/Deep Link 和相关测试。

不要求证明数学意义上的 100% 穷举；当主要入口、关键反向调用、关键条件分支、相关测试和来源分类已覆盖，且没有会改变当前实现方向的关键未知，即达到**足够进入实施**。

## Provenance

每个进入正式范围的 Feature / Atomic Item 记录来源：

```text
源系统证据
用户明确新增
目标产品要求
目标项目强制约束
推断候选
未知
```

`推断候选 / 未知` 不得静默成为 `范围内 + 必需=是`。Target 已有组件只说明“如果需要应如何实现”，不能证明产品一定需要该能力。

任何 `迁移决策=新增` 至少需要用户明确要求、已确认产品需求、Target 不可绕过强制契约或已确认 `08` Decision 之一。

## 澄清循环

```text
必须询问 / 可推断 / 可延后
```

只有答案会改变产品行为、业务规则、范围、权限、数据语义、Target 架构或不可逆方向时才优先询问。已有明确答案不重复问；暂时无法回答时标记阻塞或延后，不伪造确定性。

## 基线与范围

记录 Git、构建、类型检查、测试、E2E 基线。发现额外问题时分类：

```text
范围内 / 相关但延后 / 范围外
```

不要因为 Target 技术债或现成组件自动扩大迁移范围。

## 标准迁移工作区

```text
<target-repo>/.code-migration/
├── 00-迁移状态总览.md
├── 01-迁移任务上下文.md
├── 02-迁移约束与开发规则.md
├── 03-迁移模块功能点清单.md
├── 04-功能语义.md                  # 可选
├── 05-源行为与目标对齐清单.md      # 中/高风险按需
├── 06-页面结构与交互对齐清单.md    # 复杂前端按需
├── 07-功能融合映射.md              # 多来源按需
├── 08-迁移决策记录.md              # 重大决策按需
├── 09-迁移执行计划.md
└── modules/<module>/
```

标准顶层产物保持稳定编号；未使用的可选文档可以省略，但不要创建用途重复的无序号顶层文档。
