# 01 迁移上下文与源项目理解

## 目标

在写代码前建立足够可靠的迁移上下文，回答“为什么迁、迁什么、源项目真实是什么”。**不要把目录扫描等同于项目理解，也不要把 Agent 常识当成源系统事实。**

复杂迁移的稳定事实默认写入目标项目根目录 `.code-migration/`，并把 `00-迁移状态总览.md` 作为跨对话恢复入口。

## 上下文盘点

至少确认：

- 源仓库、目标仓库、分支与局部仓库指令；
- 技术栈、包管理器、工作区、构建与测试命令；
- 路由、页面入口、权限、功能开关、导航和部署边界；
- 状态、请求层、缓存、表单、组件库、样式、国际化、埋点；
- API、SDK、外部系统、环境变量和静态资源边界；
- 用户明确的保留、修改、融合、删除和新增要求；
- 用户新的 UX / 交互 / 页面布局迁移方案；
- 性能、无障碍、SEO、SSR、浏览器、安全等非功能要求。

## 功能发现不能只走一条调用链

从用户可达入口做正向追踪：

```text
路由 / 导航 / 用户操作
→ 页面或容器
→ 状态 / 查询 / 表单
→ API / 缓存 / 副作用
→ 界面状态与用户结果
```

同时对关键能力做反向追踪：

```text
API / Mutation / 状态转换 / Event / Storage / Timer
→ 调用方
→ 条件 / 权限 / Feature Flag
→ 用户场景
```

**代码存在不等于功能现役。** 检查未注册路由、隐藏菜单、权限、功能开关、注释、调用方、替代实现、测试和历史证据。

## 功能触点图

中/高风险功能在进入实施前，应形成轻量的功能触点图，至少覆盖适用项：

```text
入口
主要操作
条件能力
权限能力
自动行为
后台副作用
导航 / URL 状态
缓存 / Storage
异常与恢复
测试中隐含规则
```

例如：

```text
订单详情
├─ 入口：列表点击 / 深链接
├─ 操作：退款 / 取消 / 修改地址
├─ 条件：已付款才可退款
├─ 权限：admin 才可见内部备注
├─ 自动：轮询订单状态
├─ 副作用：退款后刷新 Timeline
└─ 异常：403 / 404 / 409
```

## 功能发现覆盖检查

中/高风险功能默认检查：

- [ ] 用户可达入口已检查；
- [ ] 主要操作和次级操作已检查；
- [ ] 权限 / Role 分支已检查；
- [ ] 状态机 / 枚举 / 类型分支已检查；
- [ ] Feature Flag / 配置分支已检查；
- [ ] API / Mutation / 状态转换已反向查调用方；
- [ ] 自动刷新、轮询、事件、Storage、缓存、副作用已检查；
- [ ] Loading / Empty / Error / Recovery 已检查；
- [ ] URL、返回、深链接和页面状态恢复已检查；
- [ ] 相关测试已作为发现证据检查；
- [ ] 无未解释的重要调用方或条件分支。

不要求证明数学意义上的 100% 穷举，但要达到当前证据下的**功能发现趋于稳定**：继续检查入口、反向调用、测试和条件分支时，不再持续出现新的关键必需能力。

## 功能来源真实性

每个进入正式功能台账的功能 / 子项都必须记录来源类型：

```text
源系统证据
用户明确新增
目标产品要求
目标项目强制约束
推断候选
未知
```

规则：

- `源系统证据`：必须能指向运行、契约、代码、测试或历史证据；
- `用户明确新增`：迁移决策可以是“新增”；
- `目标产品要求`：按产品要求决定新增 / 适配 / 替换；
- `目标项目强制约束`：仅加入实现真正不可绕过的要求，不自动扩张产品能力；
- `推断候选`：不能直接成为“范围内 + 必需=是”；
- `未知`：不能静默实施。

**目标仓库已有组件只说明“如果需要该能力应如何实现”，不能证明产品一定需要该能力。**

以下理由不能单独把一个能力升级为正式迁移需求：

- “一般后台都有”；
- “这样体验更好”；
- “目标项目其他页面有”；
- “Agent 建议增加”。

设计建议可以记录，但必须与“发现事实 / 目标需求”分开。

## 新增能力检查

任何 `迁移决策=新增` 至少需要一个明确依据：

```text
用户明确要求
已确认目标产品需求
目标仓库不可绕过的强制契约
已确认迁移决策记录
```

否则保留为候选 / 未知，不进入必需范围。

## 不清晰信息的澄清循环

先分类：

- `必须询问`：答案会改变产品行为、业务规则、范围、权限、数据语义、目标架构或不可逆方向；
- `可推断`：可依据目标项目惯例、高等级证据或明确默认值安全推断；
- `可延后`：不会阻塞当前切片，可后续确认。

```text
发现关键未知
→ 记录到状态总览
→ 选择最阻塞当前工作的少量问题
→ 向用户提问
→ 将回答写回功能清单 / 迁移决策 / 执行计划
→ 重新检查开始条件
```

提问规则：已有明确答案不重复问；用户回答立即持久化；暂时无法回答时标记“已阻塞”或“已延后”，不要伪造确定性。

## 基线

记录当前 Git 状态和能够运行的构建、类型检查、代码检查、测试、端到端测试。源项目原有失败必须与迁移引入的失败区分。

## 迁移范围

发现额外问题时分类：

```text
范围内 / 相关但延后 / 范围外
```

不要因为发现目标项目技术债或可复用组件就自动扩大迁移范围。

## 迁移工作区

默认写入：

```text
<target-repo>/.code-migration/
```

其中：

- `00-迁移状态总览.md`：跨对话恢复入口；
- `02-迁移模块功能点清单.md`：功能范围、来源和实施事实；
- `07-源行为与目标对齐清单.md`：中/高风险源行为验证；
- `08-页面结构与交互对齐清单.md`：中/高风险前端页面结构、交互与视觉迁移；
- `modules/<module>/`：复杂模块的局部事实。

只在有独立规划、验证或跨会话维护价值时拆模块，不按源目录树机械拆分。
