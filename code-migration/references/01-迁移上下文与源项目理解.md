# 01 迁移上下文与源项目理解

## 目标

在写代码前建立足够可靠的迁移上下文，回答“为什么迁、迁什么、源项目真实是什么”。不要把目录扫描等同于项目理解。

## 上下文盘点

至少确认：

- 源仓库、目标仓库、分支与局部仓库指令；
- 技术栈、包管理器、workspace、构建与测试命令；
- Route、页面入口、权限、Feature Flag、导航和部署边界；
- 状态、请求层、缓存、表单、组件库、样式、i18n、埋点；
- API、SDK、外部系统、环境变量和静态资源边界；
- 用户明确的保留、修改、融合、删除和新增要求；
- 性能、Accessibility、SEO、SSR、浏览器、安全等非功能要求。

## 从真实入口理解

优先从用户可达入口反向建立调用链：

```text
Route / Navigation / User Action
→ 页面或容器
→ State / Query / Form
→ API / Cache / Side Effect
→ UI 状态与用户结果
```

代码存在不等于功能现役。检查未注册 Route、隐藏菜单、权限、Flag、注释、调用方、替代实现、测试和历史证据。

## 基线

记录当前 Git 状态和能够运行的 build/typecheck/lint/test/E2E。源项目原有失败必须与迁移引入的失败区分。

## 迁移范围

发现额外问题时分类：

- `IN_SCOPE`
- `RELATED_BUT_DEFERRED`
- `OUT_OF_SCOPE`

不要因为发现目标项目技术债就自动扩大迁移范围。

## 输出

复杂任务将稳定事实写入 `../templates/01-迁移任务上下文.md`；细粒度功能事实进入功能清单，不在这里重复维护。
