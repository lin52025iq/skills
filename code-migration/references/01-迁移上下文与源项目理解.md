# 01 迁移上下文与源项目理解

## 目标

在写代码前建立足够可靠的迁移上下文，回答“为什么迁、迁什么、源项目真实是什么”。**不要把目录扫描等同于项目理解。**

复杂迁移的稳定事实默认写入目标项目根目录 `.code-migration/`，并把 `00-迁移状态总览.md` 作为跨对话恢复入口。

## 上下文盘点

至少确认：

- 源仓库、目标仓库、分支与局部仓库指令；
- 技术栈、包管理器、工作区、构建与测试命令；
- 路由、页面入口、权限、功能开关、导航和部署边界；
- 状态、请求层、缓存、表单、组件库、样式、国际化、埋点；
- API、SDK、外部系统、环境变量和静态资源边界；
- 用户明确的保留、修改、融合、删除和新增要求；
- 性能、无障碍、SEO、SSR、浏览器、安全等非功能要求。

## 从真实入口理解

优先从用户可达入口反向建立调用链：

```text
路由 / 导航 / 用户操作
→ 页面或容器
→ 状态 / 查询 / 表单
→ API / 缓存 / 副作用
→ 界面状态与用户结果
```

**代码存在不等于功能现役。** 检查未注册路由、隐藏菜单、权限、功能开关、注释、调用方、替代实现、测试和历史证据。

## 不清晰信息的澄清循环

先分类：

- `必须询问`：答案会改变产品行为、业务规则、范围、权限、数据语义、目标架构或不可逆方向；
- `可推断`：可依据目标项目惯例、高等级证据或明确默认值安全推断；
- `可延后`：不会阻塞当前切片，可后续确认。

```text
发现关键未知
→ 记录到状态总览
→ 选择最阻塞当前工作的少量问题
→ 向用户提问
→ 将回答写回功能清单 / 迁移决策 / 执行计划
→ 重新检查开始条件
→ 仍有关键未知时继续下一轮
```

提问规则：

1. 每轮优先问 1～3 个最影响迁移方向的问题；
2. 说明为什么需要答案以及影响什么；
3. 已有明确答案的内容不要重复询问；
4. 用户回答后立即持久化；
5. 用户允许默认方案时记录为迁移决策；
6. 暂时无法回答时标记“已阻塞”或“已延后”，不要伪造确定性；
7. 新对话先恢复历史问题和答案。

## 基线

记录当前 Git 状态和能够运行的构建、类型检查、代码检查、测试、端到端测试。源项目原有失败必须与迁移引入的失败区分。

## 迁移范围

发现额外问题时分类：

```text
范围内 / 相关但延后 / 范围外
```

不要因为发现目标项目技术债就自动扩大迁移范围。

## 迁移工作区

默认写入：

```text
<target-repo>/.code-migration/
```

其中：

- `00-迁移状态总览.md`：跨对话恢复入口；
- 顶层文档：全局上下文、功能映射、迁移决策与执行计划；
- `modules/<module>/`：复杂模块的局部功能、行为、计划和决策。

只在有独立规划、验证或跨会话维护价值时拆模块，不按源目录树机械拆分。
