# 01 迁移上下文与源项目理解

## 目标

在写代码前建立足够可靠的迁移上下文，回答“为什么迁、迁什么、源项目真实是什么”。不要把目录扫描等同于项目理解。

复杂迁移的稳定事实默认写入目标项目根目录的 `.code-migration/`，并把 `00-迁移状态总览.md` 作为跨对话恢复入口。

## 上下文盘点

至少确认：

- 源仓库、目标仓库、分支与局部仓库指令；
- 技术栈、包管理器、workspace、构建与测试命令；
- Route、页面入口、权限、Feature Flag、导航和部署边界；
- 状态、请求层、缓存、表单、组件库、样式、i18n、埋点；
- API、SDK、外部系统、环境变量和静态资源边界；
- 用户明确的保留、修改、融合、删除和新增要求；
- 性能、Accessibility、SEO、SSR、浏览器、安全等非功能要求。

## 从真实入口理解

优先从用户可达入口反向建立调用链：

```text
Route / Navigation / User Action
→ 页面或容器
→ State / Query / Form
→ API / Cache / Side Effect
→ UI 状态与用户结果
```

代码存在不等于功能现役。检查未注册 Route、隐藏菜单、权限、Flag、注释、调用方、替代实现、测试和历史证据。

## 不清晰信息的澄清循环

不要把所有未知都变成问题，也不要为了减少打扰而静默猜测。先分类：

- `MUST_ASK`：答案会改变当前迁移的产品行为、业务规则、范围、权限、数据语义、目标架构或不可逆实现方向；
- `CAN_INFER`：可以依据目标项目惯例、高等级证据或明确默认值安全推断；
- `CAN_DEFER`：不会阻塞当前 Slice，可以后续再确认。

对于 `MUST_ASK`，允许并鼓励多轮向用户澄清：

```text
发现关键 Unknown
→ 记录到 .code-migration/00-迁移状态总览.md
→ 选择最阻塞当前 Slice 的少量问题
→ 向用户提问
→ 将回答写回功能清单 / Decision / 执行计划
→ 重新检查 Ready Gate
→ 仍有关键 Unknown 时继续下一轮
```

提问规则：

1. 每轮优先问 1～3 个最影响迁移方向的问题，避免一次抛出长问卷；
2. 问题应说明“为什么需要这个答案”以及它会影响什么决策；
3. 已经从用户、目标仓库或 `.code-migration/` 得到明确答案的内容不要重复询问；
4. 用户回答后立即持久化，不只保留在聊天上下文中；
5. 若用户明确允许 Agent 采用某个默认方案，将其记录为 Decision，而不是以后再次询问；
6. 如果用户暂时无法回答，可将功能标记 `BLOCKED` 或在风险可控时 `DEFER`，不要伪造确定性；
7. 新对话先恢复历史问题和答案，再判断是否需要继续澄清。

## 基线

记录当前 Git 状态和能够运行的 build/typecheck/lint/test/E2E。源项目原有失败必须与迁移引入的失败区分。

## 迁移范围

发现额外问题时分类：

- `IN_SCOPE`
- `RELATED_BUT_DEFERRED`
- `OUT_OF_SCOPE`

不要因为发现目标项目技术债就自动扩大迁移范围。

## Migration Workspace

默认写入：

```text
<target-repo>/.code-migration/
```

其中：

- `00-迁移状态总览.md`：跨对话恢复入口、当前焦点、最近完成、阻塞、待澄清问题和下一步；
- 顶层 `01-05` 文档：保存全局上下文、功能映射、关键 Decision 与总体执行计划；
- `modules/<module>/`：复杂功能、页面区域或模块的局部功能清单、执行计划和决策。

只在有独立规划、独立验证或跨会话维护价值时拆模块，不按源目录树机械拆分。

## 输出

复杂任务将稳定事实从 Skill 模板实例化到目标项目 `.code-migration/`；细粒度功能事实进入功能清单或对应模块目录，不在多个文档重复维护。
