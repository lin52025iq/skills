# 09 迁移状态与跨会话协作

## 目标

让长周期迁移可以跨对话、跨 Agent 可靠续接，同时避免状态文档反过来主导迁移。`.code-migration/` 是迁移状态的持久化索引，不取代代码、测试、用户规则和已确认迁移决策。

## 默认工作区

```text
<target-repo>/.code-migration/
├── 00-迁移状态总览.md
├── 01-迁移任务上下文.md
├── 02-迁移模块功能点清单.md
├── 03-功能融合映射.md
├── 04-迁移决策记录.md
├── 05-迁移执行计划.md
├── 06-迁移约束与开发规则.md
├── 07-源行为与目标对齐清单.md
├── 08-页面结构与交互对齐清单.md
└── modules/<module>/
```

只有模块具备独立规划、验证、决策或跨会话维护价值时才拆 `modules/<module>/`。

## 事实源优先级

1. 用户最近一次明确且仍有效的迁移意图、**新 UX / 交互 / 布局方案**与开发约束；
2. 生效用户规则和已确认迁移决策 / 目标产品契约；
3. 当前真实代码、Git、运行结果和测试结果；
4. `02` 功能范围/来源/实施事实、`07` 源行为验证事实、`08` 页面结构/交互验证事实；
5. 执行计划和输入基线；
6. `00-迁移状态总览.md`。

**状态总览是恢复入口和摘要缓存，不得覆盖更高优先级事实。**

## 功能生命周期

```text
已发现 → 已设计 → 实施中 → 验证中 → 已迁移 → 已清理
```

`已阻塞` 是附加状态，不替代生命周期。

## 会话交接检查门槛

以下情况必须同步状态：

- 当前切片通过完成条件；
- 准备结束或暂停对话；
- 准备切换 Agent / 开启新对话；
- 当前工作被“必须询问”阻塞；
- 功能发现或用户新方案发生变化；
- 发现文档与代码 / Git 状态不一致。

至少记录：

```text
总体目标
用户新 UX / 交互 / 布局方案
当前风险级别
功能发现覆盖 / 来源真实性
目标期望行为
当前阶段 / 模块 / 切片
功能子项状态
07 源行为验证状态
08 页面结构 / 交互验证状态
最后完成动作
当前代码状态
测试 / 验证
输入基线
待澄清问题 + 已回答结论
未提交 / 待完成工作
下一推荐动作
```

半完成代码不得标成“已迁移”。

## 新对话恢复

新 Agent / 新对话按顺序：

1. 读取 `00-迁移状态总览.md`；
2. 恢复用户新的功能 / 交互 / 布局方案；
3. 读取 `06-迁移约束与开发规则.md` 中所有“生效中”规则；
4. 读取 `02`，恢复功能来源、范围、处理方式、实施状态和当前状态；
5. 中/高风险恢复功能发现覆盖和 `07` 源行为验证；
6. 复杂前端页面读取 `08`，恢复源/目标区域树、交互语义、响应式和已批准差异；
7. 读取执行计划和输入基线；
8. 检查 Git 分支、最近提交、工作区、实际代码和测试；
9. 状态一致时从下一推荐动作继续；
10. 不一致时只对受影响范围重新校准；
11. 不重复开发已迁移项，不重复询问已有答案，也不重新脑补已经判定为“候选/不在范围”的功能。

## 重新校准

以下情况标记 **“需要重新校准”**：

- 文档声称完成，但代码或测试不支持；
- 工作区存在未说明的半完成修改；
- 最近提交改变当前工作，但状态文档未更新；
- 无法确认当前代码对应哪个迁移阶段；
- 工作流输入基线与最新功能发现 / 源行为 / 用户新方案 / 迁移决策 / 目标行为不一致；
- `02 / 07 / 08` 对同一功能的范围或验证结论互相冲突。

重新校准只回答：

```text
哪些已完成？
哪些实现了但未验证？
哪些验证失败？
哪些半完成？
哪些尚未开始？
哪些功能来源存疑？
哪些功能发现仍不完整？
哪些 07 / 08 文档已过期？
哪些工作流输入已过期？
下一安全动作是什么？
```

## 澄清持久化

待澄清问题记录：

```text
问题 ID
问题
类型：必须询问 / 可推断 / 可延后
影响功能 / 切片 / 工作流 / 页面结构 / 交互
状态：待处理 / 已回答 / 已延后
用户回答 / 推断
关联迁移决策
```

新的对话必须先恢复历史答案，不重复提问。

## 版本控制与敏感信息

长期迁移默认让 `.code-migration/` 与代码一起进入版本控制，除非用户或目标仓库规范明确要求不提交。

禁止写入：Token、Secret、Password、API Key、Cookie、Session、私钥、`.env` 真实值、真实客户敏感数据、不必要的生产 payload。

## 多 Agent 协作模型

多 Agent 的目标是形成 **“分析提前、开发并行、验证流水化”**，不是把大量未理解功能同时交给多个 Agent。

推荐角色：

```text
协调 Agent
源 / 功能发现分析 Agent
目标架构分析 Agent
实施 Agent
验证 Agent
审查 Agent
```

典型流水线：

```text
分析 Agent：发现 / 行为 / 结构 N+1
实施 Agent：开发 N
验证 Agent：验证 N-1
协调 Agent：维护依赖、规则、台账和全局状态
```

### 并行原则

> **每个工作流内只保持一个主要实施焦点；全局可以同时存在多个通过安全检查的独立工作流。**

并行前提是每个工作流独立可解释、独立可验证、独立可合并。

### 工作流输入基线

中/高风险长任务或实施工作流开始前至少记录：

```text
工作流 ID
功能发现 / Source Evidence 版本
源行为版本
用户新 UX / 交互 / 布局方案版本
目标期望行为版本
相关迁移决策 / 用户规则版本
目标落点基线
开始时 Git 提交
```

如果实施过程中关键输入改变：

1. 判断是否影响当前功能子项或页面结构 / 交互；
2. 不影响 → 记录后继续；
3. 影响 → 相关子项和工作流标记“已阻塞”；
4. 更新输入基线；
5. 重新执行受影响的功能发现 / 行为 / 结构 / 交互 Gate；
6. 通过后再继续。

**不得按过期行为模型或过期用户方案继续开发。**

### 并行安全检查

开始新的并行工作流前至少检查：

- 是否修改相同生产文件 / 组件；
- 是否修改同一路由、布局、状态或查询所有权；
- 是否共享尚未稳定的 API / 数据契约 / 共享类型；
- 是否同时修改同一权限模型、状态机或 Invariant；
- 是否依赖同一个未完成公共基础；
- 是否修改同一公共组件 / 抽象；
- 是否修改同一 Adapter / 功能开关 / 切流路径；
- 是否同时修改 package manifest / lockfile；
- 是否同时修改 registry / generated / i18n aggregate；
- 是否存在共享脚本 / 生成器会覆盖彼此输出；
- 是否存在明确先后依赖。

允许并行必须同时满足：

```text
代码边界独立
+ 数据 / 契约独立
+ 业务语义独立
+ 页面结构 / 交互边界可独立
+ 发布 / 合并路径可独立
```

高风险重叠时：拆共享基础、指定唯一负责人，或退回串行。

### 工作区隔离

多个实施 Agent 真正并行写代码时，优先使用：

```text
独立 branch / worktree / isolated workspace
```

共享 working tree 下必须明确文件写入负责人；无法可靠隔离时退回串行。

如果当前运行环境不支持子 Agent 或安全隔离，**不得伪造并行能力**，保留工作流模型并由当前 Agent 串行执行。

### 负责人

每个并行工作流必须记录：

```text
工作流 ID
负责人
模块 / 功能 / 功能子项
来源真实性 / 功能发现状态
关联 07 / 08
允许修改范围
禁止修改范围
输入基线
依赖
当前状态
验证负责人
合并条件
```

同一功能子项、共享契约、公共基础或共享页面结构同一时刻只能有一个生产代码负责人。

### 子 Agent 写入边界

| 角色 | 生产代码 | 状态 / 事实写入 | 全局状态总览 |
|---|---|---|---|
| 协调 Agent | 必要时 | 汇总 | 主要写入者 |
| 源 / 功能发现 Agent | 否 | 来源、触点、07 分析事实 | 否 |
| 目标架构分析 Agent | 否 | Target Mapping / 08 目标结构方案 | 否 |
| 实施 Agent | 当前工作流 | `02` 当前子项 | 否 |
| 验证 Agent | 默认否 | `07 / 08` 验证事实 | 否 |
| 审查 Agent | 默认否 | 问题 / 审查结论 | 否 |

**同一状态块同一时刻只能有一个负责人。**

### 工作流验证与集成验证

每个工作流先完成自己的独立验证；多个工作流合并后，如存在共享运行边界，再执行集成验证。

集成验证至少考虑：构建、类型检查、共享测试、路由 / 权限、共享状态 / 查询 / API、页面共享 Layout、全局样式、端到端路径、lockfile / generated / registry。

**各工作流单独通过，不代表整批并行工作最终完成。**

### 冲突与降级

并行中出现共享文件、契约冲突、页面结构冲突、交互决策冲突、输入基线漂移或合并测试互相破坏时：

1. 暂停受影响工作流；
2. 相关子项标记“已阻塞”；
3. 协调 Agent 重新划分负责人、拆公共基础或更新输入基线；
4. 必要时退回串行；
5. 重新执行受影响 Gate 和验证。

## 多 Agent 交接

每个工作流结束、暂停或切换 Agent 时独立记录：

- 当前功能 / 子项；
- 功能发现覆盖 / 来源真实性；
- 用户新方案和关联 `08`；
- 已修改文件；
- 当前实施 / 验证状态；
- 输入基线；
- 未完成工作；
- 依赖其他工作流；
- 可安全继续的位置；
- 合并前还需完成的 `07 / 08 / 集成` 验证。

协调 Agent 再把这些摘要汇总到全局状态总览。
