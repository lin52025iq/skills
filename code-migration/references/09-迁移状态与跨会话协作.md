# 09 迁移状态与跨会话协作

## 目标

让长周期迁移可以跨对话、跨 Agent 可靠续接，同时避免状态文档反过来主导迁移。`.code-migration/` 是迁移状态的持久化索引，不是取代代码、测试和已确认 Decision 的另一套真相。

## 默认工作区

复杂或长周期迁移默认写入目标仓库根目录：

```text
<target-repo>/.code-migration/
├── 00-迁移状态总览.md
├── 01-迁移任务上下文.md
├── 02-迁移模块功能点清单.md
├── 03-功能融合映射.md
├── 04-迁移决策记录.md
├── 05-迁移执行计划.md
├── 06-迁移约束与开发规则.md
└── modules/
    └── <module>/
```

只有当某模块具备独立规划、验证、决策或跨会话维护价值时才拆 `modules/<module>/`；不要按源仓库目录树机械拆分。

## 事实源优先级

发生冲突时使用以下优先级：

1. 用户最近一次明确且仍有效的迁移意图；
2. 已确认并记录的 Decision / 目标产品契约；
3. 当前真实代码、Git 状态、Runtime 和测试结果；
4. 当前模块功能台账、详细功能文档与执行计划；
5. `00-迁移状态总览.md`。

`00-迁移状态总览.md` 是快速恢复入口和摘要缓存，不得拿过期总览覆盖真实代码或已确认 Decision。

如果高优先级来源之间互相冲突，停止相关 Slice，进入重新校准或澄清循环。

## 功能生命周期

运行时统一使用中文：

```text
已发现 → 已设计 → 实施中 → 验证中 → 已迁移 → 已清理
```

- `已发现`：已识别能力，但目标决策尚未完成；
- `已设计`：目标行为和 Target Mapping 已足够明确；
- `实施中`：正在开发，不能视为完成；
- `验证中`：主要实现已完成，但验证 Gate 未完成；
- `已迁移`：目标能力已通过迁移 Gate；
- `已清理`：旧入口、旧实现和临时结构已按计划退出。

`已阻塞` 是额外标记，不替代生命周期。例如：`实施中 + 已阻塞`。

## 会话交接 Gate

以下情况必须同步状态：

- 当前 Slice 通过完成条件；
- 准备结束或暂停当前对话；
- 准备切换 Agent / 开启新对话；
- 当前 Slice 被“必须询问”阻塞；
- 发现文档与代码/Git 状态不一致。

至少记录：

```text
总体目标
目标期望行为
当前阶段 / Module / Slice
生命周期状态
最后完成动作
当前代码状态
测试 / 验证
当前执行 / 待执行 / 已阻塞 / 已延后 / 已完成
待澄清问题 + 已回答结论
未提交 / 待完成工作
相关 Decision
下一推荐动作
优先读取文件 / 模块
```

半完成代码必须标为“实施中”或“验证中”，不得因为“文件已经写了”标成“已迁移”。

## 新对话恢复

新 Agent / 新对话：

1. 先读 `.code-migration/00-迁移状态总览.md`；
2. 读取 `.code-migration/06-迁移约束与开发规则.md` 中所有“生效中”规则；
3. 恢复总体目标、目标期望行为、当前 Slice、Decision 和已回答问题；
4. 按索引读取当前模块的功能台账和执行计划；
5. 检查 Git branch、最近相关 commit、working tree 和当前 Slice 实际代码；
6. 若状态一致，从“下一推荐动作”续接；
7. 若不一致，只对当前相关范围执行重新校准，不重新扫描所有源项目；
8. 不重复开发“已迁移/已清理”项，也不重复询问已有答案。

## 重新校准

以下情况标记“需要重新校准”：

- 文档声称完成，但代码或测试不支持；
- working tree 存在未说明的半完成修改；
- 最近提交改变了当前 Slice，但状态文档没有更新；
- 无法确认当前代码对应哪个迁移阶段。

重新校准只需回答：

```text
哪些已完成？
哪些实现了但未验证？
哪些半完成？
哪些尚未开始？
哪些文档已过期？
下一安全动作是什么？
```

修正状态后再继续写新代码。

## 澄清持久化

待澄清问题记录：

```text
ID
问题
类型：必须询问 / 可推断 / 可延后
影响 Feature / Slice
状态：待处理 / 已回答 / 已延后
用户回答 / 推断
关联 Decision
```

新的对话必须先恢复历史答案，不重复提问。

只有当证据不足且答案会实质改变目标行为或不可逆方向时才使用“必须询问”。普通命名、文件组织、组件选择以及目标仓库已经有稳定范例的技术细节优先“可推断”。

## 版本控制

长期迁移默认应让 `.code-migration/` 与代码一起进入版本控制，除非用户或目标仓库规范明确要求不提交。

开始时检查它是否被 `.gitignore` 忽略；若忽略且迁移需要跨机器、跨开发者或长期续接，应显式处理，而不是假设本地文件能持久存在。

迁移文档提交应与相关代码变更保持可理解的关联，但不要为了每次状态文字变化制造无意义提交。

## 敏感信息

`.code-migration/` 可能进入 Git，因此禁止写入：

- Token / Secret / Password / API Key；
- Cookie、Session、私钥；
- `.env` 的真实值；
- 真实客户或用户敏感数据；
- 不必要的生产 payload 或凭据化 URL。

允许记录环境变量名称、脱敏示例、字段结构、错误类型和必要的非敏感业务语义。

## 多 Agent 协作模型

多 Agent 的目标是形成“分析提前、开发并行、验证流水化”的迁移流水线，而不是简单把大量未理解 Feature 同时交给多个 Agent。

推荐角色：

```text
Coordinator / 协调者
Source Analyst / 源行为分析
Target Analyst / 目标架构分析
Implementer / 实施
Verifier / 验证
Reviewer / 审查
```

典型流水线：

```text
Source/Target Agent：分析 N+1
Implementer：开发 N
Verifier：验证 N-1
Coordinator：维护依赖、规则、台账和全局状态
```

### 允许多个 Implementer 并行

默认不限制为“永远只有一个开发 Agent”。当多个 Feature 彼此独立并通过并行安全检查时，可以同时建立多个实施 Workstream。

例如：

```text
Workstream A：Dashboard Alerts
Workstream B：User Settings
Workstream C：Order Export
```

如果三者不存在共享写入边界、共享契约和未解决依赖，可以由不同 Implementer 同时开发。

并行开发的前提是**每个 Workstream 独立可解释、独立可验证、独立可合并**，而不是仅仅“看起来属于不同页面”。

### 并行安全 Gate

开始新的并行实施 Workstream 前至少检查：

- 是否会修改相同生产文件或相同组件；
- 是否会修改同一 Route / Layout / Store / Query Key 所有权；
- 是否共享尚未稳定的 API / Data Contract；
- 是否同时修改同一权限模型、状态机或业务 Invariant；
- 是否依赖同一个尚未完成的 Foundation；
- 是否会同时改同一个公共组件或基础设施 abstraction；
- 是否会修改同一个临时 Adapter / Feature Flag / 切流路径；
- 是否存在明确先后依赖。

任一项存在高风险重叠时：

1. 优先拆出共享 Foundation；或
2. 明确唯一 Owner；或
3. 退回串行实施。

不得通过“不同 Agent 使用不同分支”来掩盖实际语义依赖。

### Ownership

每个并行 Workstream 必须记录：

```text
Workstream ID
Owner Agent
Module / Feature / Feature Items
允许修改范围
禁止修改范围
依赖
当前状态
验证负责人
合并条件
```

同一个 Feature Item 同一时刻只能有一个生产代码 Owner。

同一公共契约或共享 Foundation 也必须有唯一 Owner，其他 Agent 只能依赖其已确认接口，不能各自实现不同版本。

### 子 Agent 写入边界

推荐默认权限：

| 角色 | 生产代码 | Feature Item 状态 | 验证结果 | 全局状态总览 |
|---|---|---|---|---|
| Coordinator | 必要时 | 可汇总 | 可汇总 | 唯一主要写入者 |
| Source Analyst | 否 | Source/证据部分 | 否 | 否 |
| Target Analyst | 否 | Target Mapping 部分 | 否 | 否 |
| Implementer | 当前 Workstream | 当前 Items | 可记录自测 | 否 |
| Verifier | 默认否 | 验证相关状态 | 是 | 否 |
| Reviewer | 默认否 | 问题/审查结论 | 可记录审查 | 否 |

`00-迁移状态总览.md` 默认由 Coordinator 汇总，避免多个 Agent 同时覆盖全局状态。

模块级文档可以由对应 Workstream Owner 更新，但必须避免两个 Agent 同时编辑同一状态块。

### 多 Workstream 执行状态

启用并行实施后，`05-迁移执行计划.md` 不应假装全局只有一个“当前执行”。可以记录：

```text
Active Workstreams
- WS-001：当前执行
- WS-002：当前执行
- WS-003：验证中
```

每个 Workstream 内仍保持清晰的 Slice Queue 和 Feature Item 状态。

全局层面允许多个“当前执行” Workstream，但**同一 Workstream 内仍避免大量半成品**。

### 并行验证

Verifier 可以和 Implementer 并行：

```text
Implementer A：开发 Feature B
Verifier：验证 Feature A
Source Analyst：分析 Feature C
```

验证 Agent 应依据 Feature Item、Source/Target Behavior、用户规则和验证方式独立检查，不直接因为 Implementer 声称“完成”就判定通过。

### 冲突与降级

如果并行过程中出现：

- 意外共享文件；
- API / 状态模型冲突；
- 两个 Workstream 需要修改同一公共抽象；
- 一个 Workstream 的 Decision 改变另一个的目标行为；
- 合并后测试结果互相影响；

应立即暂停受影响 Workstream，把相关 Item 标记“已阻塞”，由 Coordinator 重新划分 Ownership、拆 Foundation 或调整顺序。

并行策略必须可随时从“多 Workstream”降级回串行，不能为了保持并行度而继续制造冲突。

## 多 Agent 交接

每个 Workstream 结束、暂停或切换 Agent 时，都要独立记录：

- 当前 Feature / Items；
- 已修改文件；
- 当前实施/验证状态；
- 未完成工作；
- 依赖的其他 Workstream；
- 可安全继续的位置；
- 合并前还需完成的验证。

Coordinator 再把这些摘要汇总到全局状态总览。

并行的目的应是利用稳定边界提高吞吐量，不是把尚未理解的迁移问题同时复制给多个 Agent。
