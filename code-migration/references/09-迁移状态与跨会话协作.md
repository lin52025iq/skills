# 09 迁移状态与跨会话协作

## 目标

让长周期迁移可以跨对话、跨 Agent 可靠续接，同时避免状态文档反过来主导迁移。`.code-migration/` 是迁移状态的持久化索引，不是取代代码、测试和已确认 Decision 的另一套真相。

## 默认工作区

复杂或长周期迁移默认写入目标仓库根目录：

```text
<target-repo>/.code-migration/
├── 00-迁移状态总览.md
├── 01-迁移任务上下文.md
├── 02-功能清单.md
├── 03-功能融合映射.md
├── 04-迁移决策记录.md
├── 05-迁移执行计划.md
└── modules/
    └── <module>/
```

只有当某模块具备独立规划、验证、决策或跨会话维护价值时才拆 `modules/<module>/`；不要按源仓库目录树机械拆分。

## 事实源优先级

发生冲突时使用以下优先级：

1. 用户最近一次明确且仍有效的迁移意图；
2. 已确认并记录的 Decision / 目标产品契约；
3. 当前真实代码、Git 状态、Runtime 和测试结果；
4. 当前模块功能清单与执行计划；
5. `00-迁移状态总览.md`。

`00-迁移状态总览.md` 是快速恢复入口和摘要缓存，不得拿过期总览覆盖真实代码或已确认 Decision。

如果高优先级来源之间互相冲突，停止相关 Slice，进入 Reconcile 或 Clarification Loop。

## 功能生命周期

建议使用：

```text
DISCOVERED → DESIGNED → IMPLEMENTING → VERIFYING → MIGRATED → ELIMINATED
```

- `DISCOVERED`：已识别能力，但目标决策尚未完成；
- `DESIGNED`：目标行为和 Target Mapping 已足够明确；
- `IMPLEMENTING`：正在开发，不能视为完成；
- `VERIFYING`：主要实现已完成，但验证 Gate 未完成；
- `MIGRATED`：目标能力已通过迁移 Gate；
- `ELIMINATED`：旧入口、旧实现和临时结构已按计划退出。

`BLOCKED` 是额外标记，不替代生命周期。例如：`IMPLEMENTING + BLOCKED`。

## Session Handoff Gate

以下情况必须同步状态：

- 当前 Slice 通过 Done Gate；
- 准备结束或暂停当前对话；
- 准备切换 Agent / 开启新对话；
- 当前 Slice 被 `MUST_ASK` 阻塞；
- 发现文档与代码/Git 状态不一致。

至少记录：

```text
Overall Goal
Desired Target Behavior
Current Phase / Module / Slice
Lifecycle Status
Last Completed Action
Current Code State
Tests / Validation
NOW / READY / BLOCKED / DEFERRED / DONE
Open Questions + 已回答结论
Uncommitted / Pending Work
Relevant Decisions
Recommended Next Action
Files / Modules To Read First
```

半完成代码必须标为 `IMPLEMENTING` 或 `VERIFYING`，不得因为“文件已经写了”标成 `MIGRATED`。

## 新对话恢复

新 Agent / 新对话：

1. 先读 `.code-migration/00-迁移状态总览.md`；
2. 恢复 Overall Goal、Desired Target Behavior、Current Slice、Decision 和已回答问题；
3. 按索引读取当前模块的功能清单和执行计划；
4. 检查 Git branch、最近相关 commit、working tree 和当前 Slice 实际代码；
5. 若状态一致，从 `Recommended Next Action` 续接；
6. 若不一致，只对当前相关范围执行 Reconcile，不重新扫描所有源项目；
7. 不重复开发 `MIGRATED/DONE` 项，也不重复询问已有答案。

## Reconcile

以下情况标记 `RECONCILE_REQUIRED`：

- 文档声称完成，但代码或测试不支持；
- working tree 存在未说明的半完成修改；
- 最近提交改变了当前 Slice，但状态文档没有更新；
- 无法确认当前代码对应哪个迁移阶段。

Reconcile 只需回答：

```text
哪些已完成？
哪些实现了但未验证？
哪些半完成？
哪些尚未开始？
哪些文档已过期？
下一安全动作是什么？
```

修正状态后再继续写新代码。

## Clarification 持久化

待澄清问题记录：

```text
ID
Question
Type: MUST_ASK / CAN_INFER / CAN_DEFER
Affected Feature / Slice
Status
User Answer / Inference
Related Decision
```

新的对话必须先恢复历史答案，不重复提问。

只有当证据不足且答案会实质改变目标行为或不可逆方向时才使用 `MUST_ASK`。普通命名、文件组织、组件选择以及目标仓库已经有稳定范例的技术细节优先 `CAN_INFER`。

## 版本控制

长期迁移默认应让 `.code-migration/` 与代码一起进入版本控制，除非用户或目标仓库规范明确要求不提交。

开始时检查它是否被 `.gitignore` 忽略；若忽略且迁移需要跨机器、跨开发者或长期续接，应显式处理，而不是假设本地文件能持久存在。

迁移文档提交应与相关代码变更保持可理解的关联，但不要为了每次状态文字变化制造无意义提交。

## 敏感信息

`.code-migration/` 可能进入 Git，因此禁止写入：

- Token / Secret / Password / API Key；
- Cookie、Session、私钥；
- `.env` 的真实值；
- 真实客户或用户敏感数据；
- 不必要的生产 payload 或凭据化 URL。

允许记录环境变量名称、脱敏示例、字段结构、错误类型和必要的非敏感业务语义。

## 多 Agent

默认单一迁移焦点适用于单 Agent。若明确启用多个独立 Workstream：

- 每个模块维护自己的 `NOW` 和执行计划；
- 模块 Agent 只修改自己的模块状态；
- `00-迁移状态总览.md` 记录 `Active Workstreams`，不要假装全局只有一个 Slice；
- 需要一个协调者或明确规则负责汇总跨模块依赖、冲突和全局状态；
- 多 Agent 不得并行修改同一业务能力或同一临时架构而没有 owner。

并行的目的应是利用稳定边界，不是把尚未理解的迁移问题同时复制给多个 Agent。
