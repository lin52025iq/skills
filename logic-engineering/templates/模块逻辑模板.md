> 本模板用于把候选或规范 CLM 投影为人类可读逻辑。不要把模板文本本身当成唯一事实源；正式状态仍以 CLM 语义节点为准。

## 1. 模块

```text
模块名称：

```

## 2. 领域概念

### 实体

```text
实体：订单
标识：domain.order

关键属性：
- 状态：OrderStatus
- 所属用户：UserId
- 应付金额：Money
```

### 枚举 / 值类型

```text
订单状态：
- 待支付
- 已支付
- 已发货
- 已取消
```

## 3. 功能

```text
功能：取消订单
标识：behavior.order.cancel

目的：
允许符合条件的用户取消尚可撤销的订单。
```

### 输入

```text
- 当前用户
- 目标订单
- 取消原因
```

### 前置条件

```text
- 当前用户必须拥有目标订单。
- 订单状态必须属于：待支付、已支付。
```

### 处理过程

```text
1. 将订单状态修改为“已取消”。
2. 保存取消原因。
3. 如果存在已预留库存，则释放库存。
4. 如果存在成功支付，则发起退款。
```

### 状态变化

```text
待支付 → 已取消
已支付 → 已取消
```

### 副作用

```text
- 修改订单状态。
- 可能释放库存。
- 可能调用支付系统创建退款。
```

### 失败情况

```text
- 订单不存在：返回“订单不存在”。
- 当前用户没有权限：返回“无权限”。
- 当前状态不能取消：返回“订单当前不能取消”。
```

### 原子性 / 并发 / 幂等

```text
原子性：
- 订单状态修改和取消原因保存必须全部成功或全部失败。

幂等：
- 重复处理同一个退款请求不能产生多笔退款。
```

### 完成条件

```text
- 订单最终处于“已取消”状态。
```

### 不变量

```text
- 已取消订单不能再次进入发货流程。
```

## 4. 场景

```text
场景：取消待支付订单
标识：scenario.order.cancel.pending_payment

假设：
- 当前用户拥有订单。
- 订单状态为“待支付”。

当：
- 用户执行取消订单。

那么：
- 订单状态变为“已取消”。
```
