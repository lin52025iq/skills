# 自然语言投影与可编辑逻辑规则

本文件定义如何把规范逻辑模型（CLM）稳定地投影为人类可读、可审查、可局部修改的自然语言逻辑。

目标不是生成漂亮文档，而是让不需要阅读源代码的人能够准确理解：系统什么时候执行、为什么执行、修改了什么、失败时怎样处理，以及哪些保证必须始终成立。

## 1. 三层人类视图

同一个 CLM 默认提供三种视图。

### 1.1 业务视图

只展示用户或业务人员最关心的行为：

- 功能目的；
- 允许条件；
- 主要结果；
- 关键失败；
- 核心保证。

不展示事务实现、锁策略、重试机制等技术细节，除非这些内容本身影响业务结果。

### 1.2 逻辑视图

作为默认精确视图，至少包含：

```text
功能
输入
前置条件
处理过程
分支判断
状态变化
失败情况
完成条件
保证 / 不变量
```

用户修改业务行为时优先在这一层工作。

### 1.3 技术逻辑视图

在逻辑视图基础上增加：

```text
读取 / 修改的数据
外部系统调用
事件
事务 / 原子性
并发
幂等
重试
顺序约束
最终一致性
```

仍然不要求展示 Java、Go 等源代码语法。

## 2. 基本投影原则

1. **忠实。** 不增加 CLM 中不存在的规则。
2. **确定。** `all / any / not`、边界比较、顺序、状态变化不能模糊化。
3. **领域优先。** 优先显示“订单”“退款金额”等领域名称，而不是字段变量名。
4. **实现无关。** `@Transactional`、`synchronized`、goroutine 等具体实现先转换成语义要求。
5. **关键未知可见。** 会影响结论的 UNKNOWN 必须展示。
6. **同类逻辑可合并展示，但不能改变底层节点。**

## 3. 条件投影

### 3.1 等值

CLM：

```text
order.status == PAID
```

自然语言：

```text
订单状态必须为“已支付”。
```

### 3.2 集合包含

CLM：

```text
order.status IN [PENDING_PAYMENT, PENDING_SHIPMENT]
```

自然语言：

```text
订单状态必须是以下之一：
- 待支付；
- 待发货。
```

### 3.3 all

CLM 中 `all` 投影必须明确表示“全部满足”。

```text
必须同时满足以下条件：
- 用户已经登录；
- 用户拥有目标订单。
```

### 3.4 any

必须明确表示“任意一个”。

```text
满足以下任意一个条件即可：
- 用户是订单所有者；
- 用户拥有管理员权限。
```

禁止投影成容易被理解为全部满足的普通列表。

### 3.5 not

```text
订单不能处于“已发货”状态。
```

## 4. 边界条件

边界必须完整保留。

```text
amount <= limit
```

必须表达为：

```text
金额不能超过额度；金额等于额度时仍然允许。
```

对于关键金额、数量、时间等边界，建议显式补充边界说明，避免自然语言丢失 `<` 与 `<=` 的区别。

## 5. 行为投影模板

```text
功能：<name>
标识：<semantic id>

目的：
<description>

输入：
- ...

前置条件：
- ...

处理过程：
1. ...
2. ...

分支：
- 当 ... 时：...
- 否则：...

状态变化：
- <before> → <after>

失败情况：
- 当 ... 时，返回/产生 ...

完成条件：
- ...

保证：
- ...
```

只有存在对应逻辑时才显示该部分，不制造空章节。

## 6. 决策展示

简单决策使用自然语言分支。

复杂决策优先生成决策表。

例如：

| 用户类型 | 是否闪购商品 | 是否有优惠券 | 结果 |
|---|---|---|---|
| VIP | 是 | 是 | 优惠券不可使用 |
| VIP | 否 | 是 | 使用优惠券后再应用 VIP 规则 |
| 普通 | 是 | 否 | 使用闪购价 |

决策表只是 CLM Decision/Rule 的投影，不独立维护业务事实。

## 7. 状态机展示

状态规则优先转成状态变化描述：

```text
待支付
├─ 支付成功 → 已支付
└─ 取消订单 → 已取消

已支付
├─ 发货 → 已发货
└─ 取消订单 → 已取消
```

明确禁止的迁移单独展示：

```text
禁止：已发货 → 已取消
```

不要仅因为状态图中没有一条边就推断业务明确禁止该迁移。

## 8. Effect 展示

Effect 按四类组织给人阅读：

```text
读取：系统判断时会使用哪些状态或数据
修改：哪些业务数据会发生变化
外部影响：调用外部系统、发消息、调度任务
一致性要求：原子性、幂等、并发与顺序
```

例如：

```text
外部影响：
- 向支付系统创建退款请求。

幂等要求：
- 同一笔退款请求重复执行时不能产生多次退款。
```

## 9. Primitive 的投影

Primitive 显示其契约，不显示某个目标平台实现。

例如：

```text
原子操作：
订单状态修改和取消原因保存必须全部成功或全部失败。
```

不要显示：

```text
使用 Spring @Transactional。
```

后者只属于目标实现视图。

## 10. 证据与未知

从旧代码导入时，可以附加证据视图：

```text
已确认：代码直接检查了订单状态。
推断：库存释放可能通过事件异步完成。
未知：当前证据无法确认事件失败后的最终处理方式。
```

如果 UNKNOWN 会影响功能主要解释，不能在默认逻辑视图里隐藏。

## 11. 局部可编辑原则

人类视图中的每个可编辑段落必须能映射回一个或多个稳定语义节点。

例如：

```text
允许取消的状态：
- 待支付
- 待发货
```

必须关联：

```text
rule.order.cancel.allowed_status
```

用户添加“待接单”时，系统应生成针对该节点的语义补丁，不重写整个 `behavior.order.cancel`。

## 12. 自由自然语言修改

用户可以提出：

```text
待接单的订单以后也允许取消。
```

Agent 应转换为候选修改：

```text
目标：允许取消的订单状态
修改：新增“待接单”
影响：取消订单规则、状态机相关验证和对应测试
```

然后生成结构化 Semantic Patch。

自由文本不是 canonical CLM 的直接存储格式。

## 13. 公共逻辑展示

如果多个行为引用同一个公共规则，默认只定义一次。

```text
公共规则：订单操作权限

必须同时满足：
- 当前用户已经登录；
- 当前用户拥有目标订单。
```

具体行为：

```text
取消订单的前置条件：
- 满足“订单操作权限”；
- 订单状态允许取消。
```

避免把公共规则复制到多个功能后产生自然语言漂移。

## 14. 修改前后的语义差异

优先输出 Semantic Diff，不输出源码 Diff。

例如：

```text
变更：允许取消的订单状态

新增：
+ 待接单

保持不变：
- 待支付
- 待发货
```

如果变更涉及行为语义：

```text
行为变化：是
影响范围：取消订单、订单状态验证、相关场景测试
```

## 15. 禁止的自然语言压缩

以下优化会改变精度，禁止：

- 把“全部满足”缩写成不明确的条件列表；
- 删除边界值信息；
- 把“可能发生”写成“一定发生”；
- 把异步最终结果写成同步立即结果；
- 把原子性要求写成普通顺序步骤；
- 把 ASSUMED / UNKNOWN 写成已确认规则；
- 为了表达更流畅而重排有副作用依赖的步骤。

## 16. 投影一致性检查

生成自然语言后至少自检：

```text
所有关键 Rule 是否出现
all/any/not 是否保持
比较边界是否保持
关键状态变化是否保持
Effect 是否遗漏
Failure 是否遗漏
Constraint 是否遗漏
UNKNOWN 是否按风险展示
是否引入 CLM 中不存在的新规则
```

自然语言只是一种视图；发现冲突时以 CLM 为准，并修正投影，而不是反向静默修改 CLM。
