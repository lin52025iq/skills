# 旧代码逻辑导入流程 v0.1

本流程用于把现有项目中的某个模块、功能点或业务流程，从具体编程语言实现逆向重建为候选规范逻辑模型（Candidate CLM）。

目标不是“总结代码”，而是恢复：

- 这个功能从哪里开始；
- 在什么条件下执行；
- 会经过哪些关键业务步骤；
- 会读取和修改哪些状态；
- 会产生哪些外部副作用；
- 有哪些失败、重试、并发、事务和时序语义；
- 哪些事实可以被代码直接证明，哪些只是推断或未知。

## 1. 输入

至少提供以下一种：

- 模块名；
- 功能名；
- API / 路由；
- 类、函数或方法；
- 事件或消息；
- 用户行为描述；
- 一个待解释的业务问题。

如果只给业务描述，先定位可能入口；如果入口存在多个候选，保留候选并继续用证据缩小范围。

## 2. 探索状态

整个导入过程持续维护：

```yaml
exploration_state:
  target: "解释订单取消逻辑"
  completed_nodes: []
  frontier: []
  open_questions: []
  hypotheses: []
  contradictions: []
  unresolved_dynamic_edges: []
  evidence: []
```

不要依赖临时自然语言记忆代替结构化状态。

## 3. 第一阶段：定位入口

优先寻找：

- Controller / Handler / Resolver / Command；
- 对外 API；
- 消息消费者；
- 定时任务；
- UI 触发对应的后端入口；
- 领域服务公开方法；
- 测试中明确调用的业务入口。

入口定位后先记录“当前已知”和“仍未知”，不要马上一路向下展开。

## 4. 第二阶段：发现逻辑骨架

先扫描入口的一到两层主要关系，形成骨架：

```text
入口
├─ 权限检查
├─ 业务校验
├─ 核心服务
├─ 持久化
└─ 事件 / 外部调用
```

对每个候选节点标记：

```text
关键
重要
辅助
可忽略
```

判断依据：

- 与用户问题的相关度；
- 是否改变业务结果；
- 是否修改状态；
- 是否引入外部副作用；
- 是否决定分支；
- 是否能解决关键未知问题。

## 5. 第三阶段：按重要性展开

优先读取：

1. 能关闭关键开放问题的节点；
2. 会改变状态的节点；
3. 有业务规则和判断的节点；
4. 事件、消息、异步任务和回调；
5. 权限、事务、幂等、并发、重试；
6. 动态分派、配置驱动和策略选择。

通常不深入：

- 日志；
- 普通 DTO / VO 映射；
- 简单 getter/setter；
- 不改变语义的包装方法；
- 标准库内部；
- 明确与目标问题无关的框架实现。

## 6. 开放问题

建议把大问题拆成可关闭的小问题。例如“订单取消到底怎么实现”：

```text
Q1 入口在哪里？
Q2 哪些订单允许取消？
Q3 权限如何判断？
Q4 状态在哪里真正修改？
Q5 是否释放库存？何时释放？
Q6 已支付订单是否退款？
Q7 哪些操作在同一个事务里？
Q8 失败后是否重试？
Q9 是否存在异步事件？
Q10 是否存在状态迁移漏洞？
```

每次继续搜索前先选择一个要关闭的问题。

## 7. 节点摘要

读取关键实现后，把源码压缩为逻辑节点摘要：

```yaml
semantic_id: candidate.behavior.order.cancel
责任: 取消订单
输入:
  - 当前用户
  - 订单
前置条件:
  - 用户拥有订单
  - 状态允许取消
状态读取:
  - order.status
状态写入:
  - order.status = CANCELLED
副作用:
  - 释放库存
  - 必要时发起退款
关键依赖:
  - inventory.release
  - payment.refund
证据:
  - src/order/service.xxx:80-130
置信度: high
```

不要在摘要里保留与目标无关的大段实现细节。

## 8. 动态关系

遇到接口、依赖注入、反射、工厂、策略、事件总线等动态调用时，不能直接假设真实目标。

记录：

```yaml
relation:
  source: payment.execute
  target: PaymentProcessor.*
  resolution: dynamic
  candidates:
    - StripeProcessor
    - PaypalProcessor
  resolved_by:
    - factory configuration
  status: unresolved
```

继续寻找配置、注册表、注解、工厂或运行时条件，直到关系被标记为：

```text
已解析
高概率
未解析
```

## 9. 证据等级

所有候选逻辑必须标记来源：

### 已观察

代码直接证明。

### 推断

多个已观察事实组合得到。

### 假设

依赖框架常识、命名或运行时行为，但当前未验证。

### 未知

现有代码范围内无法确定。

只有“已观察”和有充分证据支持的“推断”适合进入候选 CLM 主路径。

## 10. 已观察行为与期望逻辑

旧代码可能本身有缺陷，因此必须分开保存：

```text
已观察行为模型
= 代码现在实际上做什么

期望逻辑模型
= 人确认系统应该做什么
```

例如：

```text
已观察：已发货订单仍可进入已取消状态。
期望：已发货订单禁止取消。
```

这种差异应输出为“行为差异 / 潜在缺陷”，不能在导入阶段直接抹掉。

## 11. 上下文压缩

大型模块使用四层信息：

```text
L0 源代码证据
L1 单节点逻辑摘要
L2 子流程摘要
L3 候选 CLM
```

压缩时必须保留证据指针，后续如果发现冲突可以重新读取原始源码。

## 12. 停止条件

当满足以下条件时，可以停止主要探索：

- 关键开放问题已经解决；
- 主执行路径闭合；
- 关键状态变化已明确；
- 主要副作用已明确；
- 关键失败路径已明确；
- 事务、幂等、并发、事件等会改变解释的重要语义已明确；
- 剩余未解析依赖不会大概率改变当前结论。

如果达到资源预算但仍未完整，必须明确输出：

```text
已确认
仍未知
当前假设
下一步最值得继续调查的位置
```

## 13. 导入产出

最低产出：

```text
候选 CLM
人类可读逻辑
证据映射
开放问题 / 未知项
潜在逻辑问题
```

复杂模块可以额外生成：

```text
状态机
决策表
数据流
事件流
事务边界图
公共逻辑候选
```

## 14. 禁止行为

- 不把当前文件当成模块全貌；
- 不逐行翻译代码冒充逻辑重建；
- 不因为函数名像某个业务动作就直接认定其语义；
- 不把日志、框架胶水等噪声塞进 CLM；
- 不把推断或假设写成确定业务规则；
- 不在“恢复现状”阶段自动修复观察到的问题。
