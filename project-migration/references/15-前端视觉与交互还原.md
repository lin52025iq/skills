# 前端视觉与交互还原

## 一、前端迁移不是“组件能渲染”

前端迁移至少同时迁移六类可观察契约：

1. **功能契约**：用户能够完成什么；
2. **导航契约**：页面、路由、菜单、Tab、深链如何到达；
3. **状态契约**：加载、空、错误、禁用、选择、展开、编辑等状态如何表现；
4. **交互契约**：点击、输入、键盘、滚动、拖拽、弹层、反馈如何工作；
5. **视觉契约**：布局、尺寸、间距、字体、颜色、边框、阴影、图标、图片和层级；
6. **响应式契约**：不同 viewport、设备和内容长度下如何重新排列、隐藏和滚动。

如果用户没有明确批准 redesign，默认目标是：

> **内部实现允许目标原生重建，但用户看到和使用的页面应跟随源项目现役界面进行对齐。**

不能用“新框架写法更合理”“目标项目设计系统不同”作为未经批准改变页面外观和交互的理由。

---

## 二、先确认页面生命周期，再建立视觉基线

视觉还原只针对生命周期明确的功能和页面。

先读取 `references/14-功能生命周期与废弃识别.md`，把页面 / 功能区分为：

- Active；
- Conditional；
- Hidden；
- Disabled；
- Deprecated；
- Removed；
- Unknown。

Deprecated / Removed 的旧 UI 默认不进入视觉迁移范围。

Conditional 页面必须记录其权限、Flag、租户、地区、数据状态或 viewport 条件，避免因为当前环境看不到就漏迁。

---

## 三、页面发现不能只看路由文件

前端源研究至少检查：

- Router 配置；
- 菜单、侧边栏、顶部导航；
- Tab 和二级导航；
- 页面内部链接；
- deep link；
- redirect；
- route guard；
- permission route；
- micro-frontend registration；
- 动态 import / lazy page；
- modal / drawer / popover 触发入口；
- 页面中被条件渲染的功能区；
- 被注释或隐藏的历史入口。

一个组件文件存在，不代表它是现役页面；一个页面没有菜单入口，也不代表它不可通过 deep link 或业务流程触达。

---

## 四、建立页面视觉基线

使用 `templates/10-前端视觉基线.md`。

每个关键页面记录至少以下内容。

### 4.1 页面框架

- viewport / 主要断点；
- 全局 Header / Sidebar / Footer；
- 页面最大宽度与最小宽度；
- 主内容区定位；
- 页面内滚动与浏览器滚动谁负责；
- sticky / fixed 区域；
- z-index 层级；
- safe area / mobile viewport 行为。

### 4.2 布局结构

不要只记录“使用 Flex”。要记录用户可观察的布局约束：

- 横向 / 纵向排列；
- 列数；
- 主次区域比例；
- `gap` / margin / padding；
- min/max width；
- 内容撑开还是固定尺寸；
- overflow；
- wrap；
- 对齐方式；
- 卡片 / 表格 / 表单的排列规律；
- breakpoint 下哪些区域重新排列、折叠或隐藏。

### 4.3 视觉样式

记录：

- 字体家族；
- 字号 / 行高 / 字重；
- 文本颜色；
- 背景色；
- 边框；
- 圆角；
- 阴影；
- 图标尺寸和位置；
- 图片比例与裁剪；
- 控件高度；
- Design Token；
- theme / dark mode；
- CSS variable；
- 资源文件来源。

目标项目可以使用不同 CSS 技术实现，但最终视觉契约不能因此漂移。

---

## 五、必须建立 UI 状态矩阵

前端页面不是一张静态截图。

对关键页面 / 组件至少检查适用的状态：

```text
默认
Loading / Skeleton
Empty
Error
Partial Data
Disabled
Read-only
Hover
Focus / Focus-visible
Active / Pressed
Selected
Expanded / Collapsed
Editing
Validation Error
Submitting
Success Feedback
Modal / Drawer Open
Toast / Notification
Permission Denied
Offline / Timeout
Long Content / Overflow
```

不要只迁“数据加载成功”的 happy path。

每个状态都应记录：

- 如何触发；
- 源页面如何展示；
- 交互是否可用；
- 是否产生布局变化；
- 是否需要视觉基线或自动化验证。

Storybook 的视觉测试实践同样强调用不同 story 表达不同组件状态，再与已确认基线比较；因此本 Skill 把“状态矩阵”作为视觉迁移的基础，而不是只截默认页面。

---

## 六、响应式必须按真实行为迁移

检查源项目：

- CSS media query；
- Tailwind breakpoint；
- JS viewport 判断；
- responsive props；
- container query；
- mobile-only / desktop-only class；
- responsive table / card；
- breakpoint 下的菜单形态；
- 横竖屏行为。

不要假设：

> “桌面页面迁好以后让 CSS 自己适配手机。”

对于每个关键页面，至少选择项目真实支持的代表 viewport 建立基线。

如果源项目没有明确支持某种 viewport，不擅自扩展为 redesign 任务。

---

## 七、样式迁移：保持视觉，不复制旧 CSS 架构

这里与目标原生 Rebuild 的原则并不冲突。

允许变化：

- Sass → CSS Modules；
- Less → Tailwind；
- styled-components → CSS / CSS-in-JS；
- 全局 class → scoped style；
- 老旧 clearfix / float → Grid / Flex；
- 重复 magic number → Design Token；
- 老组件库 → 目标项目已有组件库。

但是必须证明：

- 页面布局没有无意变化；
- 间距和尺寸符合源基线或批准的新规范；
- 字体和图标没有漂移；
- 响应式行为一致；
- 交互状态一致；
- 替换组件库没有改变用户可观察语义。

目标代码可以彻底重写 CSS 结构，视觉结果仍需对齐。

---

## 八、组件库与 Design System 的处理

目标项目已有稳定 Design System 时，优先复用，但不能只因为组件名字相同就认为视觉等价。

例如源项目 `Button` 与目标项目 `Button` 仍要比较：

- 高度；
- padding；
- 字体；
- icon gap；
- hover / focus / disabled；
- loading；
- border radius；
- danger / primary / secondary；
- mobile behavior。

如果目标 Design System 与源页面存在批准之外的明显差异，需要：

- 适配；或
- 记录为行为 / 视觉差异并确认；

而不是静默接受。

---

## 九、交互还原

对每个页面主要用户流程记录：

```text
用户动作
→ UI 立即反馈
→ 状态变化
→ 请求 / 本地操作
→ 成功反馈
→ 失败反馈
→ 最终页面状态
```

检查：

- debounce / throttle；
- optimistic update；
- form validation 时机；
- submit 防重复；
- modal close 规则；
- unsaved changes；
- pagination / infinite scroll；
- scroll restore；
- focus restore；
- keyboard shortcut；
- drag/drop；
- transition / animation 是否具有功能含义。

不要只保证 API 被调用，还要保证用户体验状态机一致。

---

## 十、视觉验证协议

对于要求“跟随原项目对齐”的页面，必须建立视觉裁判。

推荐优先级：

1. 源项目可运行页面的真实截图基线；
2. 源项目 Storybook / 组件示例；
3. 产品截图 / 设计稿；
4. CSS / DOM / 组件结构作为补充证据。

验证时尽量固定：

- browser；
- OS / rendering environment；
- viewport；
- device scale；
- 字体；
- locale；
- theme；
- 数据 fixture；
- 时间 / 随机数据；
- animation / transition；
- 网络响应。

Playwright 的截图比较要求基线与比较尽量运行在一致环境，因为 OS、浏览器版本、字体等都会影响像素结果。因此不要在不一致环境下把像素差异直接判断为页面迁移错误。

### 10.1 页面级截图

适合检查：

- page shell；
- layout；
- sidebar；
- header；
- table / list；
- responsive behavior。

### 10.2 组件级截图

适合检查：

- button / field；
- card；
- dialog；
- dropdown；
- complex widget；
- loading / empty / error 等状态。

### 10.3 差异处理

视觉差异必须分类：

- **必须修复**：非预期视觉回归；
- **批准差异**：目标设计明确变化；
- **环境噪声**：字体 / rendering / animation 等；
- **未知**：需要人工确认。

不要为了让截图测试通过随意扩大 diff threshold。

---

## 十一、可访问性属于前端迁移契约

至少检查：

- 语义 HTML；
- label / name；
- keyboard navigation；
- focus order；
- focus-visible；
- dialog focus trap / restore；
- ARIA；
- button / link 语义；
- error announcement；
- color contrast；
- zoom / text resize；
- reduced motion（如果源项目或目标规范要求）。

允许在不破坏业务和视觉要求的情况下改进明显可访问性问题，但重要行为变化仍需记录。

---

## 十二、前端资源与平台行为

不要漏掉：

- icon / SVG；
- image / sprite；
- webfont；
- favicon；
- manifest；
- CSS reset；
- global style；
- theme；
- locale / i18n；
- date / number formatting；
- analytics；
- feature exposure 埋点；
- SEO / metadata；
- SSR / hydration；
- CSP / asset host；
- public path；
- code splitting；
- preload / prefetch。

它们可能不是业务逻辑，却直接影响页面展示或运行。

---

## 十三、前端迁移 Workstream 推荐

大项目可拆为：

```text
WS-FE-01 路由 / 导航 / 功能生命周期研究
WS-FE-02 页面功能与状态研究
WS-FE-03 视觉基线与 Design Token
WS-FE-04 数据访问 / API / 状态管理
WS-FE-05 页面组 A Rebuild
WS-FE-06 页面组 B Rebuild
WS-FE-07 响应式与交互验证
WS-FE-08 视觉回归 / Accessibility Review
```

不要按 `components/`、`pages/`、`utils/` 目录平均分 Agent。

---

## 十四、前端完成 Gate

前端迁移不能仅以“build 通过”和“接口能调用”结束。

至少确认：

- 现役 / 条件现役功能生命周期已确认；
- Deprecated / Removed UI 没有被错误恢复；
- 页面、路由、导航和权限可达性一致；
- 关键页面功能完整；
- 关键 UI 状态完整；
- 页面布局与视觉基线符合要求；
- 代表 viewport 的响应式行为符合要求；
- 交互反馈和错误状态符合要求；
- 字体、图标、资源和主题无明显漂移；
- 目标实现遵循目标前端项目的组件、状态、样式和测试惯例；
- 不存在明显源框架结构复制；
- 视觉差异已有修复或批准记录；
- Accessibility 阻断问题已处理；
- 关键页面完成视觉与交互验证。
