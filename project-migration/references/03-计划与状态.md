# 迁移计划与状态管理

## 一、为什么必须显式维护状态

系统迁移通常跨越多个会话、多个提交和多个参与者。只依赖对话上下文容易导致重复分析、旧结论与代码脱节、风险遗忘和范围失控。

因此关键状态写入 `.migration/`。

## 二、当前状态至少记录

- 当前阶段；
- 当前任务或批次；
- 已完成任务；
- 阻塞项；
- 高风险未知项；
- 未关闭行为差异；
- 失败队列；
- 迁移规则是否稳定；
- 本次必须处理设计问题的完成情况；
- 最近验证结果；
- 下一步动作；
- 是否允许扩大迁移范围；
- 是否允许切换。

状态是继续工作的最小事实，不是日报。

## 三、任务拆分原则

良好任务应：

- 单一明确目标；
- 能追踪到源能力或业务规则；
- 依赖关系明确；
- 修改范围可控制；
- 设计改进边界明确；
- 验收条件可执行；
- 完成后形成独立进展；
- 失败后容易回退。

不要创建：

```text
迁移订单模块全部代码
```

更好的拆分：

```text
MIG-001 建立订单核心领域语义
MIG-002 建立目标项目风格的订单仓储边界
MIG-003 实现创建订单主流程并消除源 God Service 中的跨层依赖
MIG-004 建立创建订单公共契约验证
MIG-005 实现取消规则
MIG-006 迁移订单过期任务
MIG-007 接入订单创建事件
```

## 四、按依赖顺序，不按文件顺序

常见顺序仅供参考：

```text
契约和领域语义
→ 稳定边界
→ 数据访问
→ 核心规则
→ 应用编排
→ 外部集成
→ 接口入口
→ 异步任务
→ 灰度和兼容逻辑
```

实际项目可以调整，但要解释依赖关系。

## 五、先规划试迁移，再规划批量迁移

跨技术栈、重设计或高风险迁移，把计划分为：

1. **试迁移批次**：验证规则、目标设计和裁判；
2. **正式批次**：试迁移通过后才展开；
3. **切换批次**：专门处理灰度、数据权威和临时设施；
4. **清理批次**：删除旧实现和迁移态结构。

试迁移任务不是正式完成进度，可以在验证后全部丢弃。

## 六、任务描述标准

每个任务至少包含：

```text
编号
目标
批次类型
来源能力
关联业务规则
关联技术迁移规则
关联设计改进项
前置依赖
来源证据
修改范围
明确不做
验收条件
验证方式
风险
回退方式
```

设计改进不能用“顺手重构”描述，必须引用具体问题和目标决策。

## 七、计划允许被事实推翻

出现新业务规则、新依赖、新数据所有者、目标已有能力、技术语义不等价、设计假设不成立或验证方案不可行时，应更新理解、边界、规则或计划，再继续编码。

## 八、重复失败要回到上游

同类失败反复出现时：

1. 暂停同类任务；
2. 将失败写入 `.migration/差异与失败队列.md`；
3. 判断问题来自源理解、目标架构、迁移规则、设计规则还是任务拆分；
4. 修正上游产物；
5. 找出所有受影响的已完成任务；
6. 重新验证。

不要让一个错误规则被复制到后续几十个任务。

## 九、任务结束条件

不能因为代码写完就标记完成。

至少需要：

- 目标实现完成；
- 对应验证完成；
- 相关能力矩阵更新；
- 相关业务规则台账更新；
- 相关设计改进台账更新；
- 新风险、未知和差异已记录；
- 没有遗留未解释失败。

实现完成但验证未完成，状态只能是“已实现，待验证”。

## 十、进度必须有分母

优先记录：

- 关键能力：已验证 / 需要迁移；
- 高优先级规则：已验证 / 总数；
- 必须改设计项：已关闭 / 总数；
- 未关闭差异：数量；
- 阻断未知项：数量；
- 失败队列：数量；
- 正式任务：已完成 / 总数。

分母尚未盘点完成时明确写“未知”，不要制造精确百分比。
