# 迁移计划与状态管理

## 一、为什么必须显式维护状态

系统迁移通常跨越多个会话、多个提交和多个参与者。只依赖对话上下文容易产生：

- 重复分析；
- 旧结论与实际代码脱节；
- 已知风险被遗忘；
- 迁移任务越做越大；
- 无法判断整体完成度。

因此应把关键状态写入 `.migration/`。

## 二、迁移状态应该记录什么

至少记录：

- 当前阶段；
- 已完成阶段；
- 当前任务；
- 已完成任务；
- 阻塞项；
- 高风险未知项；
- 待验证差异；
- 下一步动作；
- 最近一次验证结果；
- 当前是否允许切换。

状态是事实记录，不是日报。只保留对继续迁移有用的信息。

## 三、任务拆分原则

一个良好的迁移任务应满足：

- 单一明确目标；
- 有可追踪的源能力或业务规则；
- 依赖关系明确；
- 修改范围可控制；
- 验收条件可执行；
- 完成后能够形成独立进展；
- 失败后容易回退。

不要创建：

```text
任务：迁移订单模块全部代码
```

更好的拆分：

```text
MIG-001 建立订单状态和核心领域类型
MIG-002 建立订单仓储接口和查询能力
MIG-003 实现创建订单主流程
MIG-004 建立创建订单契约测试
MIG-005 实现订单取消规则
MIG-006 迁移订单过期任务
MIG-007 接入订单创建事件
```

## 四、按依赖顺序，而不是按文件顺序

应先识别依赖图。

常见顺序仅供参考：

```text
契约和领域语义
→ 稳定的基础接口
→ 数据访问
→ 核心领域规则
→ 应用编排
→ 外部集成
→ 接口入口
→ 异步任务
→ 灰度和兼容逻辑
```

实际项目中允许调整，但必须解释依赖关系。

## 五、任务描述标准

每个任务应包含：

```text
编号：MIG-004
目标：迁移创建订单用例。
来源能力：CAP-001 创建订单。
关联规则：BR-001、BR-004、BR-007。
前置依赖：MIG-001、MIG-002。
修改范围：目标项目订单应用层、仓储适配层和对应测试。
明确不做：不迁移支付回调；不改变公开接口字段。
验收：既有创建订单契约全部通过；重复请求行为与源系统一致。
风险：目标数据库唯一约束与源系统不同。
回退：保留旧接口路由，目标入口可由特性开关关闭。
```

## 六、计划允许被事实推翻

迁移计划不是不可修改的合同。

当实施中发现：

- 新业务规则；
- 新依赖；
- 新数据所有者；
- 目标已有可复用能力；
- 技术栈语义不等价；
- 验证方案不可行；

应先更新理解、边界或计划，再继续编码。

禁止为了“按计划完成”而忽略新事实。

## 七、迁移任务的结束条件

一个任务不能因为代码已经写完就标记完成。

至少需要：

- 目标实现完成；
- 对应测试或其他验证完成；
- 相关能力矩阵更新；
- 相关业务规则台账更新；
- 新风险和未知项已记录；
- 没有遗留未解释失败。

如果实现完成但验证尚未完成，状态应为“已实现，待验证”，不能记为完成。
