# 前端迁移执行协议

本文把主 Skill 的原则落成可重复执行的代理协议。只在需要确定工作模式、范围、证据、产物、进度或失败恢复时读取。

## 目录

1. 请求分类
2. 范围与风险分级
3. 只读接入协议
4. 证据账本
5. 工作区 profile
6. 计划与实施循环
7. 进度与交接

## 1. 请求分类

### 1.1 评估模式

适用于“先看看能不能迁”“评估风险”“给方案但不要改代码”。

执行边界：

- 只读检查源、目标、Git、CI、依赖和运行基线；
- 可以创建迁移报告，除非用户连文档也不希望写入；
- 不修改产品代码、锁文件、依赖或配置；
- 输出可行性、范围、策略候选、阻断项和下一步。

### 1.2 规划模式

适用于“制定迁移计划”“拆任务”“设计目标架构”。

至少产出：

- 范围和不迁移项；
- 功能生命周期与关键页面状态；
- 目标项目画像与范例；
- 迁移策略、切片、依赖图；
- 验证矩阵、回滚和清理条件。

不要写出“把 A 文件转成 B 文件”的文件翻译计划。

### 1.3 实施模式

适用于“开始迁移”“直接改代码”“完成这个页面”。

实施前必须具备最小可执行输入：

- 源行为或预期行为；
- 目标落点；
- 允许变化；
- 最近层级验证命令；
- 失败时的恢复方式。

信息不完整时不要停在提问。先完成可安全执行的只读侦察、建立假设和最小试迁移，再把真正影响行为的未知项列为阻断。

### 1.4 审查模式

适用于“看看迁得对不对”“review 这个迁移 PR”。

审查顺序：

1. 生命周期遗漏或错误恢复；
2. 功能、权限、导航和数据语义回归；
3. 视觉、响应式和交互回归；
4. SSR/hydration、runtime、Accessibility 与性能风险；
5. 源框架 Copy-Smell 和目标项目惯例偏离；
6. 测试、切流、回滚和清理缺口。

先报告可操作问题，按严重度排序，并引用文件、Route、测试或截图证据。不要用长篇总结埋住问题。

### 1.5 救援模式

适用于迁移反复失败、批次越做越慢、目标代码结构失控或发布不敢切流。

先定位问题属于哪一层：

```text
源功能理解
→ 生命周期判断
→ 迁移边界
→ 目标架构
→ 技术栈规则
→ 任务拆分
→ 实现
→ 验证裁判
→ 切流/运行环境
```

修正最上游的错误层，再重做受影响切片。不要只继续修当前报错。

## 2. 范围与风险分级

### 2.1 范围级别

| 级别 | 判断信号 | 默认 profile |
|---|---|---|
| Component | 无独立 Route；依赖和状态局部 | 对话内或 `small` |
| Page | 一个或少量 Route；有数据与页面状态 | `small` |
| Feature/Module | 多 Route、共享状态、权限或数据层 | `standard` |
| Application | Router、构建、SSR、运行时或整仓变化 | `full` |

### 2.2 风险维度

分别给每项标记 `低 / 中 / 高 / 未知`：

- 用户影响与流量；
- 写操作、支付、身份、权限或敏感数据；
- Route、Deep Link 与 SEO；
- SSR、hydration、缓存与边缘运行时；
- 共享状态、组件库、Theme、Token 和全局 CSS；
- 外部 API 与数据契约；
- 现有自动化测试与可运行性；
- 视觉和响应式复杂度；
- 回滚和新旧共存能力；
- 团队并行与共享文件冲突。

任一关键维度为“高”或“未知”时，不选择只依赖一次性发布的策略，除非边界极小且回滚已演练。

### 2.3 迁移单位

迁移单位应满足：

- 有清晰用户入口或调用入口；
- 能描述可观察结果；
- 能独立验证；
- 能决定新旧实现的路由或所有权；
- 失败时有有限影响面。

好的单位：`订单列表页面及筛选/分页`、`登录与会话恢复`、`账户设置表单`。

不好的单位：`components/`、`utils.ts`、`迁移 30 个 Vue 文件`。

## 3. 只读接入协议

### 3.1 仓库指令

按从根到目标目录的顺序读取：

```text
AGENTS.md / CLAUDE.md / CONTRIBUTING.md
README 与开发文档
package.json / workspace 配置
CI、lint、format、test 配置
目标目录附近的局部说明
```

若规则冲突，离被修改文件更近的局部规则优先，但不得违反用户和系统级约束。

### 3.2 Git 基线

记录：

- 当前分支、HEAD、工作树是否干净；
- 已有用户修改；
- 源和目标是否同仓、不同 package 或不同仓库；
- 是否已有迁移分支或 PR；
- 哪些生成文件或锁文件不应随意变化。

不得使用 `reset --hard`、无差别 checkout、全仓格式化或删除未跟踪文件来“清理环境”。

### 3.3 工程基线

优先运行仓库已有命令，不发明另一套工具链：

1. 使用锁文件对应的 package manager；
2. 读取 `package.json` scripts；
3. 优先已有 `build`、`typecheck`、`lint`、`test`、`e2e`、`storybook`；
4. 记录命令、退出码和关键失败；
5. 将原有失败标成 baseline，不静默忽略。

若依赖未安装，先判断仓库惯例和网络条件。不要仅为盘点安装新依赖或改锁文件。

### 3.4 静态盘点

运行 `scripts/frontend_inventory.py`，再人工核查它给出的候选路径。盘点脚本不能证明功能现役，也不能理解动态 Route、运行时 Flag 或业务权限。

### 3.5 运行侦察

应用可运行时：

- 使用固定账号、fixture、locale、theme、viewport；
- 等待页面稳定后再读取 DOM 或截图；
- 记录 console error、failed request、redirect 和 hydration warning；
- 对关键流程采集成功、失败、空状态和权限路径；
- 避免在真实生产环境执行有副作用操作，除非用户明确授权并有安全数据。

应用不可运行时：

- 记录失败原因和尝试过的命令；
- 使用 Storybook、测试、设计稿、代码和历史截图形成降级基线；
- 将视觉和交互结论标记为较低证据等级。

## 4. 证据账本

每个关键结论采用以下最小结构：

| 字段 | 含义 |
|---|---|
| ID | `CAP-*`、`LIFE-*`、`VIS-*`、`RULE-*`、`DIFF-*` |
| 结论 | 需要保持、改变、淘汰或继续验证的事实 |
| 证据等级 | E3 / E2 / E1 / E0 |
| 证据位置 | Route、文件、测试、截图、日志或设计稿 |
| 决策 | 迁移 / 适配 / 不迁移 / 待确认 |
| 验证 | 如何证明目标结果 |
| Owner | 谁关闭该项 |

### 4.1 冲突证据

例如 UI 中看不到入口，但 Route 仍可直接访问：

- 不要直接判定 Removed；
- 记录导航、Route、Flag、权限和调用证据；
- 分类为 `Hidden`、`Conditional` 或 `Unknown`；
- 用真实账号或配置验证可达性。

### 4.2 疑似源缺陷

源行为看起来是 bug 时：

1. 记录源实际行为；
2. 说明为什么可疑；
3. 查测试、需求、issue 或用户依据；
4. 将目标差异标为“待批准”或“批准变化”；
5. 不通过“顺便修了”隐藏产品变化。

## 5. 工作区 profile

### 5.1 Small

适合单页面或短周期迁移。通常保留：

- 迁移上下文；
- 当前状态；
- 功能文档；
- 前端视觉基线；
- 目标项目画像；
- 目标实现蓝图；
- 验证报告。

### 5.2 Standard

适合多页面或模块，增加：

- 功能生命周期；
- 迁移语义规格；
- 能力迁移矩阵；
- 迁移边界；
- 技术栈规则；
- 迁移计划；
- 差异与失败队列；
- 切换与回滚。

### 5.3 Full

适合整应用或长期并行迁移，复制全部模板并启用 Workstream、fixtures、results 和 scripts 子目录。

### 5.4 工作区约束

- `.migration/` 根目录保存事实、决策和状态；
- 可执行脚本放 `.migration/scripts/`；
- 测试数据放 `.migration/fixtures/`；
- 截图和机器结果放 `.migration/results/`；
- 不在文档中保存 token、cookie、私钥、完整生产数据或未脱敏请求；
- 同一事实只保留一个权威位置，其他文档链接引用。

## 6. 计划与实施循环

### 6.1 切片模板

每个切片至少说明：

```text
用户能力：
源入口与证据：
生命周期：
目标 Route/组件/状态落点：
复用的目标范例：
依赖与共存方式：
允许差异：
功能裁判：
视觉/交互裁判：
最近层级验证命令：
回滚动作：
完成条件：
```

### 6.2 实施顺序

通常按以下顺序降低返工：

1. 契约、类型、adapter 和测试 fixture；
2. 数据读取与错误映射；
3. 页面骨架和主要状态；
4. 用户交互与写操作；
5. 响应式、Accessibility 和视觉细节；
6. Route/Flag 接入；
7. old/new 对照和切流；
8. 旧代码、兼容层和依赖清理。

具体项目惯例优先于此通用顺序。

### 6.3 每次修改后的最小验证

从快到慢：

```text
受影响文件静态检查
→ 相关 typecheck/lint
→ 相关 unit/component test
→ 相关页面/E2E
→ visual/a11y/runtime
→ 更大范围回归
```

不要等全部页面迁完才第一次运行目标应用。

## 7. 进度与交接

阶段报告保持可继续执行：

```markdown
### 当前阶段与 Gate
### 已确认事实与证据
### 本轮修改
### 已运行验证及结果
### 差异、Unknown 与阻断
### 下一安全切片
```

多 Agent 交接必须包含：

- 基线 commit/branch；
- 允许写入的路径；
- 不允许修改的共享边界；
- 输入文档版本；
- 验收命令；
- 产生的 fixtures、截图和差异；
- 未解决风险。

## 8. 失败恢复

### 8.1 基线失败

如果迁移前已有失败：

- 重跑确认可复现；
- 缩小到源/目标/环境问题；
- 记录为 baseline；
- 选择能区分新增回归的局部裁判；
- 基线影响核心路径时，暂停切流但可继续只读研究或独立切片。

### 8.2 同类失败重复

当多个切片出现相同问题：

```text
停止复制修复
→ 找共同生成原因
→ 更新规则或蓝图
→ 标记受影响切片
→ 用一个切片验证新规则
→ 再恢复批次
```

常见共同原因：

- 源状态所有权理解错误；
- 把 server state 搬进全局 client store；
- 目标组件库默认交互与源行为不同；
- SSR/client 边界混淆；
- CSS reset、字体或容器宽度造成全局视觉漂移；
- 任务按源文件拆分导致重复 adapter 和状态。

### 8.3 无法建立视觉基线

- 固定数据、字体、动画、timezone、locale、theme、viewport；
- 使用 component/Storybook 级截图缩小噪声；
- 将像素比较降级为结构与关键属性断言，但标记风险；
- 视觉敏感发布需要人工批准，不得假装自动化已经覆盖。

### 8.4 目标架构失控

出现第二套 Router、API Client、状态库、Token 或错误体系时，暂停实现并检查：

- 是否忽略目标项目范例；
- 是否错误复制源抽象；
- 是否需要短期 adapter 而不是永久新体系；
- 兼容层是否有删除条件；
- 当前任务是否超出迁移边界。
