# 自动化盘点与迁移证据

重复事实应由确定性工具收集，产品语义和取舍由 Agent 结合证据判断。本文件说明如何建立可复现的前端迁移基线。

## 1. 先锁定真实 before state

执行任何安装、Codemod 或配置修改前记录：

```bash
git status --short
git rev-parse HEAD
git branch --show-current
git diff --stat
git diff -- package.json pnpm-lock.yaml yarn.lock package-lock.json bun.lock bun.lockb
```

同时保存：

- Node / Bun / Deno 版本；
- package manager 与 lockfile；
- 关键环境变量名称，不保存 secret 值；
- browser、OS、viewport、locale、timezone、theme；
- 测试账号、权限和 fixture；
- 后端或 mock 版本。

工作树已经升级时，不直接回退用户改动。先寻找 commit、tag、release artifact、部署环境、独立 worktree 或历史截图。无法恢复时，把可信度标为 `partial` 或 `unavailable`，并说明结论限制。

## 2. 自动盘点脚本

### 2.1 生成盘点

```bash
python3 <skill-root>/scripts/inventory_frontend.py <project-root> \
  --output .migration/source-inventory.json
```

脚本使用 Python 标准库，收集：

- package manifests、scripts 和 dependencies；
- package manager；
- framework、Router、State、Data、Form、UI、Styling、i18n、Analytics 和 Test 工具；
- build / framework config；
- 常见入口和文件路由；
- Route 配置候选；
- Feature Flag、Permission、Hidden、Deprecated 等代码线索；
- 扫描文件计数和截断警告。

结果必须人工复核：

- 正则匹配不证明 Route 可达；
- `deprecated` 字样不证明产品已废弃；
- CSS `display:none` 不证明永不可见；
- package 存在不证明仍被运行路径使用；
- 文件路由候选不证明部署后可访问。

### 2.2 比较盘点

```bash
python3 <skill-root>/scripts/compare_frontend_inventory.py before.json after.json
```

比较适合发现：

- framework / build / Router / State 等栈变化；
- dependency 和 script 增删；
- config、入口和 Route 候选变化；
- 生命周期线索数量变化。

盘点差异不是回归结论。移除旧依赖可能是迁移目标，新增 Route 也可能是批准变化；必须结合 contract 和 plan 解释。

## 3. 基线目录

推荐：

```text
.migration/
├── source-inventory.json
├── target-inventory.json
├── baselines/
│   ├── environment.json
│   ├── commands.md
│   ├── routes.json
│   ├── tests.txt
│   ├── console.json
│   ├── network.json
│   ├── screenshots/
│   ├── measurements/
│   └── accessibility/
└── results/
    └── ...同类结构
```

大文件和截图是否提交 Git 由项目策略决定；至少在 verification 中保留可访问位置和生成命令。

## 4. Route 与场景清单

Route 来源按可信度组合：

1. 生产 sitemap、路由 manifest 或部署清单；
2. Router 配置和文件路由；
3. Menu、Deep Link、redirect、permission 和 feature flag；
4. E2E、Storybook 和 analytics 中出现的入口；
5. 代码扫描候选。

每个关键 Route 记录场景：

```json
{
  "route": "/orders/:id",
  "viewport": "1440x900",
  "locale": "zh-CN",
  "theme": "light",
  "role": "operator",
  "fixture": "order-paid",
  "states": ["default", "loading", "error", "permission-denied"]
}
```

不要只测试 happy path 和桌面首屏。

## 5. 浏览器证据

### 5.1 截图

固定：

- browser 与版本；
- OS / rendering environment；
- viewport 与 device scale factor；
- font 文件和加载完成条件；
- locale、timezone、theme；
- fixture 和账号权限；
- animation、随机数和当前时间；
- network mock 或后端版本。

优先使用项目现有 Playwright、Cypress、Storybook 或 visual regression 能力。像素阈值必须有理由，不能通过不断放大阈值隐藏真实漂移。

### 5.2 DOM 尺寸

对视觉敏感页面可保存：

- bounding box；
- computed font；
- scroll width / height；
- overflow owner；
- sticky/fixed position；
- 关键 token 或 CSS custom property。

尺寸对比用于定位变化，不要求所有页面机械追求 0px 差异。批准的 responsive 或 Design System 变化应有新基线。

### 5.3 Console 与 Network

在导航后和关键交互后分别采集：

- error / warning；
- unhandled rejection；
- hydration mismatch；
- failed request；
- duplicate request；
- redirect loop；
- aborted / stale response；
- websocket / SSE 连接异常。

迁移后新增错误默认视为回归，除非有明确解释。

## 6. 测试证据

记录命令、exit code、通过/失败/跳过数量和运行环境：

```text
pnpm lint                  exit 0
pnpm typecheck             exit 0
pnpm test --run            128 passed, 2 skipped
pnpm playwright test       34 passed
```

迁移前现有失败要单独列为 baseline，不得在迁移后把“失败数量没增加”伪装为全通过。

验证裁判应先在迁移前状态运行，并尽量通过一个故意破坏的小变体验证它确实能失败。无法证明裁判有效时，降低结论可信度。

## 7. Accessibility 与性能

按项目能力收集：

- keyboard path 和 focus order；
- accessible name、role、state；
- contrast 与 reduced motion；
- axe / Lighthouse / Storybook a11y；
- bundle size、chunk 数和重复依赖；
- LCP、INP、CLS 或项目自定义指标；
- request count 和关键交互延迟。

不要求所有迁移都做完整性能实验，但高流量、SSR、组件库或构建工具迁移必须给出风险相称的证据。
