# 功能文档与递归下钻

## 一、目标

功能文档用于回答“这个模块到底提供了哪些功能，这些功能在什么条件下如何工作”。

它不是目录说明、类图，也不是把代码注释重新整理一遍。它应该成为源系统研究与迁移语义规格之间的一层业务视图：

```text
源码与测试
→ 从真实入口递归下钻
→ 功能树与功能文档
→ 技术无关迁移语义规格
→ 目标项目设计与 Rebuild
```

源代码是功能事实的证据，但功能文档按照业务能力和用户可观察行为组织，不按照 Controller、Service、Repository、DTO 或文件目录组织。

---

## 二、先枚举真实入口

开始时先找迁移范围内能够真实触发行为的入口：

- HTTP / RPC / GraphQL 接口；
- 前端路由、页面动作和交互事件；
- 消息消费者；
- 事件监听器；
- 定时任务；
- CLI / Job；
- 后台管理动作；
- 对外暴露的库接口；
- 回调、Webhook；
- 其他模块直接调用的公开能力。

不要从“这个目录有多少文件”开始生成功能列表。

每个入口先记录：

```text
入口
→ 谁触发
→ 用户/上游意图
→ 主要输入
→ 可观察输出
→ 初步功能名称
```

入口只是起点，不能把“找到 Controller”当作功能理解完成。

---

## 三、递归下钻协议

对于每个入口，沿真实调用、数据和副作用路径不断向下研究。

每进入一个新的函数、方法、组件、SQL、事件或配置节点，都问：

1. 这里是否做了新的业务决策？
2. 是否改变了业务状态？
3. 是否读写了对业务结果有意义的数据？
4. 是否调用外部系统或产生用户可观察副作用？
5. 是否处理权限、幂等、事务、并发、超时、重试、补偿或重要失败？
6. 是否根据条件分裂出新的业务分支？
7. 是否触发异步链路，使功能在当前请求结束后继续执行？
8. 是否隐藏了此前没有发现的子功能？

只要答案中存在与迁移语义有关的新信息，就继续向下。

推荐按下面的路径推进：

```text
入口
→ 参数/身份/权限
→ 应用编排
→ 业务决策
→ 状态转换
→ 数据访问
→ 外部集成
→ 消息/事件/异步任务
→ 后续消费者或回调
→ 最终可观察结果
```

不要因为跨了模块、包、服务或异步边界就自动停止。

---

## 四、使用“探索队列”，不要只追一条主链

一条调用链经常会分叉。

研究过程中维护概念上的探索队列：

| 待研究节点 | 来源 | 为什么需要继续 | 状态 |
|---|---|---|---|
| 库存预占 | 创建订单主流程 | 改变库存状态 | 待研究 |
| 优惠计算 | 价格计算 | 存在多条件业务决策 | 待研究 |
| OrderCreated 消费者 | 订单创建事件 | 可能继续产生副作用 | 待研究 |

完成一个节点后，将它发现的新业务相关分支继续加入队列。

对于循环调用或已经研究过的符号，不重复无限下钻；引用已有结论即可。

---

## 五、功能层级如何形成

不要按代码调用层数直接定义功能层级。

建议使用：

```text
L0 业务域 / 大模块
└── L1 用户或上游可识别的能力
    ├── L2 子功能 / 业务用例
    │   ├── L3 业务规则、状态变化和关键副作用
    │   └── L3 异常、补偿和边界行为
    └── L2 异步或后台能力
```

例如：

```text
订单管理
├── 创建订单
│   ├── 校验购买资格
│   ├── 计算订单价格
│   ├── 预占库存
│   ├── 创建订单记录
│   └── 发布 OrderCreated
├── 取消订单
│   ├── 判断是否允许取消
│   ├── 释放库存
│   └── 记录取消原因
└── 订单过期
    ├── 扫描待支付订单
    └── 自动取消超时订单
```

`OrderService`、`PriceManager`、`OrderRepository` 不应该天然成为功能节点；它们只能作为功能证据或实现位置。

## 六、什么时候停止继续向下

递归理解不是无限阅读。

满足以下情况时可以停止当前分支：

### 6.1 只剩纯技术实现细节

例如：

- 通用字符串处理；
- 无业务含义的对象转换；
- 标准日志封装；
- 框架 glue code；
- 与业务无关的底层序列化工具。

如果它们不改变业务语义，只记录必要技术依赖，不继续作为功能下钻。

### 6.2 已到稳定外部边界

例如第三方支付 API。

无需阅读第三方源码，但要记录：

- 调用目的；
- 请求/响应语义；
- 失败和超时；
- 重试；
- 幂等；
- 对当前功能的影响。

### 6.3 已到明确的数据事实

当下钻到数据库时，不必继续研究数据库引擎实现，但必须理解业务相关的表、字段、约束、事务和写入结果。

### 6.4 没有产生新的业务信息

如果继续向下只重复已有结论，可以停止。

### 6.5 当前证据不足

不能继续确认时不要猜。记录为未知项，并注明下一步需要什么证据。

## 七、下钻后必须反向验证

完成主调用链后，再从结果反向检查：

- 谁还调用这个能力；
- 是否存在第二个入口绕过主入口；
- 同一数据是否还有其他写入者；
- 同一事件是否还有其他生产者/消费者；
- 同一状态是否在其他 Job、Consumer、后台操作中变化；
- 是否存在 Feature Flag、租户、地区、版本或客户特例；
- 测试是否揭示当前功能树没有覆盖的行为。

正向下钻用于发现功能，反向搜索用于发现遗漏和旁路。

## 八、每个功能点的文档标准

每个重要功能至少记录：

```text
功能编号
功能名称
业务目的
使用者 / 调用方
触发入口
前置条件
主流程
关键分支
业务规则
状态变化
读取数据
写入数据
外部依赖
消息 / 事件 / 其他副作用
失败与异常行为
幂等 / 并发 / 事务要求
权限与安全
配置 / Feature Flag
可观察结果
来源证据
相关测试
未知项
迁移优先级
```

功能文档应让没有阅读源代码的人也能理解系统行为，同时让后续 Agent 可以回到具体证据位置核验。

---

## 九、证据必须跟着功能走

功能文档中的重要结论都要尽量带证据，例如：

```text
FUN-012 取消订单

规则：已发货订单不能直接取消。
证据：
- src/order/CancelOrderService.java#cancel
- OrderCancelPolicy.canCancel
- OrderCancelIntegrationTest.shouldRejectShippedOrder

类型：证据
```

如果只是推断：

```text
类型：推断
原因：发现状态判断，但没有对应测试或契约说明
下一步：检查后台管理取消流程和历史提交
```

功能文档不能把推断包装成产品需求。

---

## 十、功能文档与迁移语义规格的区别

### 功能文档

更适合人和 Agent 阅读，强调：

- 系统有哪些功能；
- 用户如何使用；
- 功能如何展开；
- 业务规则和异常是什么；
- 代码证据在哪里。

### 迁移语义规格

更接近迁移合同，强调：

- 哪些行为必须保持；
- 哪些允许改变；
- 契约和数据语义；
- 事务、幂等、失败等迁移要求；
- 如何验证。

推荐顺序：

```text
功能文档
→ 审查功能完整性
→ 蒸馏迁移语义规格
```

不要跳过功能理解直接把源类和方法转换成语义规格。

---

## 十一、大模块的多 Agent 功能研究

模块很大时，Supervisor 可以先按入口或初步业务能力拆 Research Workstreams：

```text
Research Worker A → 用户侧订单创建/修改入口
Research Worker B → 支付与回调链路
Research Worker C → Job / Event / Consumer 异步链路
Research Worker D → 数据约束和状态写入
```

Worker 输出局部功能发现和证据，不各自创建互相冲突的全局功能编号。

Supervisor 负责：

1. 合并重复功能；
2. 解决不同入口指向同一能力的问题；
3. 统一 FUN 编号；
4. 补齐跨 Workstream 链路；
5. 形成最终 `.migration/功能文档.md`。

这样可以并行深挖，但全局功能树仍只有一份真相。

---

## 十二、功能理解 Gate

进入迁移语义规格和目标设计前，至少满足：

- 迁移范围内的主要真实入口已经枚举；
- 每个高价值入口已经沿关键业务链下钻到数据、外部依赖或稳定边界；
- 关键条件分支已经展开；
- 关键异步链路已经追踪到实际消费者或最终结果；
- 核心状态变化已经识别；
- 关键数据读写和约束已经识别；
- 权限、失败、幂等、事务、并发等重要行为已经覆盖；
- 反向搜索没有发现尚未解释的重要旁路；
- 重要功能都有代码或测试证据；
- 高风险未知项已显式记录。

如果功能文档仍主要是“有哪些 Controller / Service / 方法”，说明研究深度不够，不得进入正式迁移设计。
