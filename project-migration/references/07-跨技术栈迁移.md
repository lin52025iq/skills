# 跨技术栈迁移

## 一、核心原则

跨语言、框架、数据库或中间件时，不进行语法一对一翻译。先识别源实现依赖的语义，再找到目标技术栈中最稳定、最符合目标项目惯例的表达方式。

## 二、语言层语义

### 空值与缺省值

检查：

- 缺失字段和显式空值是否不同；
- 零值是否具有业务意义；
- 可选值在目标语言中如何表示；
- 序列化后是否仍能区分。

### 数值与精度

检查：

- 金额是否使用浮点；
- 十进制实现；
- 舍入方式；
- 整数溢出；
- 大整数范围；
- JSON 数值精度。

### 时间

检查：

- 时区；
- 夏令时；
- 时间精度；
- Unix 时间单位；
- 数据库存储时区；
- 序列化格式；
- “本地时间”是否具有业务含义。

### 错误模型

检查：

- 异常、错误值、结果类型之间的差异；
- 堆栈信息；
- 可重试错误；
- 业务错误和系统错误的分类；
- HTTP 或 RPC 错误映射。

### 并发模型

检查：

- 线程安全；
- 协程；
- 事件循环；
- 共享可变状态；
- 锁；
- 上下文取消；
- 超时传播。

## 三、框架层语义

### 生命周期

检查：

- 单例、请求级、会话级或瞬时对象；
- 初始化和销毁；
- 连接池；
- 后台任务生命周期。

### 依赖注入

不要机械复制注解或容器配置。确认依赖所有权和生命周期后，使用目标项目现有方式。

### 中间件与拦截器

检查源框架是否隐式完成：

- 认证；
- 授权；
- 事务；
- 日志；
- 追踪；
- 重试；
- 参数校验；
- 异常映射；
- 序列化。

迁移业务代码时最容易漏掉这些“框架自动行为”。

## 四、数据库与 ORM

重点检查：

- 默认事务行为；
- 自动刷新；
- 懒加载；
- 级联；
- 软删除；
- 乐观锁；
- 主键生成；
- 默认值；
- 唯一约束；
- NULL 排序；
- 大小写；
- 字符集和排序规则；
- 时间类型；
- JSON 类型；
- SQL 方言；
- 隔离级别。

不要认为“两个 ORM 都叫 save”就具有相同语义。

## 五、接口与序列化

检查：

- 字段命名；
- 字段顺序是否重要；
- 缺失字段；
- 空字段；
- 默认值；
- 枚举未知值；
- 日期格式；
- 大整数；
- 错误结构；
- 内容类型；
- 编码；
- 向后兼容。

## 六、消息系统

检查：

- 至少一次、至多一次或近似恰好一次；
- 消费确认；
- 重投；
- 顺序；
- 分区键；
- 死信；
- 幂等；
- 延迟消息；
- 消费者并发；
- 事务消息；
- Schema 演进。

## 七、缓存

检查：

- 缓存键格式；
- TTL；
- 空值缓存；
- 穿透与击穿；
- 更新顺序；
- 分布式锁；
- 序列化兼容；
- 多版本服务同时运行时的缓存兼容性。

## 八、安全

检查：

- 身份认证；
- 权限；
- 角色和策略；
- Token 校验；
- 密钥读取；
- 输入校验；
- 输出脱敏；
- 审计；
- 跨域；
- CSRF；
- 请求签名。

技术栈迁移经常会绕过原框架的默认安全能力，必须显式确认。

## 九、形成迁移规则

每个语义差异建议记录：

```text
主题：事务边界
源行为：创建订单与库存预占记录在同一数据库事务中提交。
目标做法：通过目标项目现有事务执行器包裹应用用例。
禁止：分别提交两个仓储操作。
验证：模拟第二次写入失败，确认第一次写入不会保留。
```

规则应服务于实施和验证，而不是只解释技术差异。
