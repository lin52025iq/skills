# 跨技术栈迁移

## 一、核心原则

跨语言、框架、数据库或中间件时，不做语法一对一翻译。

默认顺序：

```text
识别源语义
→ 查目标项目已有惯例
→ 查目标技术栈成熟表达
→ 形成迁移规则
→ 用难样本试迁移
→ 批量实施
```

目标是“目标原生且行为可证”，不是“源结构在新语言中复刻”。

## 二、建立规则书和差距清单

规则书处理可重复决策；差距清单处理规则默认值覆盖不了的特殊情况。

如果多个任务会遇到同一种问题，优先形成规则，不要让每个实现者重新选择。

规则至少记录：

```text
主题
源语义
目标决策
理由
禁止做法
适用范围
验证方式
```

## 三、语言层语义

### 空值与缺省值

检查缺失字段、显式空值、零值、Optional/pointer/result 和序列化差异。

### 数值与精度

检查金额、十进制、舍入、整数范围、溢出和 JSON 数值精度。

### 时间

检查时区、夏令时、精度、Unix 单位、数据库存储和业务本地时间。

### 错误模型

检查异常、错误值、Result 类型、业务错误与系统错误、可重试性和 HTTP/RPC 映射。

### 并发模型

检查线程、协程、事件循环、共享状态、锁、取消和超时传播。

### 语言惯例

不要把源语言为了弥补自身限制形成的模式机械带入目标语言。例如：

- 不因为源语言大量继承，目标语言也强制继承；
- 不因为源语言缺少代数数据类型，就在目标语言继续保留字符串状态；
- 不因为源语言依赖异常控制流程，就拒绝目标语言成熟的显式错误模式；
- 不因为源语言需要 Builder/Factory，就默认目标语言也需要。

## 四、框架层语义

### 生命周期

检查单例、请求级、会话级、瞬时对象、初始化、销毁和连接池。

### 依赖注入

确认依赖所有权和生命周期后，使用目标项目现有方式。不要为了“可测试”给每个类型制造接口。

### 中间件与拦截器

检查源框架是否隐式完成：认证、授权、事务、日志、Trace、重试、校验、异常映射和序列化。

这些隐式行为往往比显式业务代码更容易迁漏。

## 五、数据库与 ORM

重点检查：

- 默认事务；
- 自动刷新；
- 懒加载；
- 级联；
- 软删除；
- 乐观锁；
- 主键生成；
- 默认值；
- 唯一约束；
- NULL 排序；
- 大小写和排序规则；
- 时间类型；
- JSON；
- SQL 方言；
- 隔离级别。

不要认为两个 ORM 的同名方法具有相同语义，也不要强制把 ORM Entity 继续作为全部层的统一模型。

## 六、接口与序列化

检查字段命名、缺失/空值、默认值、未知枚举、日期、大整数、错误结构、内容类型、编码和向后兼容。

## 七、消息系统

检查投递保证、消费确认、重投、顺序、分区键、死信、幂等、延迟、并发、事务消息和 Schema 演进。

## 八、缓存

检查键格式、TTL、空值缓存、穿透/击穿、更新顺序、分布式锁、序列化和多版本兼容。

## 九、安全

检查认证、授权、角色和策略、Token、密钥、输入校验、输出脱敏、审计、CORS、CSRF 和请求签名。

技术栈迁移经常会绕过原框架默认安全能力，必须显式确认。

## 十、技术替换同时检查设计质量

跨技术栈时主动问：

- 源框架的结构是否只是历史偶然，而不是业务需要；
- 目标项目是否已有更简单的基础设施能力；
- 原有 abstraction 是否仍解决真实问题；
- 能否在不改变业务语义的情况下减少框架侵入；
- 能否让业务规则更接近领域概念；
- 是否应该使用 ACL 隔离旧模型；
- 是否需要 Branch by Abstraction 支持内部渐进替换。

## 十一、试迁移是规则压力测试

选择高复杂度样本，按规则完成一次迁移，并由独立视角比较：

- 规则驱动实现；
- 按目标技术栈高级工程师惯例实现。

如果两者差异暴露更优目标设计，更新规则。试迁移代码默认可丢弃。

## 十二、规则示例

```text
主题：事务边界
源行为：创建订单与库存预占记录在同一数据库事务提交。
目标做法：通过目标项目现有事务执行器包裹应用用例。
设计改进：业务层不直接依赖 ORM Transaction 类型。
禁止：分别提交两个仓储操作；把 ORM Session 传入领域对象。
验证：模拟第二次写入失败，确认第一次写入不会保留。
```
