# 前端跨技术栈迁移

跨框架、构建工具、状态管理或组件库时，先迁移语义，再选择目标技术表达。不要建立语法转换表后批量照搬。

## 1. 建立前端迁移矩阵

对每个受影响能力记录：

| 主题 | 源语义 | 目标决策 | 风险 | 禁止做法 | 验证 |
|---|---|---|---|---|---|
| Route |  |  |  |  |  |
| Props / Input |  |  |  |  |  |
| Event / Output |  |  |  |  |  |
| State |  |  |  |  |  |
| Data Fetching |  |  |  |  |  |
| Form |  |  |  |  |  |
| Styling |  |  |  |  |  |
| SSR / Hydration |  |  |  |  |  |
| Test |  |  |  |  |  |

如果不同执行者可能给出不同答案，且差异会影响多个迁移单元，就把答案固化为规则。

## 2. 必须逐项确认的语义

### 2.1 组件与内容组合

检查：

- props / inputs 的默认值、可选性和双向绑定；
- events / outputs 的命名、payload 和冒泡；
- slot、children、content projection、render prop 和 portal；
- ref、imperative handle 和 DOM ownership；
- keep-alive、teleport、transition 和动态组件。

不要把 Vue watcher、Angular lifecycle 或 class component lifecycle 机械翻译成大量 React `useEffect`。先区分纯派生值、用户事件、外部订阅和真正副作用。

### 2.2 状态所有权

为每项状态标记：

- Server State；
- URL State；
- Global Client State；
- Feature State；
- Local UI State；
- Derived State；
- Ephemeral DOM State。

迁移时重新确认所有权，不默认把一个源 Store module 对应为一个目标 Store module。优先使用目标项目已有的 query cache、router state、form state 和局部状态模式。

### 2.3 数据请求与缓存

检查：

- 请求触发时机；
- 去重、cache key、stale time 和失效策略；
- pagination / infinite scroll；
- optimistic update 与回滚；
- abort、race、retry 和 timeout；
- error mapping；
- SSR preload、dehydrate / hydrate 和 client refetch；
- websocket / SSE / polling。

两个库的同名 API 不代表相同生命周期或缓存语义。

### 2.4 Router 与页面生命周期

检查：

- static / dynamic / optional / catch-all 参数；
- nested route、layout 和 outlet；
- redirect、guard、loader、action 和 error boundary；
- scroll restoration、transition 和 unsaved changes；
- base path、locale prefix 和 trailing slash；
- SPA fallback、SSR 和静态输出；
- Deep Link 与刷新后的直接可达性。

路由迁移必须从真实可达入口生成清单，不能只看文件名。

### 2.5 Form 与验证

检查：

- controlled / uncontrolled；
- schema、field-level 和 server validation；
- touched、dirty、submitting 和 reset；
- async validation、debounce 和 race；
- file input、date、number 和 locale；
- keyboard submit、focus error 和 accessible name；
- 后端错误如何映射到字段和页面。

更换 Form 库或组件库时重点验证默认事件、值类型、清空行为和 disabled/read-only 差异。

### 2.6 Styling 与 Design System

允许重建 CSS 架构，但保留批准的视觉契约：

- global CSS、CSS Modules、CSS-in-JS、Tailwind、Scoped CSS；
- specificity、cascade、reset 和 CSS layer；
- token、theme、dark mode 和 runtime theme；
- font loading、icon、image 和 asset URL；
- Grid/Flex、container query、breakpoint 和 overflow；
- portal、z-index、sticky / fixed 和 scroll owner。

组件库替换不能只比较 API；必须比较 DOM、keyboard、focus、ARIA、默认 spacing、popup container 和 responsive 行为。

### 2.7 SSR、Hydration 与平台边界

检查：

- server-only / client-only API；
- window、document、storage 和 media query；
- deterministic render；
- hydration mismatch 与首屏闪烁；
- streaming、Suspense 和 loading boundary；
- cookies、headers、auth 和 personalization；
- metadata、SEO、canonical 和 structured data；
- runtime、edge、Node 和 browser target。

SPA → SSR 不是把页面包进新框架。数据边界、认证、缓存、客户端副作用和第三方脚本都需要重新设计。

### 2.8 构建、环境与资产

检查：

- ESM / CJS；
- alias、dynamic import 和 glob import；
- env prefix、compile-time / runtime env；
- CSS、SVG、worker、WASM 和 public assets；
- code splitting、preload 和 chunk naming；
- proxy、base URL 和 deployment path；
- test environment、Storybook 和 coverage；
- browser support 与 polyfill。

Webpack → Vite / Rspack 时，Loader / Plugin 的名称不能直接映射；先确认它解决的真实构建语义。

## 3. 常见迁移方向

### Vue → React

重点重新设计：

- computed / watch / watchEffect → derived state、event 或 effect；
- `v-model` → value + event 或目标 Form 方案；
- slot / scoped slot → children / render prop / composition；
- provide/inject → context 或显式依赖；
- Pinia/Vuex → URL、query cache、local state 或目标 global state；
- directive → component、hook 或 DOM behavior。

禁止把每个 `.vue` 文件机械变成一个 `.tsx`，也不要保留只为 Vue 生命周期服务的层次。

### Angular → React / Vue

重点确认：

- module / standalone component 边界；
- DI scope 与 service state；
- RxJS stream、subscription 和 teardown；
- template form / reactive form；
- route guard / resolver；
- change detection 和 zone 依赖；
- content projection 和 directive。

不要复制 Controller/Service 层级或把 Observable 全部塞进 component effect。

### React SPA → Next.js / Remix / 其他 SSR

重点确认：

- server/client component 边界；
- loader/action 或 server action；
- cache、revalidation 和 mutation；
- auth、cookie 和 redirect；
- metadata、not-found 和 error boundary；
- hydration、streaming 和 third-party script；
- Route 与 Layout 文件结构。

目标框架的数据模型和路由惯例优先于源 SPA 组件树。

### JavaScript → TypeScript

先建立边界类型，而不是批量加 `any`：

- API response、event payload、route params、form values；
- discriminated union 与未知枚举；
- nullable / optional；
- component public props；
- third-party adapter；
- runtime validation 与 compile-time type 的边界。

禁止用大量 `@ts-ignore`、`as any` 或宽泛 index signature 伪造完成。

## 4. Codemod 协议

Codemod 适合重复、局部、语义明确的转换，不适合产品和架构判断。

执行顺序：

1. 固定工具和规则版本；
2. 在干净或可回退的迁移分支运行 dry-run；
3. 选择少量代表文件检查 false positive / false negative；
4. 保存命令、输入范围和生成 diff；
5. 分批应用；
6. 每批运行 format、lint、typecheck、tests 和页面验证；
7. 对无法自动判断的变化加显式队列，不静默猜测；
8. 规则修正后重新生成，而不是手工修数百个同类实例。

以下默认需要人工审查：

- effect / lifecycle；
- state ownership；
- event payload；
- slot / children；
- form value；
- permission 和 feature flag；
- SSR / hydration；
- CSS specificity 和 responsive；
- accessibility。

## 5. 新旧共存与 Bridge

迁移期允许 adapter、compat component、route proxy 或 shared contract，但必须记录：

- 解决的具体边界；
- 数据和事件转换；
- 新旧版本兼容矩阵；
- 所有调用方；
- 性能与错误风险；
- 删除条件和最晚清理阶段。

Bridge 只做边界适配，不继续堆新的产品逻辑。迁移完成后重新判断是否保留。

## 6. 验证

跨栈迁移至少验证：

- 相同用户场景的功能结果；
- Route、URL 和导航行为；
- 数据请求次数、顺序、取消和错误；
- Default / Loading / Empty / Error / Disabled；
- keyboard、focus、form 和 popup；
- desktop / tablet / mobile；
- SSR / hydration / console；
- visual diff；
- a11y；
- bundle、首屏和关键交互性能。

技术栈名称变化不是迁移成功证据；可观察契约和目标原生审查才是。
