# 功能生命周期与废弃识别

## 一、为什么需要单独判断功能生命周期

迁移时最危险的误判之一，是把“仓库里还能找到代码”直接理解成“这个功能仍然有效并且需要迁移”。

遗留系统，尤其是前端项目，经常通过以下方式停用功能而没有立即删除代码：

- 页面 JSX / Vue Template / Angular Template 被整块注释；
- 路由定义被注释、移除注册或永远无法匹配；
- 菜单项、按钮、Tab 被注释或不再注册；
- `v-if`、`ng-if`、条件渲染、权限判断使功能不可达；
- CSS 使用 `display: none`、`visibility: hidden` 或特定 class 长期隐藏；
- Feature Flag 被永久关闭；
- AB 实验、租户、地区、版本条件使功能只对极少范围可见；
- 后端 API、事件或数据结构仍保留，但 UI 已停止使用；
- 新实现已经替代旧实现，旧组件仍留在仓库；
- 代码标记 deprecated / legacy / old / unused / TODO remove；
- 测试被 skip / disabled；
- 入口被删除，但内部 Service 或 Component 仍存在；
- 历史样式、选择器、图片和文案仍残留。

因此：

> **代码存在只能证明“历史上可能存在过这个能力”，不能证明它当前仍属于产品功能。**

迁移决定必须结合“可达性 + 运行条件 + UI 暴露 + 配置 + 历史 + 测试 + 调用关系”判断。

## 二、功能生命周期状态

每个发现的功能至少归入以下一种状态：

### Active / 现役

当前存在真实入口，正常用户或上游可以触达，且代码链路有效。

默认：需要继续进入迁移边界判断。

### Conditional / 条件现役

只在特定条件可用，例如：

- Feature Flag；
- 权限 / 角色；
- 租户；
- 地区；
- AB 实验；
- 环境；
- 版本；
- 特定数据状态。

不能因为默认环境看不到就当作废弃。必须记录触发条件和覆盖范围。

### Hidden / 隐藏但可能有效

UI 当前不直接展示，但仍可能通过深链、程序调用、快捷入口、后台动作或其他页面触达。

需要继续验证运行可达性。

### Disabled / 已禁用

代码仍存在，但明确被配置、路由、注册、Feature Flag 或条件关闭。

不能自动迁移，也不能自动删除。先确认禁用是否是临时的。

### Deprecated / 已废弃

存在明确证据表明业务已停止使用或已有替代方案，例如：

- 注释说明；
- ADR / issue / commit；
- 新组件替代；
- 功能下线记录；
- 长期关闭的 Flag；
- 无运行入口且历史明确。

默认“不迁移”，但迁移文档要记录依据。

### Removed / 已移除

产品功能已经正式不存在，只剩残留代码、样式、资源或数据兼容逻辑。

通常不迁移；必要兼容数据和外部契约单独判断。

### Unknown / 待确认

证据冲突或不足。

未知项必须保留，不允许为了推进迁移擅自归为 Active 或 Deprecated。

## 三、前端项目必须检查的生命周期证据

### 3.1 页面和模板层

检查：

- JSX / TSX 注释块；
- Vue `<template>` 中被注释内容；
- Angular HTML 注释；
- Svelte / Astro / Server Template 注释；
- 条件渲染；
- 永远为 false 的条件；
- 临时隐藏 class；
- 已删除但仍 import 的组件；
- fallback / legacy component。

**被注释的 UI 是强烈的“非现役信号”，但不是单独的最终证据。**

继续查它是否还有其他入口、同功能的新实现或后端依赖。

### 3.2 路由和导航

检查：

- route table；
- lazy route；
- menu config；
- sidebar / navbar；
- deep link；
- redirect；
- route guard；
- permission route；
- micro-frontend registration；
- server-side route / rewrite。

一个页面文件存在但没有可达路由，不能直接算现役页面。

### 3.3 Feature Flag 和环境条件

检查：

- Feature Flag SDK；
- `.env`；
- config；
- build-time defines；
- tenant / region；
- rollout percentage；
- experiment；
- debug-only / dev-only 分支。

记录默认值不足够，还要确认实际生产环境或部署配置（如果可获取）。

### 3.4 权限和身份

检查：

- role；
- permission；
- entitlement；
- plan / subscription；
- internal user；
- admin-only；
- organization state。

“当前账号看不到”不能证明功能废弃。

### 3.5 样式隐藏

检查：

- `display: none`；
- `visibility: hidden`；
- `opacity: 0` + pointer behavior；
- off-screen positioning；
- responsive breakpoint hiding；
- utility class，例如 `hidden` / `sr-only`；
- theme-specific hiding。

注意区分：

- 响应式隐藏；
- 权限/状态隐藏；
- 永久废弃隐藏。

### 3.6 调用与数据

检查：

- API 是否仍有调用方；
- store/action 是否仍被 dispatch；
- event 是否仍有生产/消费；
- component 是否仍被 import；
- query/mutation 是否仍被执行；
- 数据字段是否仍被读取；
- 埋点事件是否仍存在；
- 后台 Job 是否仍维护对应状态。

## 四、注释代码的处理规则

注释代码必须进入研究视野，但默认不能进入迁移实现。

发现大块注释 UI / 逻辑时：

1. 识别它表达的历史功能；
2. 查找同功能是否有现役替代实现；
3. 查找路由、菜单、Flag、权限和调用方；
4. 查找相关 API / 数据 / 测试是否仍有效；
5. 查看注释、commit、issue 或历史说明；
6. 将功能标记为 Disabled / Deprecated / Unknown 等生命周期状态；
7. 在迁移边界阶段明确：迁移 / 不迁移 / 保留兼容 / 待确认。

禁止：

> 看到一段完整注释页面 → “为了完整性”把它恢复并迁到新项目。

也禁止：

> 看到它被注释 → 直接认为整个业务能力已经废弃。

## 五、证据优先级

判断生命周期时优先组合多类证据，不依赖单点。

建议参考：

1. 当前可达入口和运行注册；
2. 生产或真实环境配置（若可获得）；
3. 现役调用关系；
4. Feature Flag / 权限；
5. 自动化测试和 E2E；
6. 新旧实现替代关系；
7. Git 历史、issue、ADR、注释；
8. 残留代码或样式。

只有残留代码而没有入口、调用、配置或业务证据时，迁移优先级应降低。

## 六、形成生命周期清单

使用 `templates/04-功能生命周期清单.md`。

至少记录：

```text
功能编号
功能名称
生命周期状态
入口状态
UI 暴露状态
路由/注册状态
Feature Flag
权限条件
调用关系
替代实现
注释/历史证据
迁移决策
置信度
未知项
```

功能文档中的每个高层功能都应该能对应生命周期状态。

## 七、迁移边界规则

### Active

正常进入能力迁移判断。

### Conditional

迁移时必须保留触发条件或明确批准改变。

### Hidden

先确认真实可达性，再决定。

### Disabled

默认不直接实现到目标产品入口；先确认未来是否可能重新开启。

### Deprecated / Removed

默认不迁移业务 UI 和旧实现，只迁移仍有必要的兼容契约或数据处理。

### Unknown

如果可能影响产品能力完整性，作为 Gate 阻塞项。

---

## 八、独立审查问题

迁移前 Reviewer 至少问：

1. 哪些功能只是因为代码存在才被列入迁移？
2. 哪些页面实际上已没有路由或导航入口？
3. 哪些 UI 被整块注释或长期隐藏？
4. 哪些 Feature Flag 已长期关闭？
5. 哪些功能已有替代实现？
6. 哪些权限/租户条件导致“看不到但仍有效”？
7. 是否把 Deprecated 功能错误恢复到了新系统？
8. 是否误删了只是 Conditional 的功能？

如果生命周期未确认，不能把“功能清单完整”视为“需要全部迁移”。
