# 项目迁移方法论

> 本文是 `project-migration` Skill 的方法论总纲。它面向跨项目、跨架构、跨技术栈的系统迁移，重点约束 AI 如何理解、决策、现代化、实施和验证，而不是提供某一种语言或框架的固定转换教程。

## 一、核心定义

系统迁移不是“把源代码翻译成另一套代码”，而是把一组**可观察系统能力**迁移到新的技术和架构环境，并在迁移过程中有意识地减少遗留设计问题。

迁移围绕六个对象组织：

1. **能力**：系统对用户、上游或下游提供什么；
2. **业务规则**：在什么条件下做出什么业务决策；
3. **契约**：输入、输出、事件、错误和数据边界；
4. **副作用**：数据写入、消息、外部调用、缓存、文件、审计等；
5. **设计质量**：能力在目标系统中如何被清晰、稳定、可测试地组织；
6. **证据**：为什么相信源行为如此，以及如何证明目标行为满足要求。

文件、类、函数和数据库表只是实现载体，不应成为迁移边界和进度的主要度量。

## 二、我们吸收的社区经验

### 1. Agent Skills：主 Skill 做路由，细节渐进加载

Anthropic 的 Agent Skills 实践强调 progressive disclosure：Skill 被触发后先读取 `SKILL.md`，特定场景的详细知识再从 references 按需读取。这样能减少上下文竞争，让复杂 Skill 仍然可组合、可维护。

因此 `project-migration` 采用三层结构：

```text
SKILL.md      → 状态机、关键约束、门禁和路由
references/   → 各阶段方法、设计原则和检查项
templates/    → 迁移项目中的持久化事实、状态与证据
```

主文件不追求覆盖全部细节。新增经验优先判断应该进入核心规则，还是只在某个阶段按需读取。

### 2. Anthropic 大型代码迁移：先有裁判，才有退出条件

Anthropic 2026 年公开的大型代码迁移实践把“judge”作为迁移前置条件：裁判必须能够以相同标准评价旧实现和新实现，否则没有客观完成条件。

对本 Skill 的启发：

- 现有测试如果只依赖源项目内部结构，不能直接充当迁移裁判；
- 优先把测试提升到公共接口、契约或真实业务场景；
- 行为对照工具必须先证明自己能在旧实现上通过；
- 条件允许时，用故意破坏的实现验证裁判确实能够失败；
- 没有可靠裁判时，不扩大批量实施。

### 3. 规则书先于批量实施

跨技术栈迁移会反复遇到相同决策：空值、时间、精度、错误、事务、并发、序列化、ORM、消息、生命周期等。

如果每个迁移任务临时决定，最终实现会发生漂移。

因此使用“迁移规则书”：

> 如果两个有经验的执行者可能对同一问题给出不同答案，而且差异会影响迁移一致性，就应把该问题沉淀为规则。

规则至少包含：源语义、目标决策、理由、禁止做法、适用范围和验证方式。

### 4. 先做可丢弃试迁移，再扩大执行

Anthropic 的迁移实践会用小范围迁移压力测试规则；对于重设计型迁移，则通过对抗式设计审查和可丢弃的端到端试跑验证设计。

试迁移不以“完成几个文件”为目标，而是提前发现会被批量复制的问题。

优先选择：

- 依赖最复杂的能力；
- 技术栈语义差异最大的能力；
- 错误路径和事务最复杂的能力；
- 框架隐式行为最多的能力；
- 历史 bug 多或业务规则密集的能力。

试迁移结束后允许删除目标代码。真正应保留的是修正后的规则、架构决策、验证标准和任务拆分方式。

### 5. “不要修代码，要修产生代码的过程”

Anthropic 的公开经验强调：如果同一种失败重复出现，继续逐个修实例会把成本线性放大，更好的做法是修正产生这些实例的规则或循环。

本 Skill 采用失败反馈机制：

```text
一次失败
→ 修实例并记录原因

同类失败反复出现
→ 暂停该类批量实施
→ 检查源理解 / 边界 / 架构 / 规则 / 任务拆分
→ 修正上游产物
→ 标记所有受影响单元
→ 重新验证
```

“三次同类失败”可以作为强提示，但不是机械阈值。关键在于识别失败是否具有可复制性。

### 6. Strangler Fig：优先渐进替换而不是大爆炸

AWS 对 Strangler Fig 的现代化指导建议，在大型、紧耦合、不能停机的系统中，让新旧实现共存，并逐步把能力或流量转移到新系统，以降低一次性替换风险。

适合：

- 外围请求或调用可以被路由；
- 业务不能长时间冻结；
- 迁移需要按能力逐步放量；
- 旧系统必须继续承担未迁移能力。

但临时路由层可能成为性能瓶颈和新的复杂度，因此必须有清理条件。

### 7. Branch by Abstraction：深层组件通过抽象逐步替换

Martin Fowler 的 Branch by Abstraction 用一个稳定抽象让旧实现和新实现并存，使大型替换可以在系统持续交付的情况下逐步完成。

适合：

- 被迁移组件位于系统内部；
- 上游调用者多；
- 无法通过外围路由直接切流；
- 希望旧、新实现同时存在并做行为比较。

抽象层是迁移手段，不一定是永久架构。迁移完成后必须重新判断是否保留。

### 8. Anti-Corruption Layer：保护目标模型不受遗留语义污染

Microsoft Azure Architecture Center 的 Anti-Corruption Layer 模式强调，在新旧系统语义、数据模型或接口不同的情况下，用 facade/adapter 翻译两边模型，使目标系统无需为了兼容旧系统而污染自己的设计。

适合：

- 新旧领域模型差异明显；
- 旧 API 或数据结构质量较差；
- 迁移周期较长；
- 新系统必须暂时继续调用旧能力。

ACL 中只放边界翻译和适配，不应继续堆新的业务规则。

### 9. Characterization Testing：先锁住真实行为，再安全改设计

遗留系统往往缺少可信规格。Characterization Test 的价值是先捕获系统当前真实行为，让重构和现代化拥有安全网。

需要注意：捕获“当前行为”不代表所有当前行为都是正确需求。发现疑似 bug 时，应记录成显式差异并决定是保持还是修正，不能因为测试记录了它就永久保留。

## 三、迁移成功是“双轨目标”

传统代码迁移容易走向两个极端：

- **只保行为**：把旧设计、旧框架习惯和技术债完整复制到新系统；
- **只追求重构**：大幅重写后无法判断行为差异来自迁移还是重新设计。

本方法采用双轨模型：

### 轨道 A：业务语义连续性

明确需要保持：

- 核心业务能力；
- 业务规则；
- 对外契约；
- 数据语义；
- 关键副作用；
- 失败、重试、幂等、事务和一致性语义；
- 安全、权限和审计要求。

### 轨道 B：目标原生现代化

主动改善：

- 错误的模块边界；
- 过度耦合；
- 业务规则散落；
- 框架和基础设施侵入；
- 重复代码和重复能力；
- 隐式副作用；
- 难测试设计；
- 不符合目标语言/框架惯例的实现；
- 没有价值的历史兼容结构。

两条轨道共同推进，但不能混淆“设计变化”和“业务行为变化”。

## 四、把源系统内容分为三类

迁移每项重要行为或实现时，先分类：

### A. 必须保持的业务语义

例如订单状态规则、金额计算、幂等要求、权限、外部事件契约。

默认保持，并建立验证证据。

### B. 应该改善的实现设计

例如 God Service、循环依赖、跨层调用、ORM 实体泄漏到领域层、重复规则、隐式全局状态。

允许在目标实现中直接采用更好结构，不要求先复制旧设计再二次重构。

### C. 疑似错误业务行为

例如源系统可能存在已知 bug、错误计算、历史兼容异常。

不能因为“现代化”而静默修改。必须：

1. 记录源行为证据；
2. 说明为什么怀疑它错误；
3. 记录预期新行为；
4. 获得明确依据或用户接受；
5. 在验证报告中作为批准差异展示。

## 五、九阶段迁移闭环

```text
0 可行性与迁移接入
  ↓
1 源系统理解
  ↓
2 迁移边界
  ↓
3 目标系统理解与架构映射
  ↓
4 迁移规则、设计改进与实施计划
  ↓
5 验证裁判、安全网与试迁移
  ↓
6 增量实施与受控现代化
  ↓
7 行为验证、质量审查与独立审查
  ↓
8 切换、回滚与清理
```

每个阶段必须回答四个问题：

- 输入是什么；
- 本阶段要得到什么事实或决策；
- 证据保存在哪里；
- 什么条件满足才允许进入下一阶段。

Gate 是退出条件，不是提醒清单。

---

## 六、阶段 0：先决定“该不该迁”

迁移请求到达后先只读评估：

- 迁移解决什么问题；
- 保持现状的成本是什么；
- 局部迁移是否已经足够；
- 是否应先解耦或补测试；
- 目标项目是否已有等价能力；
- 迁移是行为保持型还是重设计型；
- 验证成本是否可接受；
- 旧系统能否在迁移期继续运行；
- 数据切换和回滚是否现实可行；
- 现代化收益是否足以抵消设计变化风险。

明确输出：

```text
迁移 / 局部迁移 / 先解耦再迁移 / 暂缓 / 不迁移
```

---

## 七、阶段 1：建立证据化行为模型

使用：

```text
结构
→ 业务
→ 依赖与副作用
→ 失败与边界
→ 反证
```

重要结论标记为证据、推断或未知。

输出至少覆盖：能力、业务规则、契约、数据、副作用、失败路径、技术约束和高风险未知项。

---

## 八、阶段 2：按能力定义边界

每项关键能力分类：

```text
迁移 / 复用 / 适配 / 替换 / 保留 / 淘汰 / 待确认
```

同时明确：

- 能力所有者；
- 数据所有者；
- 对外契约；
- 新旧连接方式；
- 临时态；
- 最终态。

边界不清晰时，优先继续理解或先解耦，不应用“拆成微服务”代替边界分析。

---

## 九、阶段 3：先设计目标态，再设计迁移态

目标项目不是源项目的容器。

先理解目标项目中维护良好、近期活跃、经过测试的类似实现，然后定义：

```text
源概念 → 目标概念 → 需要保持的语义
```

同时区分：

- **目标态架构**：迁移结束后真正希望长期保留的结构；
- **迁移态架构**：为了新旧共存暂时引入的 proxy、adapter、ACL、双写、兼容层等。

所有迁移态设施都应有退出条件，防止临时架构永久化。

---

## 十、阶段 4：规则书 + 设计改进台账 + 依赖计划

### 1. 规则书

沉淀容易产生实现分歧的高影响决策。

### 2. 设计改进台账

记录源设计问题，并分类：

- 必须改；
- 应该改；
- 后续改。

### 3. 迁移计划

按依赖和能力顺序拆成小任务，而不是按文件顺序。

每个任务同时引用：

```text
来源能力
+ 业务规则
+ 技术迁移规则
+ 设计改进项
+ 验证方式
```

---

## 十一、阶段 5：建立裁判并做试迁移

### 验证裁判

至少有一项能客观判断新实现是否满足要求。

验证裁判本身：

- 在旧实现上可运行并通过；
- 不依赖不需要保留的内部结构；
- 条件允许时，对故意破坏实现能够失败。

### 可丢弃试迁移

选择少量难样本，用真实规则和目标设计完成一次端到端迁移。

试迁移结束问：

- 哪些规则不够明确；
- 哪些设计改进让验证困难；
- 哪些目标抽象过度；
- 哪些源框架隐式行为被漏掉；
- 哪些任务粒度不适合；
- 哪些裁判无法识别真实错误。

先修流程，再放大执行。

---

## 十二、阶段 6：实施时允许受控现代化

目标实现不需要经历“先复制坏设计，再重构”的中间步骤。

如果源设计问题已经有证据，目标架构和验证方式已经明确，可以直接实现目标原生结构。

但每项设计变化都必须能回答：

- 这是设计变化还是业务行为变化；
- 为什么目标结构更好；
- 是否符合目标项目惯例；
- 是否增加不必要抽象；
- 通过什么测试证明业务语义仍成立；
- 如果失败，能否回退或缩小范围。

实施中发现新事实时，先回写理解、规则、设计台账或计划，再继续编码。

---

## 十三、阶段 7：同时审查行为和代码质量

### 行为审查

旧实现尽可能保持可运行。

出现验证失败时分类：

```text
旧实现也失败 → 继承问题或裁判问题
只有新实现失败 → 迁移回归
两边都成功但结果不同 → 行为差异
```

### 目标代码质量审查

至少检查：

- 模块职责是否清晰；
- 依赖方向是否合理；
- 业务规则是否集中在合适位置；
- 基础设施是否污染核心业务；
- 事务和副作用边界是否清晰；
- 错误模型是否一致；
- 是否遵循目标语言和框架惯例；
- 是否重复目标项目已有能力；
- 是否增加无价值抽象；
- 是否容易测试、观察和继续修改；
- 临时迁移设施是否有清理条件。

“更现代”不能仅由层数、模式数量或代码行数证明。

---

## 十四、阶段 8：真实流量和数据安全转移后才算结束

部署不等于完成。

按场景选择一次性切换、Feature Flag、灰度、影子流量、双读、双写或新旧并行。

切换前定义：

- 观测指标；
- 放量条件；
- 停止条件；
- 回滚触发条件；
- 回滚后的数据处理；
- 数据权威；
- 临时架构清理条件。

稳定性满足后再删除旧实现和临时兼容设施。

---

## 十五、推荐的迁移质量度量

比“迁移文件数”和模糊完成百分比更有意义：

### 能力覆盖率

```text
已验证关键能力 / 需要迁移的关键能力
```

### 业务规则验证率

```text
已有验证证据的高优先级规则 / 高优先级规则总数
```

### 设计改进完成率

```text
已关闭的本次必须处理设计问题 / 本次必须处理设计问题总数
```

### 未关闭行为差异

所有差异进入持久化队列。

### 阻断未知项

影响迁移正确性、安全或切换的未知项不能隐藏。

### 规则稳定性

同类失败持续出现，说明规则或架构尚不稳定，不适合扩大批量迁移。

---

## 十六、如何持续改进这个 Skill

Skill 的演进应来自真实迁移任务，而不是不断增加理论检查项。

每完成一个代表性案例，复盘：

1. AI 在哪个阶段最容易误判；
2. 哪些门禁没有真正阻止错误推进；
3. 哪些 reference 很少被需要，是否应简化；
4. 哪些决策在多个项目重复出现，应升级为核心规则；
5. 哪些模板产生无价值文档，应该删除或合并；
6. 哪些错误直到后期才出现，能否把验证前移；
7. 哪些设计改进导致范围失控，应增加限制；
8. 哪些目标技术栈有稳定经验，值得新增专门 reference。

优先通过真实案例评测 Skill，而不是以文档长度衡量成熟度。
