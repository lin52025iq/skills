# 前端项目迁移方法论

本文是 `project-migration` 的前端迁移总纲。详细执行入口以 `SKILL.md` 为准；这里只解释核心判断模型。

## 1. 迁移对象是可观察契约

前端迁移的基本单位不是文件、组件或 Hook，而是用户能够观察到的一组契约：

1. **入口与可达性**：Route、Menu、Deep Link、Tab、Modal、Flag 和 Permission；
2. **功能与业务规则**：用户意图、前置条件、成功/失败结果；
3. **数据与状态**：请求、缓存、状态所有权、并发、取消和副作用；
4. **视觉与响应式**：布局、字体、颜色、图标、断点和滚动；
5. **交互与反馈**：Keyboard、Focus、Form、Loading、Empty、Error、Toast；
6. **平台与质量**：SSR、Hydration、SEO、i18n、Accessibility、性能和运行错误。

源项目回答“现役产品真实做什么、长什么样”；目标项目回答“新代码应该怎样组织”。两者之间必须经过技术无关契约与目标蓝图，不能直接按源组件树生成目标组件树。

## 2. 迁移的双轨目标

### 轨道 A：用户语义连续性

默认保持：

- Active / Conditional 用户能力；
- Route、权限与 Deep Link；
- 数据语义、错误反馈和关键副作用；
- 视觉、响应式和交互基线；
- Accessibility 与平台约束。

### 轨道 B：目标原生现代化

允许改善：

- 组件边界和状态所有权；
- 请求、缓存和错误模型；
- 旧框架生命周期与隐式副作用；
- CSS 架构和 Design Token 使用；
- 重复组件、过度抽象和不可测试结构；
- 构建、代码分割和资产处理。

现代化不能静默改变用户可观察行为。需要改变时，把差异列为产品决策并建立新验收标准。

## 3. 三种范围，三种流程重量

### 小型迁移

单组件、单页面或单用户流程。允许把 context、contract、plan 和 verification 合并到一个 Markdown，只保留相关基线与测试。

### 标准迁移

一个 Feature、页面组或技术子系统。使用最小迁移包、自动盘点、试迁移和分波实施。

### 大型迁移

多应用、微前端或多个 Route 域。增加 Workstreams、共享资源单写者、集成门禁、灰度、回滚和旧路径清理。

流程重量由风险和范围决定，不由模板数量决定。

## 4. 六阶段闭环

```text
A 范围与真实 before state
→ B 源入口、生命周期、契约与基线
→ C 目标项目研究与目标原生蓝图
→ D 试迁移、风险和实施波次
→ E 小步实现与逐单元验证
→ F 全量对照、发布、回滚与清理
```

每个阶段都要回答：

- 输入和证据是什么；
- 哪些事实已确认，哪些仍是 Unknown；
- 产物保存在何处；
- 什么退出条件允许进入下一阶段。

Gate 是阻止错误扩散的退出条件，不是提醒清单。

## 5. 证据优先级

### 功能与生命周期

```text
可运行产品行为
→ 生产/测试配置与真实 Route
→ E2E / component tests
→ 调用关系、Flag、权限和版本历史
→ 源代码局部事实
→ 注释和命名线索
```

注释或文件存在只能说明“曾经有过或可能有”，不能单独证明现役。

### 视觉与交互

```text
固定环境下的真实页面截图与交互录像
→ Storybook / visual test
→ 设计稿或产品截图
→ DOM、CSS、组件结构
```

### 目标实现

```text
目标项目维护良好的相似模块
→ 目标项目规范与测试
→ 目标框架官方迁移文档
→ 成熟社区实践
→ 源实现，仅用于回查事实
```

## 6. 试迁移不是进度展示

试迁移用于压力测试：

- 契约是否完整；
- 目标组件和状态边界是否自然；
- Codemod 或适配规则是否可靠；
- 验证裁判能否发现真实回归；
- 工作拆分是否会造成共享资源冲突。

优先选择风险有代表性、边界可控的样本。试迁移代码允许重做；应沉淀的是修正后的规则、蓝图和验证方式。

## 7. 系统性失败要修上游

同类问题在多个页面重复出现时，不继续逐个打补丁：

```text
重复失败
→ 暂停该类批量实施
→ 检查盘点、生命周期、契约、目标蓝图、Codemod 或任务切分
→ 修正上游规则
→ 标记受影响单元
→ 重新验证
```

例如多个页面都出现重复请求、Hydration mismatch 或移动端 overflow，通常不是单个组件问题，而是数据策略、SSR 边界或 Layout 规则错误。

## 8. 完成定义

迁移完成必须同时满足：

- 现役和条件现役能力有明确终态；
- Deprecated / Removed 没有被错误恢复；
- Route、Menu、Deep Link、Flag 和 Permission 可达性正确；
- 关键 UI 状态、交互和响应式行为已验证；
- 视觉差异已修复、批准或解释；
- 目标实现符合目标项目惯例，无阻断 Copy-Smell；
- lint、typecheck、tests、console、a11y 和平台检查有证据；
- 临时 bridge、旧组件、CSS、Flag、asset 和依赖有清理决策；
- 回滚边界可执行。

“代码已复制”“能编译”“页面能打开”都不是独立完成条件。
