# 目标原生前端重建

目标原生重建的目标是：保留批准的用户契约，同时让新代码看起来像目标项目本来就会写出的代码，而不是旧框架换了一层语法。

## 1. 语义防火墙

目标实现从以下输入推导：

```text
源功能与生命周期
+ 视觉 / 交互 / 响应式基线
+ 数据和平台契约
+ 目标项目画像与相似范例
= 目标前端实现蓝图
```

源文件树、源组件树和源 Store 列表只能作为事实证据，不能直接充当目标 TODO。

## 2. 先研究目标项目

至少选择 2～5 个维护良好、近期使用、测试充分的目标范例。完全相似的页面不存在时，分别寻找：

- Route / Page / Layout 范例；
- data fetching / cache / mutation 范例；
- form / validation 范例；
- Component Library / Styling / Token 范例；
- error / permission / loading boundary 范例；
- component、E2E、visual 和 a11y 测试范例。

记录采用和不采用的惯例，避免只搜索与源组件同名的目标文件。

## 3. 目标项目画像

### 工程

- package manager、workspace 和运行命令；
- framework、runtime、bundler 和 TypeScript；
- alias、env、asset、CSS 和 deployment；
- lint、format、typecheck 和 CI。

### 应用结构

- Router、Page、Layout、Feature 和 shared 边界；
- server / client component 或 loader/action；
- error、loading、not-found 和 permission boundary；
- micro-frontend entry 与共享依赖。

### 状态与数据

- Server State、URL State、Global State、Feature State 和 Local State；
- API client、query cache、mutation、retry 和 cancellation；
- form、schema、validation 和 optimistic update；
- event、websocket、polling 和 background refresh。

### UI 与体验

- Design System、Component Library 和 token；
- Styling、theme、typography、icon 和 asset；
- responsive、scroll、portal 和 z-index；
- Accessibility 约定。

### 测试与可观测性

- unit、component、Storybook、E2E 和 visual regression；
- console、network、analytics 和 error monitoring；
- performance budget 和 bundle analysis。

## 4. 目标蓝图

蓝图至少回答：

### Route 与入口

- URL、nested route、layout 和 lazy boundary；
- menu、deep link、redirect、guard 和 permission；
- page enter/leave、scroll restore 和 unsaved changes。

### 页面与组件边界

按产品职责、复用范围、状态所有权和变化频率拆分，而不是按源组件数量拆分。

| 目标单元 | 职责 | State Owner | 复用目标能力 | 验证 |
|---|---|---|---|---|
|  |  |  |  |  |

### 状态模型

明确每项状态属于：Server、URL、Global、Feature、Local、Derived 或 DOM。禁止为了复刻源 Store 而制造第二套全局状态体系。

### 数据流

```text
User Action
→ UI / Form State
→ Query / Mutation / Event
→ Response / Error Mapping
→ Cache / State Update
→ Visual Feedback / Navigation
```

说明 cache key、invalidations、retry、cancel、optimistic rollback 和 permission failure。

### UI 状态

为 Default、Loading、Empty、Error、Partial、Disabled、Read-only、Validation、Submitting、Success、Permission Denied、Offline 和 Overflow 指定实现与验证。

### 视觉与响应式

说明 Page Shell、Grid/Flex、container、spacing、typography、token、theme、icon、scroll owner、portal、z-index 和 breakpoint 行为。未经批准不得因组件库默认样式而改变现役页面。

### 平台与质量

说明 SSR/Hydration、SEO、i18n、analytics、asset、browser support、a11y、tests、console 和 performance。

### 过渡结构

每个 adapter、compat component、bridge route 或 dual-write state 都记录用途、风险、调用方、删除条件和回滚方式。

## 5. 实施时的上下文优先级

```text
1. 目标项目真实代码与范例
2. 目标实现蓝图
3. 源视觉 / 交互 / 响应式基线
4. 迁移契约与生命周期决策
5. 前端跨栈迁移规则
6. 目标框架官方文档
7. 源代码，仅用于回查具体事实
```

回看源代码前先形成具体问题，例如：

> 保存失败时，页面保留用户输入还是重置表单？

不要使用：

> 阅读这个旧组件并完整迁过去。

新事实写回契约或决策记录后再继续实现。

## 6. 禁止的一对一映射

没有产品或契约理由时，默认禁止：

- 一个 `.vue` / Angular Component 对应一个 `.tsx`；
- 一个源 Page 按旧组件树完整复刻；
- 一个 Vuex / Pinia / NgRx module 对应一个目标 Store；
- 一个 watcher / lifecycle 对应一个 `useEffect`；
- 一个 mixin 对应一个 hook；
- 一个旧 CSS / Less 文件对应一个新样式文件；
- 批量复制 utils、base components 和 wrapper；
- 为模仿旧框架建立目标项目不存在的 DI、事件总线或抽象层。

允许保留的是稳定产品概念和公开契约名称，不是偶然实现分解。

## 7. Copy-Smell

出现以下信号时暂停扩展：

- 新目录树与源目录树高度相似；
- 大量源框架术语、文件名和非产品组件名被保留；
- 页面充满用于模拟旧生命周期的 effect；
- 所有状态都进入新的全局 Store；
- 目标项目已有 Router、API client、Form、UI 或 Token 却未复用；
- CSS 通过大量 `!important`、magic number 或 wrapper 强行模拟；
- 新模块的错误、loading、test 和 a11y 方式与目标项目不一致；
- 代码运行正常，但目标技术栈维护者会判断“像另一种框架写出来的”。

先检查问题源头：

```text
契约是否夹带源结构？
目标项目画像是否不足？
蓝图是否从源组件树推导？
跨栈规则是否缺失？
任务是否按文件而不是用户能力拆分？
Codemod 是否越过了语义边界？
```

先修上游，再修实例。

## 8. 目标原生审查

每个迁移单元完成后，从目标项目维护者视角检查：

1. 不知道源项目时，这段代码仍然自然吗？
2. 组件边界来自用户能力和状态所有权吗？
3. Route、data、form、error 和 styling 是否复用目标惯例？
4. 是否保留只为源框架服务的 watcher、service、store 或 wrapper？
5. 是否因为“最佳实践”引入目标项目没有的过度抽象？
6. 业务规则和副作用是否更容易定位与测试？
7. Loading、Error、Permission、responsive 和 a11y 是否是正式设计，而不是补丁？
8. 目标框架高级开发者是否会把它视为正常代码？

存在阻断 Copy-Smell 时，不能标记为已验证。
