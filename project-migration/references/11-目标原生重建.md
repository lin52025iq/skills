# 目标原生重建

## 一、为什么需要“重建”而不是“翻译”

跨项目、跨语言、跨框架迁移时，最常见的失败方式之一，是把源模块的目录、类、函数、DTO、Service、Repository、异常、工具类和调用顺序逐个映射到目标项目。

这种方式通常能较快得到“能编译的目标代码”，但会把源系统的历史结构、框架习惯和技术债一起带入目标项目，最终形成：

- Java 形状的 Go；
- Spring 形状的 Node.js；
- AngularJS 形状的 React；
- ORM Entity 驱动的领域模型；
- 与目标项目现有模块完全不同的第二套架构。

本 Skill 默认采用 **Research → Review → Rebuild** 思路：

```text
研究源系统真实行为
→ 把行为蒸馏成技术无关语义规格
→ 研究目标项目和目标技术栈
→ 审查并设计目标原生方案
→ 从语义规格重建实现
→ 用源系统和验证裁判校验结果
```

源代码用于回答“原系统真实做什么”，不是回答“目标代码应该长什么样”。

---

## 二、建立语义防火墙

源实现与目标实现之间必须经过一层技术无关的“语义防火墙”。

推荐形成三个核心产物：

```text
.migration/迁移语义规格.md
.migration/目标项目画像.md
.migration/目标实现蓝图.md
```

### 2.1 迁移语义规格

只记录需要迁移的系统事实，不复制源代码结构。

至少描述：

- 能力与用例；
- 用户或调用方意图；
- 输入与输出语义；
- 业务规则与例外；
- 状态变化；
- 数据所有权和数据约束；
- 外部依赖和副作用；
- 失败、重试、幂等、事务和一致性；
- 权限与安全；
- 性能和运行要求；
- 需要保留、改变、淘汰的行为；
- 对应证据和验证场景。

默认不要记录：

- “把 `OrderService.java` 改写成 `order_service.go`”；
- “把这个类的 12 个方法逐个实现”；
- “复制原目录结构”；
- “保留所有 helper / manager / util”；
- 只反映源框架实现细节的对象关系。

### 2.2 目标项目画像

在决定目标实现结构前，先单独研究目标项目。

必须优先寻找 2～5 个维护良好、近期活跃、测试充分、与当前能力相近的目标模块作为“目标范例”。

记录：

- 语言、框架和运行时版本；
- 模块/包组织方式；
- 入口与应用编排方式；
- 领域规则组织方式；
- 数据访问和事务方式；
- 错误模型；
- 依赖注入/依赖传递方式；
- 并发与异步模式；
- API、事件和序列化约定；
- 日志、指标、Trace、审计；
- 测试风格与测试目录；
- 已有可复用组件；
- 明确禁止或不推荐的写法；
- 目标语言和框架的惯用实践。

如果目标项目没有明确范例，再参考目标技术栈官方文档和成熟社区实践，而不是回退到源项目结构。

### 2.3 目标实现蓝图

目标实现蓝图从“迁移语义规格 + 目标项目画像”推导，不从源文件树推导。

至少说明：

- 每项能力在目标项目中的落点；
- 目标模块边界；
- 对外契约；
- 核心数据结构；
- 业务规则所在位置；
- 数据访问方式；
- 外部依赖边界；
- 事务、错误、并发和副作用处理；
- 需要复用的目标能力；
- 需要的 adapter / ACL / transitional architecture；
- 本次设计改进；
- 验证方式。

蓝图可以和源项目长得完全不同，只要业务语义和批准的差异能够被验证。

## 三、实施阶段的上下文优先级

开始写目标代码后，使用以下优先级：

```text
1. 目标项目真实代码与已有范例
2. 目标实现蓝图
3. 迁移语义规格
4. 技术栈迁移规则
5. 目标技术栈官方/成熟惯例
6. 源代码（只用于回答尚未确认的具体事实）
```

这意味着：

- 不要一边打开一个源文件，一边创建一个目标文件；
- 不要把源类列表当 TODO；
- 不要按源函数顺序驱动实现；
- 不要先复制再“以后重构”；
- 不要因为源项目有某个抽象就默认目标项目也需要。

需要回看源代码时，先明确一个具体问题，例如：

> “重复支付回调时原系统如何决定是否再次发事件？”

而不是：

> “阅读这个 Service，然后把它迁过去。”

源代码回查结束后，把新事实写回迁移语义规格或业务规则台账，再继续目标实现。

## 四、禁止一对一结构映射

除非有明确业务或契约理由，默认禁止以下做法：

- 一个源文件对应一个目标文件；
- 一个源类对应一个目标类/struct；
- 一个源方法对应一个目标函数；
- 一个源 package/module 对应一个目标 package/module；
- 一个源 Entity 对应一个目标 Entity；
- 一个源异常类对应一个目标错误类型；
- 一个源框架注解对应一个目标框架机制；
- 一个源 helper/util 对应一个目标 helper/util。

允许保留的是稳定的**领域名称和公开契约名称**，而不是偶然的实现分解。

例如 `Order`、`Payment`、`CancelOrder` 如果是真实业务概念可以保留；`BaseManager`、`AbstractCommonService`、`UtilsV2` 等实现名称没有保留义务。

## 五、目标语言必须真正被“使用”

跨语言迁移时，除了语法正确，还要检查目标语言的模型是否被正确采用。

至少研究：

- 数据建模方式；
- 可空/可选值；
- 错误处理；
- 资源生命周期；
- 并发和取消；
- 接口/trait/protocol 使用习惯；
- 泛型和组合方式；
- 包与模块可见性；
- 测试习惯；
- 标准库和成熟生态能力。

典型反模式：

### Java → Go

避免把继承层级、Bean 风格 getter/setter、异常式控制流、过度接口化、复杂 Builder/Factory 原样搬入 Go。

优先研究目标 Go 项目现有的 package 边界、显式 error、组合、context、接口定义位置和测试风格。

### Java/Spring → Node.js/TypeScript

避免复制 Controller → Service → Manager → DAO 的固定层级，避免为了模仿注解容器建立第二套 DI 体系。

优先遵循目标项目现有模块组织、错误模型、异步控制流、Schema/validation 和数据访问方式。

### AngularJS/Vue → React

不要把旧 controller/watch 生命周期机械翻译成 hooks，也不要为了“等价”制造大量 `useEffect`、`useMemo`。

先明确状态所有权、数据流、用户行为和目标项目已有组件模式，再重建组件。

### ORM A → ORM B / SQL

不要按 ORM 方法名做 API 翻译。先确认事务、加载、级联、锁、默认值和约束语义，再选择目标项目最自然的数据访问方式。

## 六、目标范例驱动

实施一个迁移单元前，应先找到目标项目中的相似范例，并明确哪些惯例要复用。

示例：

```text
目标范例：internal/customer/create.go
我们复用：
- use case 组织方式
- typed error
- transaction helper
- repository ownership
- table-driven tests

不复用：
- customer 特有缓存逻辑
```

如果找不到完全相似的模块，可以分别寻找：

- 一个展示模块边界的范例；
- 一个展示数据访问的范例；
- 一个展示错误处理的范例；
- 一个展示测试风格的范例。

禁止仅通过搜索与源类同名的目标文件来决定目标结构。

---

## 七、Copy-Smell：发现这些信号要暂停

出现以下情况时，先暂停实现并重新检查目标设计：

- 目标目录树与源目录树高度相似；
- 大量非领域类名和方法名被原样保留；
- 目标代码仍有明显源框架术语；
- 一个源 Service 被整体改写成一个目标 Service；
- 原有 DTO / Entity / VO 层级被完整复制；
- 原有 helper/util 文件被批量迁入；
- 目标项目已有能力却没有复用；
- 新模块的错误、事务、日志、配置、测试方式和目标项目其他模块不一致；
- 代码能运行，但熟悉目标技术栈的开发者会觉得“像另一种语言写出来的”。

发现 Copy-Smell 后不要立即重构代码，先判断问题源头：

```text
迁移语义规格是否夹带了实现结构？
目标项目画像是否不足？
目标实现蓝图是否从源目录推导？
技术栈规则是否缺失？
任务是否按源文件而不是按能力拆分？
```

先修上游规则，再修目标实现。

## 八、任务应该按能力拆分

错误示例：

```text
MIG-021 迁移 OrderService.java
MIG-022 迁移 OrderRepository.java
MIG-023 迁移 OrderUtils.java
```

更好的示例：

```text
MIG-021 在目标项目实现“创建订单”用例
MIG-022 在目标项目实现“取消订单”规则
MIG-023 接入订单持久化与事务语义
MIG-024 接入 OrderCreated 事件并验证幂等
```

任务输入应引用：

- CAP 能力；
- BR 业务规则；
- 迁移语义规格；
- 目标实现蓝图；
- 目标项目范例；
- 验收场景。

源文件只能作为证据位置，不应成为任务目标。

---

## 九、目标原生审查

每个迁移单元完成后，以“目标项目维护者”视角审查：

1. 如果不知道源系统长什么样，这份代码在目标项目里仍然自然吗？
2. 文件和模块边界来自目标能力还是源目录？
3. 是否使用了目标项目已有能力？
4. 错误、事务、依赖、配置、日志和测试是否符合目标项目惯例？
5. 是否保留了只为源语言/框架服务的模式？
6. 是否有一对一文件/类/方法映射的痕迹？
7. 业务规则是否比源实现更容易定位？
8. 重要副作用是否更容易发现和验证？
9. 是否为了“最佳实践”产生了目标项目本来没有的过度抽象？
10. 目标语言高级开发者是否会把它当作该语言的正常代码？

如果答案显示明显“移植味”，任务状态不能直接标为“已验证”。

## 十、与行为验证的关系

目标原生重建不意味着可以自由改变业务。

验证仍然以：

```text
迁移语义规格
+ 业务规则台账
+ 公共契约
+ 明确批准的行为差异
```

作为裁判。

目标代码结构可以彻底不同，但关键业务输出、状态变化、数据约束、失败语义和必要副作用必须满足裁判。

这使我们可以同时做到：

> **实现结构可以重新设计，业务语义不能靠猜。**

## 十一、社区经验来源

本方法重点吸收以下经验：

- Thoughtworks / Martin Fowler：Research, Review, Rebuild。先研究旧实现，经过业务与架构 Review，再结合目标项目 conventions 和 style guide 重建目标功能，而不是直接把旧代码作为生成模板：https://martinfowler.com/articles/research-review-rebuild.html
- Microsoft Azure Architecture Center：Anti-Corruption Layer。新系统不应因为需要兼容遗留系统而让自己的设计被旧系统语义和实现方式污染：https://learn.microsoft.com/azure/architecture/patterns/anti-corruption-layer
- Martin Fowler / Thoughtworks：Patterns of Legacy Displacement。遗留替换应围绕目标结果和增量能力迁移组织，而不是围绕旧系统技术结构组织：https://martinfowler.com/articles/patterns-legacy-displacement/
- Martin Fowler：Legacy Seam。通过稳定 seam 隔离遗留依赖、建立测试和逐步重定向到新模块：https://martinfowler.com/bliki/LegacySeam.html

这些资料用于指导迁移方式，不要求机械套用任何具体架构模式。
