# 迁移边界与目标架构

## 一、目标

确定“哪些能力真正需要进入目标项目”，以及“这些能力应该怎样融入目标项目现有架构”。

迁移边界的单位是业务能力和契约，不是目录、类或表。

## 二、能力分类

对源能力使用以下分类：

### 迁移

目标项目应拥有该能力，需要建立目标实现。

### 复用

目标项目已经存在等价能力，应使用现有实现，不重复建设。

### 适配

能力仍由原系统、第三方或其他服务提供，目标项目只需通过适配层访问。

### 替换

业务能力保留，但技术实现应使用目标技术栈已有方式替换。

### 保留

当前迁移阶段仍留在源系统，可能通过远程调用继续使用。

### 淘汰

经证据确认已经不再需要。

### 待确认

当前证据不足，不应提前决定。

## 三、识别隐藏边界

特别检查以下问题：

- 源模块是否直接写其他业务域的数据表；
- 其他模块是否绕过公开接口直接调用源模块内部实现；
- 是否存在共享数据库；
- 是否通过缓存共享隐式状态；
- 是否存在多个生产者写同一业务数据；
- 是否存在多个消费者改变同一状态；
- 定时任务是否补充主流程行为；
- 特性开关是否让不同用户走不同实现；
- 是否存在历史兼容逻辑仍在生效。

## 四、判断目标项目已有能力是否真的“等价”

不要只因为名称相同就复用。

至少比较：

- 输入；
- 输出；
- 错误语义；
- 状态变化；
- 数据一致性；
- 权限；
- 幂等；
- 时序；
- 外部副作用；
- 性能和容量；
- 生命周期。

如果只能覆盖部分行为，应标记为“适配”或“部分复用”，并明确缺口。

## 五、理解目标架构

在设计新代码之前，先研究目标项目：

- 一个相似功能是如何组织的；
- 入口层如何定义；
- 业务逻辑放在哪里；
- 数据访问接口如何抽象；
- 错误如何表达和映射；
- 事务如何创建和传播；
- 消息如何发布和消费；
- 配置如何注入；
- 测试如何组织；
- 日志和指标如何记录；
- 权限在哪里处理。

优先参考目标项目中维护良好、近期仍活跃、经过测试的相似模块，不要复制明显遗留的局部模式。

## 六、建立源概念到目标概念映射

映射描述的是语义，不是文件名。

示例：

```text
源：框架事务注解
目标：应用服务边界内显式事务执行器
语义：同一用例内关键数据库写入必须原子提交
```

```text
源：本地用户 DAO
目标：目标项目已有用户服务客户端
语义：订单模块不再拥有用户主数据，只消费用户查询能力
```

```text
源：进程内事件
目标：持久化消息或领域事件
语义：订单创建成功后通知后续处理，但投递失败不能造成订单主事务不一致
```

## 七、什么时候需要适配层或防腐层

出现以下情况时优先考虑：

- 源数据模型与目标领域模型差异很大；
- 第三方 SDK 侵入业务代码；
- 新旧系统需要并行；
- 远程调用协议与目标内部接口不同；
- 迁移期间需要同时支持新旧格式；
- 外部错误模型不适合直接传播到目标业务层。

适配层的目标是隔离变化，不是增加形式化层次。

## 八、避免“迁移式重复建设”

发现目标项目已有能力时，先比较而不是重写。

典型重复：

- 两套用户模型；
- 两套权限判断；
- 两套日志规范；
- 两套错误码体系；
- 两套消息客户端；
- 两套数据库事务封装；
- 两套配置加载方式。

迁移的目标应该降低长期系统复杂度，而不是把两个项目的历史同时保留。

## 九、边界阶段完成标准

对迁移范围内的每个关键能力都能回答：

- 它是否进入目标项目；
- 如果不进入，未来由谁提供；
- 目标项目通过什么契约访问；
- 数据所有权属于谁；
- 是否存在临时并行方案；
- 最终态是什么；
- 如何验证迁移后的等价性或已批准差异。
