# 前端迁移策略、共存与回滚

本文用于选择迁移拓扑，并把“如何退出旧实现”设计成可执行方案。页面、模块、整应用、Router、SSR、组件库或微前端迁移应在形成蓝图时读取。

## 1. 策略选择信号

不要凭偏好选择 Big Bang 或 Strangler。先记录：

- 迁移单位是否能被 Route、Flag、adapter、package 或部署边界隔离；
- 源和目标能否同时运行；
- 是否涉及写操作、身份、支付、SEO、SSR 或高流量页面；
- 内部调用方和外部 Deep Link 数量；
- 功能、截图和运行裁判是否可信；
- 目标项目是否已具备接入点；
- 兼容层对 bundle、性能和维护的成本；
- 一次发布失败的恢复时间；
- 数据和 API 是否允许 old/new 同时读取或写入；
- 团队是否能在迁移期维护两个实现。

未知信号按风险处理，不按乐观默认处理。

## 2. 六种策略

## 2.1 原地增量升级

**适用：**

- 同一仓库和部署单元；
- 官方或项目已有兼容升级路径；
- 可按依赖、页面或配置逐步推进；
- 旧、新 API 能短期共存；
- 每步都能构建和回归。

**示例：** JavaScript 逐目录启用 TypeScript、Webpack 到 Vite 的兼容过渡、组件库分批替换。

**必要护栏：**

- 每批次只有一个主要变化轴；
- 锁定 package manager 与运行时版本；
- 旧配置和新配置并存时间有上限；
- 每步能回退到上一个可发布 commit。

**不适用：** 目标架构与旧架构无法共存，或升级会一次改变 Router、SSR、状态和设计系统多个轴。

## 2.2 Route / Feature Strangler

**适用：**

- 页面或功能可通过 Route、导航、反向代理、feature flag 或模块注册切换；
- 旧应用必须继续承载未迁移功能；
- 希望按页面或用户群逐步放量。

典型结构：

```text
Entry / Router / Shell
├── old implementation
└── new implementation
       ↑ flag / route / cohort / percentage
```

**关键决策：**

- 谁拥有顶层 Route 和导航；
- 认证、locale、theme、analytics 和错误边界如何共享；
- Deep Link、back/forward、scroll restoration 是否一致；
- 新旧页面间跳转是否刷新整页；
- 旧 CSS 或全局事件是否污染新页面；
- 什么时候删除路由分流层。

## 2.3 Parallel / Shadow Run

**适用：**

- 高风险读取、SSR 输出、权限判断或计算结果需要 old/new 对照；
- 新实现可以在不影响用户的情况下接收同样输入；
- 差异可脱敏记录并归类。

前端常见方式：

- 同一 fixture 同时渲染旧、新 Story/页面并截图；
- 同一请求数据驱动旧、新 formatter/selector 并比较输出；
- SSR 请求在后台生成新 HTML/metadata 与旧结果比较；
- 新 Route 对内部用户或测试 cohort 开启，外部仍走旧实现。

**禁止：** 对支付、创建、删除等写操作无保护地双写。需要幂等、隔离数据或只影子执行可逆计算。

## 2.4 Adapter / Branch by Abstraction

**适用：**

- 组件库、API Client、状态接口或运行时服务调用方很多；
- 无法一次修改全部调用方；
- 可以定义稳定的目标接口，让新旧实现短期互换。

```text
Callers
  ↓
Stable target-facing interface
  ├── legacy adapter
  └── new implementation
```

Adapter 只翻译边界：props、事件、数据模型、错误、主题或生命周期。不要在 adapter 中继续堆产品业务规则。

每个 adapter 必须记录：owner、创建原因、调用方数量、性能成本、删除 Gate 和最晚复审日期。

## 2.5 Micro-frontend Bridge

**适用：**

- 独立团队、部署、运行时或业务边界真实存在；
- Shell 可以提供认证、导航、locale、theme 与观测能力；
- 迁移周期较长，必须让不同技术栈并存。

在采用前验证：

- bundle 重复和启动成本；
- CSS、DOM、事件和全局变量隔离；
- 共享依赖版本；
- Route 与浏览器历史；
- 错误隔离和降级；
- 本地开发、测试和发布复杂度；
- 最终是永久架构还是临时桥接。

不要仅因为跨框架就默认引入微前端。

## 2.6 一次性替换

**只在以下条件同时较强时采用：**

- 迁移单位小、边界封闭；
- 依赖和调用方可枚举；
- 功能与视觉裁判可信；
- 数据契约稳定；
- 发布窗口和回滚简单；
- 不需要长期双栈维护。

一次性替换不等于无计划重写。仍需基线、试迁移、回滚 commit/部署和发布后监控。

## 3. 决策矩阵

| 信号 | 原地升级 | Strangler | Parallel | Adapter | Micro-FE | 一次替换 |
|---|---:|---:|---:|---:|---:|---:|
| 同仓且升级路径清晰 | 强 | 中 | 弱 | 中 | 弱 | 中 |
| Route 可独立切换 | 中 | 强 | 强 | 弱 | 强 | 中 |
| 调用方多、接口稳定 | 中 | 中 | 中 | 强 | 中 | 弱 |
| 高风险且能对照 | 弱 | 强 | 强 | 中 | 中 | 弱 |
| 独立部署/团队边界 | 弱 | 中 | 中 | 弱 | 强 | 弱 |
| 迁移单位小且裁判强 | 强 | 中 | 弱 | 中 | 弱 | 强 |
| 目标和源无法共存 | 弱 | 弱 | 弱 | 弱 | 中 | 强 |
| 回滚必须分钟级 | 中 | 强 | 强 | 强 | 中 | 中 |

选择结果不是单一标签。复杂迁移通常组合：

```text
应用级 Route Strangler
+ 组件库 Adapter
+ 高风险 selector Parallel Compare
+ 构建工具原地升级
```

组合时明确每种策略作用在哪个边界，避免形成多层永久兼容结构。

## 4. 共存边界

### 4.1 Shell 所有权

新旧实现并存时，顶层 Shell 只应有一个 owner。明确：

- HTML document、head、metadata；
- Router 和 history；
- auth/session；
- locale/timezone；
- theme/design token；
- analytics/error reporting；
- global keyboard shortcut；
- toast/modal portal；
- scroll container。

若两边都初始化这些能力，容易出现重复埋点、双重导航、z-index 冲突、样式污染和 session 不一致。

### 4.2 数据与缓存

明确每个资源的 owner：

- old/new 是否共用 API；
- cache key、stale time、normalization 是否一致；
- 切换页面后缓存是否可复用；
- mutation 后哪一边负责 invalidate；
- optimistic update 失败如何恢复；
- SSR cache 与 client cache 如何衔接。

### 4.3 CSS 与资源

共存期检查：

- global reset 和基础元素选择器；
- CSS Modules/Tailwind class collision；
- font 和 icon 重复加载；
- portal、overlay、z-index；
- asset public path/base URL；
- Shadow DOM 或样式隔离是否真的必要。

### 4.4 导航

old/new 跳转至少验证：

- direct URL、刷新和 Deep Link；
- browser back/forward；
- query/hash；
- auth redirect；
- 404/403；
- scroll restoration；
- analytics page view；
- SSR 与客户端首屏一致性。

## 5. 切流计划

每个迁移单位填写：

| 项目 | 内容 |
|---|---|
| 切流边界 | Route、Flag、cohort、package、proxy 或部署 |
| 默认路径 | 切流前用户走哪一边 |
| 开关 owner | 谁有权限切换 |
| 放量顺序 | 内部 → 小流量 → 目标 cohort → 全量 |
| 观测指标 | error、conversion、latency、hydration、console、visual diff 等 |
| 对照窗口 | 使用现有 SLO/业务周期推导，不写无依据数字 |
| 回滚动作 | 一条明确、已测试的命令或开关步骤 |
| 数据恢复 | 是否需要回滚写入、cache 或 schema |
| 清理 Gate | 何时删除旧 Route、Flag、adapter 和依赖 |

### 5.1 渐进放量

优先使用项目现有 feature flag、路由和发布能力，不为迁移单独再造控制面。

每个阶段只改变一个主要变量，例如流量比例或用户 cohort。变更后观察足够覆盖关键业务周期的窗口，再扩大范围。

### 5.2 开关安全性

- 默认值在配置缺失时必须安全；
- 服务端和客户端对同一 Flag 解释一致；
- SSR 首屏和 hydration 不能因为 Flag 不一致切到不同实现；
- 开关事件记录版本、操作者和时间；
- 紧急回滚不依赖重新构建客户端包时更安全。

## 6. 回滚触发与演练

### 6.1 触发来源

根据项目已有基线和 SLO 定义，而不是复制固定阈值：

- 关键用户流程失败率或转化异常；
- 5xx、JS runtime、hydration、chunk load error；
- 权限或身份错误；
- 页面空白、不可导航或 Deep Link 失效；
- 写操作重复、丢失或不可恢复；
- 视觉阻断导致主要操作不可用；
- p75/p95 交互或加载明显超出基线；
- Accessibility 阻断项；
- old/new 对照出现未批准的高严重度差异。

### 6.2 回滚等级

| 等级 | 动作 |
|---|---|
| Slice rollback | 关闭单 Route/Feature，恢复旧实现 |
| Release rollback | 回退部署或 commit |
| Dependency rollback | 恢复锁文件和工具链配置 |
| Data remediation | 修复或补偿写入、cache、索引和事件 |
| Full cutover abort | 停止后续批次，恢复默认 old 路径 |

### 6.3 演练

发布前至少在可控环境演练：

1. 切到新实现；
2. 产生可识别请求或会话；
3. 触发回滚；
4. 验证旧实现恢复；
5. 验证 Route、session、cache、数据和监控；
6. 记录完成时间、人工步骤和失败点。

“理论上可以 git revert”不等于回滚已验证。

## 7. 兼容层和旧实现清理

### 7.1 临时结构清单

| 结构 | 用途 | 成本/风险 | Owner | 删除 Gate |
|---|---|---|---|---|
| Feature Flag | old/new 切流 | 分支复杂度 |  | 全量稳定并过对照窗口 |
| Adapter | 调用方渐迁 | 双模型维护 |  | 调用方为零 |
| Proxy/Route 分流 | 页面渐迁 | 延迟与配置风险 |  | 全部 Route 归目标 |
| Legacy CSS | 视觉兼容 | 污染与重复 |  | 旧页面为零且截图通过 |
| Duplicate dependency | 双栈运行 | bundle/安全成本 |  | 旧实现删除 |

### 7.2 删除前检查

- 搜索真实调用方、动态 import、Route 注册、Flag 和文档；
- 验证 Deep Link 和回退路径不再依赖旧代码；
- 删除 skip/disabled 的迁移临时测试；
- 删除旧 asset、字体、CSS、polyfill 和环境变量；
- 更新监控、所有权和运行手册；
- 跑完整目标回归并重新盘点依赖。

### 7.3 永久保留的兼容层

只有在它表达长期边界而非迁移历史时保留，例如稳定的外部 API adapter。重命名并补充正式测试、owner 和文档，避免继续以 `legacy`、`temp`、`migration` 名义永久存在。
