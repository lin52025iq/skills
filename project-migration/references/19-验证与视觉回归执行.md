# 前端迁移验证与视觉回归执行

本文用于建立迁移裁判、运行浏览器验证、分类差异，并给出发布证据。开始代表性试迁移、审查迁移 PR 或准备切流时读取。

## 1. 裁判先行

迁移裁判必须能回答：

- 源实现当前做什么；
- 目标实现应该保持或批准改变什么；
- 如何用同一标准判断 old/new；
- 哪种差异是产品回归，哪种是环境噪声；
- 裁判本身是否真的能失败。

现有测试若断言源组件内部结构、类名、Store shape 或私有实现，不足以直接充当迁移裁判。优先提升到：

- 用户结果；
- Route 和导航；
- accessible role/name；
- 公共 props/event/API 契约；
- 截图和布局；
- 数据与副作用；
- 错误、权限和恢复。

在试迁移阶段可故意改变一个已知行为，确认裁判会失败，然后恢复。这能避免“永远绿色”的无效测试。

## 2. 验证矩阵

按风险选择，不要求每个组件运行所有层级。

| 风险/能力 | Unit | Component | Integration | E2E | Visual | A11y | Perf/Runtime |
|---|---:|---:|---:|---:|---:|---:|---:|
| 纯 formatter/selector | 强 | 弱 | 中 | 弱 | 弱 | 弱 | 弱 |
| 交互组件 | 中 | 强 | 中 | 中 | 强 | 强 | 中 |
| 表单与写操作 | 中 | 强 | 强 | 强 | 中 | 强 | 中 |
| Route/权限/Deep Link | 弱 | 中 | 强 | 强 | 中 | 中 | 强 |
| 响应式页面 | 弱 | 中 | 中 | 强 | 强 | 强 | 中 |
| SSR/hydration | 中 | 中 | 强 | 强 | 中 | 中 | 强 |
| 组件库/Theme | 中 | 强 | 中 | 中 | 强 | 强 | 强 |
| 构建工具 | 弱 | 中 | 强 | 强 | 中 | 弱 | 强 |

“强”表示通常必须；“中”取决于影响面；“弱”仅在有特殊风险时。

## 3. 可重复环境

视觉和行为比较至少固定适用项：

- browser 与版本；
- viewport、deviceScaleFactor；
- OS/容器和字体；
- locale、timezone、number/date format；
- theme、color scheme、reduced motion；
- 登录身份、权限和 Feature Flag；
- API fixture、时间、随机数和 ID；
- animation、transition、skeleton timing；
- 网络条件和 cache；
- SSR/CSR 入口。

不要直接把不同 OS、字体、数据和动画时刻的像素差当成产品回归。

### 3.1 Fixture 原则

- 数据最小但覆盖真实边界；
- 包含空、长文本、Unicode、错误、无权限和极值；
- 脱敏且可提交；
- 不依赖即将过期的生产账号；
- 明确 fixture 版本和关联契约；
- 写操作使用隔离环境、幂等 key 或可清理数据。

## 4. 浏览器侦察与 Playwright

采用“先侦察，再行动”：

```text
启动或连接应用
→ 导航并等待真实稳定条件
→ 截图、DOM、console、network 侦察
→ 使用发现的 role/name/test id 定位
→ 执行交互
→ 断言用户结果
```

### 4.1 稳定等待

不要无条件依赖固定 sleep。优先等待：

- 明确页面元素；
- 请求完成或 mock 响应；
- loading 消失；
- URL/Route 变化；
- 动画结束；
- 页面自定义 ready signal。

`networkidle` 对持续连接、analytics 或轮询页面可能永不稳定；根据项目行为选择条件。

### 4.2 Selector 优先级

```text
role + accessible name
→ label/text（稳定产品文案）
→ 项目现有 test id
→ 稳定 CSS/DOM 属性
→ 脆弱层级或 nth selector（最后手段）
```

迁移不能为了让测试通过而给每个元素加入无语义 ID；优先改善语义和可访问名称。

### 4.3 浏览器证据

每个关键流程保存适用项：

- 起始条件；
- 操作步骤；
- 最终 URL/状态；
- 截图；
- console error/warning；
- failed request；
- trace/video；
- old/new 差异结论。

机器产物放 `.migration/results/`，报告只引用路径和结论，避免把大量二进制或日志贴进主文档。

## 5. 功能与交互

### 5.1 页面状态矩阵

至少覆盖适用状态：

```text
Default
Loading / Skeleton
Empty
Error / Retry
Partial / Stale
Disabled / Read-only
Validation Error
Submitting
Success
Permission Denied
Offline / Timeout
Long Content / Overflow
```

### 5.2 导航

验证：

- 菜单、按钮、Tab、Modal/Drawer 入口；
- direct URL 和刷新；
- params/query/hash；
- redirect、404、403；
- back/forward；
- Deep Link；
- scroll restoration；
- unsaved changes；
- auth return URL。

### 5.3 表单和写操作

- 字段初值和格式；
- validation 时机与文案；
- keyboard、focus 和 tab order；
- double submit；
- loading/disabled；
- server error；
- optimistic rollback；
- success feedback 与后续导航；
- 刷新后数据一致；
- 权限和幂等。

### 5.4 交互细节

- hover/focus-visible/pressed/selected；
- modal focus trap、Escape、outside click 和 focus return；
- dropdown、combobox、日期和虚拟列表键盘行为；
- drag/drop、resize、scroll、sticky；
- debounce/throttle/cancellation；
- mobile touch target 和 virtual keyboard；
- reduced motion。

## 6. 视觉回归

### 6.1 基线粒度

组合使用：

- component screenshot：定位组件和状态；
- page screenshot：布局和跨组件影响；
- viewport matrix：响应式；
- element screenshot：减少不相关噪声；
- 人工对照：品牌、层级、动效和主观质量。

### 6.2 截图场景

每个关键页面选择高价值场景，而不是只截默认态：

- desktop 默认与长内容；
- mobile navigation；
- loading/empty/error；
- modal/dropdown/open state；
- validation；
- permission/read-only；
- dark theme/locale（如果真实支持）。

### 6.3 差异定位顺序

视觉漂移时先检查全局原因：

1. 字体是否加载和一致；
2. reset/global CSS/import order；
3. container width、root height、scroll owner；
4. theme/token 与 CSS variable；
5. browser/viewport/device scale；
6. 数据、locale、timezone；
7. animation 和异步稳定；
8. 最后才检查局部 margin/padding。

### 6.4 阈值

- 优先消除环境噪声；
- 阈值必须根据既有项目实践和差异类型设置；
- 不通过持续增大阈值掩盖真实回归；
- 文本抗锯齿噪声可用稳定容器、字体和局部截图处理；
- 布局、遮挡、可读性和操作区域差异通常不能靠阈值接受。

### 6.5 批准变化

批准 redesign 或组件库差异时：

- 保存 old、新预期和批准依据；
- 更新 baseline，而不是删除截图测试；
- 说明是否影响功能、响应式和 Accessibility；
- 确保其他未批准区域仍与源基线比较。

## 7. Accessibility、运行与性能

### 7.1 Accessibility

自动化和人工至少覆盖：

- semantic HTML 和 landmark；
- accessible name/description；
- keyboard 完整操作；
- focus order、可见性和恢复；
- form label/error association；
- modal/dialog；
- ARIA 状态；
- contrast；
- zoom/reflow；
- reduced motion；
- 动态更新公告。

自动 axe 类检查不能证明键盘流程、焦点体验和文案清晰度。

### 7.2 Runtime

浏览器验证同时检查：

- uncaught error / unhandled rejection；
- hydration mismatch；
- failed chunk / asset / API；
- duplicate analytics 或 event listener；
- memory/listener 泄漏的明显信号；
- React/Vue/Angular/Svelte 框架 warning；
- CSP、cookie、CORS 和 mixed content；
- source map 与错误上报。

### 7.3 性能

以现有预算和基线为主：

- route bundle 和重复依赖；
- LCP、INP、CLS 或项目已有 Web Vitals；
- 首屏请求数和关键 waterfall；
- hydration/interaction ready；
- list/table 渲染；
- image/font；
- cache 命中与预取；
- SSR latency 和 streaming。

迁移带来的性能改善不能抵消功能或视觉回归；性能下降必须解释并获得接受。

## 8. 差异分类和报告

每项差异使用：

| 字段 | 内容 |
|---|---|
| ID | `DIFF-FE-*` |
| 场景 | Route、viewport、状态、账号 |
| Old | 源结果与证据 |
| New | 目标结果与证据 |
| 类型 | 功能 / 视觉 / 交互 / 响应式 / A11y / Runtime / Perf |
| 严重度 | Blocker / High / Medium / Low |
| 分类 | 必须修复 / 批准变化 / 环境噪声 / Unknown |
| 根因 | 代码、环境、fixture、基线或待查 |
| 处理 | 修复、更新基线、接受或阻断 |
| Owner | 负责人 |

### 8.1 严重度参考

- **Blocker**：核心流程不可用、权限/数据错误、白屏、不可回滚；
- **High**：主要用户流程、关键响应式或 Accessibility 受损；
- **Medium**：次要流程或明显视觉偏差，有可行绕过；
- **Low**：不影响任务完成的细节或环境噪声候选。

### 8.2 验证报告

最终至少列出：

- 命令、环境和 commit；
- 通过/失败/跳过及原因；
- 页面和状态覆盖矩阵；
- visual baseline 路径；
- runtime/console/network 结论；
- 未关闭差异；
- 允许发布与否；
- 回滚演练结果。

“测试通过”不是证据的全部，必须说明测试覆盖了哪些产品契约。

## 9. 发布 Gate

允许切流前确认：

- 裁判在源基线和目标实现上都可信；
- Blocker/High 的未批准差异为零；
- 关键账号、权限、viewport 和 UI 状态已覆盖；
- build、type、相关 test、E2E、visual、A11y 和 runtime 检查完成；
- 适用性能不超出接受范围；
- Flag/Route/proxy 默认值和回滚已演练；
- 监控能区分 old/new；
- 数据或 cache 恢复方案明确；
- 旧实现暂不删除，直到对照窗口和清理 Gate 满足。

若某项无法执行，报告原因、替代证据和剩余风险，由明确 owner 接受；不要把“未验证”写成“通过”。
