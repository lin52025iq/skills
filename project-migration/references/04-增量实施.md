# 增量实施方法

## 一、实施前检查

每次开始一个迁移任务前：

1. 读取当前状态；
2. 读取任务涉及的能力和业务规则；
3. 读取相关技术栈迁移规则；
4. 检查目标项目当前代码，确认没有与计划冲突的新变化；
5. 明确本任务的修改边界和验收方式。

## 二、优先保持行为

迁移第一阶段默认不做以下事情：

- 改业务规则；
- 顺便调整接口；
- 顺便重命名大量领域概念；
- 顺便替换所有基础设施；
- 顺便做全项目格式或结构重构；
- 为“更优雅”改变错误或状态语义。

如果目标架构确实要求结构变化，应保持可观察业务行为不变，并记录架构决策。

## 三、实施中的证据回流

编码过程中经常会发现源理解不完整。

发现新事实时：

1. 判断它是证据、推断还是未知；
2. 更新源系统理解或业务规则台账；
3. 检查是否影响迁移边界；
4. 检查是否影响其他任务；
5. 必要时调整计划；
6. 再继续当前实现。

不要把新发现只留在代码注释或临时对话中。

## 四、限制修改范围

优先小范围修改。

如果当前任务突然需要修改大量无关模块，应先判断：

- 迁移边界是否定义错误；
- 目标项目是否缺少稳定接口；
- 是否正在复制源项目耦合；
- 是否应该先增加适配层；
- 是否应拆出新的前置任务。

## 五、跨技术栈实现

跨语言或框架时，按照“语义 → 目标惯例”实现。

例如：

- 源框架通过异常表达业务失败，目标项目可能使用显式结果或类型化错误；
- 源 ORM 自动管理事务，目标项目可能需要显式事务边界；
- 源语言对象默认可空，目标语言可能需要明确指针或可选类型；
- 源运行时默认单线程语义，目标实现可能引入并发安全问题。

任何这种差异都先写入技术栈迁移规则，再实施。

## 六、先最小正确，再优化

每个迁移单元优先完成：

1. 正确领域语义；
2. 正确数据行为；
3. 正确外部契约；
4. 正确失败行为；
5. 对应验证。

性能优化、抽象提炼和内部美化可以后置，除非它们是满足目标系统基本要求所必需。

## 七、提交级思维

即使不直接操作版本控制，也应让每个任务具备“可成为一个小提交”的边界。

理想的迁移提交：

- 目的单一；
- 测试与实现同批出现；
- 不混入无关格式化；
- 可独立审查；
- 回退后不会留下半套逻辑。

## 八、完成后立即更新状态

一个任务验证通过后立即更新：

- 当前状态；
- 能力迁移矩阵；
- 业务规则台账；
- 风险与未知项；
- 验证报告中的相关证据。

不要等整个迁移结束后再补文档，因为那会丢失过程中的事实和决策。
