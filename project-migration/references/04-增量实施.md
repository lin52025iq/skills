# 增量实施方法

## 一、实施前检查

每次开始迁移任务前：

1. 读取当前状态；
2. 读取任务涉及的能力、业务规则和设计改进项；
3. 读取相关技术栈迁移规则；
4. 检查源、目标项目是否出现让计划失效的新变化；
5. 明确修改边界、目标设计和验收方式。

## 二、保留业务语义，不机械复制结构

迁移第一阶段默认不改变未经批准的业务行为，但允许直接实现已经明确的目标原生结构。

也就是说，不要求：

```text
先复制源坏设计
→ 验证
→ 再重构
```

如果业务语义已有安全网、源设计问题已有证据、目标方案已明确，可以直接：

```text
理解源语义
→ 目标原生实现
→ 行为验证
```

## 三、受控现代化的执行规则

每项设计变化实施前确认：

- 源设计问题是什么；
- 有什么证据；
- 为什么本次处理，而不是后置；
- 目标项目已有何种惯例；
- 是否改变用户可观察行为；
- 如何证明迁移语义仍成立；
- 是否引入新的长期抽象；
- 如果是临时抽象，何时删除。

如果无法回答，不把它混进当前迁移任务。

## 四、实施中的证据回流

发现新事实时：

1. 判断是证据、推断还是未知；
2. 更新源系统理解、业务规则或设计改进台账；
3. 检查是否影响迁移边界；
4. 检查是否影响目标架构或迁移规则；
5. 检查是否影响其他已完成任务；
6. 必要时调整计划并重新验证。

不要把新发现只留在代码注释或当前对话。

## 五、限制修改范围

当前任务突然需要修改大量无关模块时，先判断：

- 边界是否定义错误；
- 目标项目是否缺少稳定接口；
- 是否正在复制源项目耦合；
- 是否应该使用 adapter / ACL / abstraction；
- 是否正在以“最佳实践”为名扩大范围；
- 是否应拆出新的前置任务。

## 六、跨技术栈实现

按照“语义 → 目标项目惯例 → 目标技术栈惯例”实现。

例如：

- 源框架用异常表达业务失败，目标项目可能使用类型化错误；
- 源 ORM 自动事务，目标项目可能要求显式事务边界；
- 源对象默认可空，目标语言可能要求显式 Optional / pointer / result；
- 源代码通过继承复用，目标语言可能更适合组合；
- 源框架把认证、重试或序列化隐式放在中间件中，目标实现必须显式确认等价机制。

任何高影响差异先写入迁移规则，再扩大实施。

## 七、先最小正确，再做有价值的优化

每个迁移单元优先保证：

1. 正确业务语义；
2. 正确数据行为；
3. 正确外部契约；
4. 正确失败行为；
5. 合理目标结构；
6. 对应验证。

性能优化、抽象提炼和内部美化只有在有明确问题、目标项目惯例或迁移收益时才做。

## 八、重复失败不是普通 TODO

同类失败反复出现时，暂停该类实施。

把问题上升到：

```text
源理解
目标架构
迁移规则
设计改进规则
验证裁判
任务拆分
```

修正后重新检查已经实施的同类单元。

## 九、提交级思维

理想迁移提交：

- 目的单一；
- 测试与实现同批出现；
- 设计改进与来源问题可追踪；
- 不混入无关格式化；
- 可独立审查；
- 回退后不会留下半套逻辑。

## 十、完成后立即更新状态

任务验证通过后更新：

- 当前状态；
- 能力迁移矩阵；
- 业务规则台账；
- 设计改进台账；
- 差异与失败队列；
- 风险与未知项；
- 验证报告中的相关证据。
