# 设计现代化与代码质量

## 一、目标

迁移后的代码不应只是“功能搬过来了”，还应成为目标项目中自然、清晰、可维护的一部分。

但“优化设计”不能成为无边界重写的理由。本方法要求：

```text
业务语义有证据
+ 设计问题有证据
+ 目标方案符合目标项目惯例
+ 变化可以验证
= 允许在迁移中现代化
```

## 二、先区分行为与设计

### 必须保持的业务语义

通常包括：

- 核心业务规则；
- API/RPC/事件契约；
- 数据含义；
- 权限；
- 金额、状态和时间语义；
- 幂等、重试、事务和一致性；
- 用户或上下游可观察的必要副作用。

### 不需要原样保持的实现设计

通常包括：

- 文件和目录结构；
- 类数量；
- 框架注解；
- ORM 使用方式；
- 源项目的基础设施封装；
- 过度耦合的内部调用；
- 历史兼容层；
- 命名和局部抽象。

### 疑似错误业务行为

不能以“重构”为名静默改变。把它作为明确的行为变更项，要求依据、影响分析和验证。

## 三、目标原生设计的证据优先级

选择目标实现方式时，优先参考：

1. 目标项目中维护良好、近期活跃、测试充分的相似模块；
2. 目标项目明确的架构和编码规范；
3. 目标技术栈官方或成熟社区惯例；
4. 通用设计原则；
5. 源项目结构。

源项目“以前就是这么写的”不能成为目标设计的充分理由。

## 四、重点识别的源设计问题

### 4.1 模块职责混乱

信号：

- 一个 Service 同时处理领域规则、数据库、HTTP、缓存、消息和格式转换；
- 同一个模块拥有多个不相关的变化原因；
- 修改一个小规则需要跨大量无关代码。

目标：按稳定业务职责和目标项目边界重新组织，而不是按源类一对一复制。

### 4.2 业务规则散落或重复

信号：

- 同一状态规则在 Controller、Service、Job、Consumer 多处重复；
- 依赖魔法数字、字符串和条件分支；
- 测试和生产代码各自维护一份规则。

目标：把同一业务事实集中到容易发现、容易测试的稳定位置，并消除不必要重复。

不要为了“领域建模”强制增加大量类型。只有能降低歧义和重复时才抽象。

### 4.3 跨层和反向依赖

信号：

- 领域逻辑直接依赖 Web 框架类型；
- 核心业务直接操作 ORM Session、HTTP Request、消息 SDK；
- 基础设施层反过来决定业务流程；
- 包之间存在循环依赖。

目标：让稳定的业务逻辑尽量不依赖易变化基础设施，通过目标项目已有接口、adapter 或边界隔离变化。

### 4.4 数据模型泄漏

信号：

- 数据库 Entity 同时作为 API DTO 和领域对象；
- 表结构变化直接影响全部业务代码；
- 外部系统 DTO 在核心逻辑中传播。

目标：只有当不同模型确实承载不同语义时才分离模型。避免“每层一个 DTO”的形式主义复制。

### 4.5 隐式副作用

信号：

- 一个看似查询的方法会写数据库或发消息；
- 保存操作隐式触发级联；
- 日志、审计、消息发布和远程调用隐藏在通用工具里；
- 错误处理依赖全局拦截器但迁移后不再存在。

目标：让重要副作用在用例或稳定边界中可发现，并能独立验证。

### 4.6 事务和一致性边界不清

信号：

- 事务由框架注解偶然覆盖；
- 多个数据库写入不知道是否原子；
- 消息与数据库提交顺序不明确；
- 重试可能重复产生副作用。

目标：在目标实现中明确事务、一致性和幂等边界，而不是机械寻找同名注解。

### 4.7 错误模型混乱

信号：

- 所有错误都是字符串或统一异常；
- 业务错误和系统错误混在一起；
- Controller 依赖异常文本决定状态码；
- 可重试与不可重试错误不可区分。

目标：采用目标项目已有错误模型，保持公开错误契约，同时让内部错误分类更清晰。

### 4.8 全局状态和难测试依赖

信号：

- 静态单例、全局变量、隐藏 Service Locator；
- 测试只能启动整个应用；
- 时间、随机数、外部客户端无法控制。

目标：在不制造接口爆炸的前提下，让关键依赖可替换、关键业务规则可隔离验证。

### 4.9 重复基础设施和重复能力

信号：

- 迁入目标项目后又出现第二套 HTTP client、日志、配置、事务、鉴权或消息封装；
- 目标项目已有等价业务能力但仍复制源实现。

目标：优先复用目标项目稳定能力，必要时加轻量适配层。

### 4.10 历史兼容和死代码

信号：

- 已失效 Feature Flag；
- 永远不会进入的旧版本分支；
- 只针对已经下线客户或协议的兼容逻辑；
- 迁移期临时 adapter 没有退出条件。

目标：有证据确认失效后不迁移；不确定时标记未知，而不是凭感觉删除。

## 五、设计改进优先级

### 必须改

满足任一情况：

- 原结构无法融入目标项目而不形成重复体系；
- 会让核心业务依赖已淘汰技术；
- 会把严重耦合或安全风险直接传入目标系统；
- 会使关键行为无法可靠测试或验证；
- 与目标项目明确架构规则冲突。

### 应该改

能够明显改善：

- 清晰度；
- 可测试性；
- 变化隔离；
- 一致性；
- 可观测性；
- 错误处理；
- 目标技术栈惯用性；

同时迁移风险可控。

### 后续改

虽然设计不理想，但与当前迁移边界关系弱，处理会显著扩大范围或引入额外风险。

“后续改”必须记录，但不应成为迁移无限扩张的借口。

## 六、优秀目标代码的判断维度

### 6.1 清晰

- 名称表达业务意图；
- 关键流程容易顺着读懂；
- 重要规则不隐藏在通用工具和魔法行为里；
- 代码结构与目标项目一致。

### 6.2 内聚

- 同一个模块围绕稳定能力组织；
- 一次业务变化尽量落在少量相关位置；
- 不为了“分层”把一个简单用例拆成大量空壳对象。

### 6.3 低耦合

- 依赖方向清晰；
- 外部系统通过明确边界接入；
- 核心业务尽量不依赖具体基础设施；
- 避免循环依赖和共享可变状态。

### 6.4 可测试

- 关键业务规则可以在合理成本下验证；
- 外部依赖和副作用可以隔离或在集成层验证；
- 不要求所有代码都变成可 Mock 接口。

### 6.5 失败语义清晰

- 业务失败和系统失败可区分；
- 超时、重试、补偿和幂等策略可发现；
- 错误不会在层之间被随意吞掉或改义。

### 6.6 可运营

- 关键业务结果和失败可观测；
- 日志、指标和 Trace 能定位迁移边界的问题；
- 临时兼容层本身也有监控。

### 6.7 目标技术栈惯用

- 使用目标语言成熟的数据结构和控制流；
- 使用目标框架推荐的生命周期和依赖方式；
- 不保留只因为源语言需要才存在的模式；
- 不机械模仿源项目异常、继承、注解、线程或 ORM 风格。

## 七、避免“最佳实践”过度设计

以下行为不自动算优化：

- 为每个类增加一个接口；
- 为每一层复制 DTO；
- 把简单模块强行拆成微服务；
- 为可能永远不会出现的需求设计通用框架；
- 引入目标项目从未使用的新架构流派；
- 只为了减少函数行数而拆成难追踪的小函数；
- 用复杂事件驱动替换清晰同步流程却没有业务需求；
- 使用大量设计模式但无法说明具体问题。

判断标准始终是：是否降低理解成本、变化成本和错误风险。

## 八、设计变化必须可追踪

使用 `.migration/设计改进台账.md`。

每项改进至少记录：

```text
编号
源设计问题
问题证据
优先级
目标设计原则
目标实现决策
是否改变可观察行为
关联能力/规则
验证方式
状态
```

如果设计改进意外导致行为变化，立即转入 `.migration/差异与失败队列.md`，不能用“这是重构”掩盖。

## 九、设计审查问题

完成一个迁移单元后，至少问：

1. 目标实现是否只是把源类换了语言？
2. 是否复制了目标项目已经有的能力？
3. 业务规则是否比源系统更容易定位和验证？
4. 外部依赖是否被放在清晰边界？
5. 事务、副作用和错误处理是否比源系统更明确？
6. 是否出现无必要的抽象或层次？
7. 是否保留了只属于源框架的设计？
8. 新代码是否与目标项目类似模块风格一致？
9. 临时迁移设施何时删除？
10. 所有“更好”的判断是否有具体问题和收益支撑？

## 十、代码质量不是迁移后的额外奖励

对于本 Skill，代码质量属于迁移验收的一部分。

但是验收只要求关闭本次明确列为“必须改”的设计问题，并对“应该改 / 后续改”做出清晰决策。不要把迁移项目变成无限期全仓重构。
