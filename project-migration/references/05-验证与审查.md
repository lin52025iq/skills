# 迁移验证与独立审查

## 一、验证目标

验证的是：

1. 迁移后的系统是否满足业务能力和行为要求；
2. 目标实现是否符合本次明确的目标设计和代码质量要求。

不是验证“目标代码是否像源代码”。

## 二、先建立验证裁判

大规模迁移前必须回答：什么机制能够客观判断旧、新实现是否满足同一要求？

裁判可以是：

- 公共接口测试；
- 契约测试；
- 端到端测试；
- parity harness；
- 数据一致性比较；
- 明确人工验收协议。

### 裁判自身也要被验证

优先确认：

- 在旧实现上能运行并通过；
- 不依赖不需要保留的源内部结构；
- 条件允许时，对故意制造的错误能够失败；
- 重写测试时没有弱化关键断言。

不能发现错误的测试不能作为迁移完成依据。

## 三、验证层次

### 静态与构建

编译、类型检查、静态检查、格式和基础质量规则。必要但不充分。

### 单元验证

适合纯业务规则、状态转换、计算、边界条件和错误分类。

### 集成验证

适合数据库真实约束、ORM、消息、缓存、文件、第三方客户端和事务。

### 契约验证

比较请求、响应、状态码、错误码、事件 Schema、默认值和兼容策略。

### 行为对照

相同输入分别运行旧、新实现，比较：

- 返回结果；
- 持久化结果；
- 状态转换；
- 事件；
- 外部调用；
- 错误分类；
- 审计和必要副作用。

比较前定义允许不同的字段，例如随机 ID、时间戳或 Trace ID。

### 端到端

覆盖真实用户或上游可观察的关键流程。

### 非功能

按项目风险检查性能、容量、安全、权限、可观测性和恢复能力。

## 四、失败先做三方分类

验证失败时先判断：

```text
旧实现也失败
→ 可能是继承问题、测试环境问题或裁判问题

只有新实现失败
→ 迁移回归

旧、新都成功但结果不同
→ 行为差异，需要判断是 bug 还是批准变化
```

不要默认所有失败都靠改新代码解决。

## 五、业务规则和能力覆盖

必须能够追踪：

```text
业务规则
→ 目标实现
→ 验证方式
→ 验证结果
```

以及：

```text
源能力
→ 迁移决策
→ 目标实现
→ 验证证据
```

不能用测试数量或迁移文件数代替覆盖。

## 六、代码质量与设计验证

迁移验收增加目标代码质量审查：

- 本次“必须改”的源设计问题是否关闭；
- 目标实现是否遵循目标项目已有稳定惯例；
- 是否只是把源类、源层次和源框架概念换了语法；
- 是否重复目标项目已有业务或基础设施能力；
- 模块职责和依赖方向是否更清晰；
- 业务规则是否更容易发现和测试；
- 外部依赖、事务、副作用和错误边界是否清晰；
- 是否引入没有问题支撑的抽象；
- 迁移态设施是否有删除条件；
- 目标代码是否使用目标语言/框架成熟惯例。

设计审查不以“层更多”“接口更多”“代码更短”为成功标准。

## 七、独立审查方法

切换为审查者后主动寻找失败证据。

### 源 → 目标

检查漏掉的能力、规则、契约和副作用。

### 目标 → 源

检查目标实现新增的重要行为，确认是否得到批准。

### 设计 → 目标项目

检查是否把遗留设计带入目标系统，或反过来为了追求模式而过度设计。

### 验证 → 真实错误

检查测试是否真的能识别破坏，而不是只验证快乐路径。

## 八、技术栈语义差异

特别检查：空值、时间、精度、排序、序列化、事务、隔离级别、并发、错误传播、消息投递、缓存、生命周期。

## 九、验证失败如何处理

1. 记录实际差异；
2. 判断源行为理解是否错误；
3. 判断目标实现是否错误；
4. 判断裁判是否错误；
5. 判断是否是批准的新行为；
6. 判断是否暴露了规则或架构缺陷；
7. 更新规则、计划、实现或裁判；
8. 再次验证。

不得为了让测试通过而削弱测试去适应错误实现。

## 十、最低验证证据

至少应有：

- 构建或基础运行成功；
- 关键业务流程验证；
- 关键业务规则验证；
- 关键数据变化验证；
- 关键接口或事件契约验证；
- 关键失败路径验证；
- 本次必须处理设计项的审查结果；
- 未解决差异和遗留设计项清单。
