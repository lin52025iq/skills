# 迁移验证与独立审查

## 一、验证目标

验证的是“迁移后的系统是否满足能力和行为要求”，不是“目标代码是否像源代码”。

## 二、验证层次

按风险选择组合：

### 静态与构建验证

- 编译或构建；
- 类型检查；
- 静态检查；
- 格式和基础质量规则。

它们必要但不充分。

### 单元验证

适合：

- 纯业务规则；
- 状态转换；
- 计算逻辑；
- 边界条件；
- 错误分类。

### 集成验证

适合：

- 数据库真实约束；
- ORM 行为；
- 消息；
- 缓存；
- 文件或对象存储；
- 第三方客户端适配。

### 契约验证

重点比较：

- 请求字段；
- 响应字段；
- 类型；
- 默认值；
- 状态码；
- 错误码；
- 事件结构；
- 兼容策略。

### 行为对照

适合跨语言、跨框架、高风险规则迁移。

使用相同输入分别运行旧实现和新实现，比较：

- 返回结果；
- 持久化结果；
- 状态转换；
- 事件；
- 外部调用；
- 错误分类；
- 审计或必要日志。

比较前应定义哪些字段允许不同，例如随机标识符、时间戳、追踪编号。

### 端到端验证

覆盖真实用户或上游可观察的关键流程。

### 非功能验证

按项目要求检查：

- 性能；
- 容量；
- 安全；
- 权限；
- 可观测性；
- 恢复能力。

## 三、业务规则覆盖

验证报告不应只统计测试数量。

应能从业务规则台账追踪到：

```text
业务规则
→ 目标实现
→ 验证方式
→ 验证结果
```

任何高优先级规则没有验证时，都应显式列为缺口。

## 四、能力覆盖

能力迁移矩阵应支持回答：

- 源系统共有多少项关键能力；
- 哪些决定不迁移；
- 哪些已实现；
- 哪些已验证；
- 哪些阻塞；
- 哪些仍未知。

不能用“迁移了多少文件”代替能力覆盖率。

## 五、独立审查方法

切换为审查者后，目标是寻找当前方案失败的证据。

### 从源到目标检查遗漏

逐项遍历源能力和业务规则，确认目标去向。

### 从目标到源检查意外新增

反向检查目标实现中的重要行为，询问源系统是否存在同样语义。如果不存在，确认是否是明确批准的变化。

### 检查成功路径之外的行为

重点看：

- 重复；
- 并发；
- 超时；
- 重试；
- 部分成功；
- 回滚；
- 异步延迟；
- 外部故障；
- 数据冲突。

### 检查技术栈语义差异

特别检查：

- 空值；
- 时间；
- 精度；
- 排序；
- 序列化；
- 事务；
- 隔离级别；
- 并发；
- 错误传播；
- 消息投递。

### 检查证据质量

所有阻断级结论都应有充分证据，不能建立在“通常框架会这样做”的假设上。

## 六、验证失败如何处理

验证失败时：

1. 记录实际差异；
2. 判断源行为是否已经理解错误；
3. 判断目标实现是否错误；
4. 判断差异是否是用户批准的新行为；
5. 更新规则、计划或实现；
6. 再次验证。

不得为了让测试通过而修改测试去适应错误实现，除非有明确证据证明原测试不再代表需求。

## 七、迁移完成前的最低验证证据

至少应有：

- 构建或基础运行成功；
- 关键业务流程验证；
- 关键业务规则验证；
- 关键数据变化验证；
- 关键接口或事件契约验证；
- 关键失败路径验证；
- 未解决差异清单。
