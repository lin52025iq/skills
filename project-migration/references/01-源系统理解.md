# 源系统理解方法

## 目标

建立一个足以支撑迁移决策的源系统行为模型，并把研究结果整理成真正的**功能文档**。

重点不是生成代码目录说明，而是理解：

- 系统有哪些功能；
- 谁在使用这些功能；
- 功能如何展开；
- 哪些规则决定结果；
- 状态和数据如何变化；
- 有哪些外部依赖和副作用；
- 失败、重试、事务、幂等和权限如何工作；
- 哪些代码只是实现细节，不应成为迁移结构。

阶段 1 推荐形成：

```text
.migration/源系统理解.md
.migration/功能文档.md
.migration/业务规则台账.md
.migration/依赖与副作用.md
.migration/风险与未知项.md
```

功能文档通过后，再蒸馏：

```text
.migration/迁移语义规格.md
```

不要跳过功能理解，直接把源类、方法和目录转换成迁移任务。

---

## 一、从真实入口出发，不从目录出发

优先找到真正能够触发系统行为的入口：

- HTTP、RPC、GraphQL 或其他接口；
- 前端路由、页面动作和交互事件；
- 消息消费者；
- 定时任务；
- 事件监听器；
- Webhook / 回调；
- 命令行入口；
- 后台管理动作；
- 对外暴露的库接口；
- 其他模块直接调用的公开能力。

对每个入口先建立：

```text
入口
→ 谁触发
→ 用户 / 上游意图
→ 输入
→ 初步业务能力
→ 可观察结果
```

然后沿真实代码路径继续向下。

找到 Controller、Handler 或 Consumer 只是研究开始，不代表已经理解功能。

---

## 二、必须递归向下理解功能点

对每个入口沿调用链、数据流和副作用链持续向下研究。

每到一个新节点，都判断：

- 是否出现新的业务决策；
- 是否改变业务状态；
- 是否读写有业务意义的数据；
- 是否产生外部调用、事件、消息、通知或其他副作用；
- 是否处理权限、安全、事务、并发、幂等、超时、重试或补偿；
- 是否存在新的条件分支；
- 是否启动后续异步链路；
- 是否揭示新的子功能。

只要仍有新的业务语义，就继续向下。

推荐链路：

```text
入口
→ 身份 / 权限 / 前置校验
→ 应用编排
→ 业务决策
→ 状态转换
→ 数据读写
→ 外部集成
→ 事件 / 消息 / Job
→ 后续 Consumer / Callback
→ 最终业务结果
```

如果调用分叉，不只追“主成功路径”。把所有重要分支加入探索队列逐个研究。

详细的递归下钻、功能树、停止条件和文档标准见：

`references/13-功能文档与递归下钻.md`。

对应模板：

`templates/04-功能文档.md`。

---

## 三、功能层级按业务语义形成

功能树不要使用代码层级作为功能层级。

建议：

```text
L0 业务域 / 大模块
└── L1 用户或上游可识别的能力
    ├── L2 子功能 / 用例
    │   ├── L3 业务规则 / 状态变化 / 副作用
    │   └── L3 失败 / 补偿 / 边界行为
    └── L2 异步或后台能力
```

例如：

```text
订单管理
├── 创建订单
│   ├── 校验购买资格
│   ├── 价格计算
│   ├── 库存预占
│   └── 发布订单创建事件
├── 取消订单
└── 订单过期
```

不要把：

```text
OrderController
OrderService
OrderRepository
OrderUtils
```

当成功能树。

这些只是功能实现的证据位置。

## 四、五轮理解法

递归下钻不是只做一遍调用链阅读，还应从不同视角反复验证。

### 第一轮：结构视角

回答：

- 模块物理位置在哪里；
- 主要包、目录、组件是什么；
- 哪些是真实入口；
- 哪些是领域核心；
- 哪些是基础设施；
- 哪些是共享能力。

本轮建立研究地图，不急着下业务结论。

### 第二轮：功能与业务视角

围绕入口递归下钻，并逐步形成 `.migration/功能文档.md`。

对每个功能回答：

- 谁触发；
- 为什么触发；
- 输入和前置条件；
- 主流程；
- 条件分支；
- 业务规则；
- 状态如何变化；
- 成功意味着什么；
- 用户或上下游能看到什么。

### 第三轮：依赖与副作用视角

检查：

- 数据库表和字段；
- 缓存键；
- 搜索索引；
- 对象存储；
- 外部 API；
- SDK；
- 消息主题或队列；
- 邮件、短信、通知；
- 审计记录；
- 文件输出；
- 任务调度；
- 其他服务写入。

不要把函数返回值误认为完整行为。真实业务效果经常存在于副作用和异步链路中。

### 第四轮：失败与边界视角

对关键功能检查：

- 参数非法；
- 数据不存在；
- 数据重复；
- 权限不足；
- 外部服务失败；
- 网络超时；
- 部分步骤成功；
- 数据库提交失败；
- 消息发送失败；
- 重复消息；
- 并发请求；
- Job 重复执行；
- 重试后成功；
- 补偿失败。

特别关注 catch、recover、defer、finally、事务、锁、唯一约束、状态判断和重试机制。

### 第五轮：反证视角

主链研究完成后，主动寻找能推翻当前功能理解的证据：

- 同一接口的多个实现；
- 同一状态的所有判断；
- 同一表的其他写入者；
- 同一事件的其他生产者和消费者；
- 同一配置或 Feature Flag 的使用位置；
- 已弃用但仍可触达的代码；
- 特殊客户、租户、地区、版本逻辑；
- 测试中的边界案例；
- 历史提交中的关键 bug 修复。

反证发现新的功能、分支或例外时，回写功能文档和业务规则台账。

---

## 五、什么时候停止向下

不要无限深入所有工具函数。

满足以下情况时可以停止当前分支：

- 后续只剩纯技术 plumbing，不再产生业务语义；
- 已达到稳定外部系统边界，只需记录契约和失败语义；
- 已到明确数据库事实，只需记录数据、约束和事务；
- 后续调用不会产生新的可观察行为；
- 已进入研究过的循环节点；
- 当前证据不足，已经明确记录未知项。

如果不确定某个节点是否只是技术细节，先问：

> 删除或替换这个实现细节后，功能规则、状态、数据、副作用或失败行为会不会变化？

不会变化时，通常不需要把它继续展开成功能点。

---

## 六、测试是功能证据，不只是质量工具

分析测试时重点提取：

- 测试名称描述的业务条件；
- arrange 构造了哪些状态；
- act 触发什么功能；
- assert 关心什么业务结果；
- 是否验证数据库、副作用、事件或外部调用；
- 是否存在参数化边界；
- 是否存在历史 bug 回归测试。

测试中发现功能文档没有记录的行为时，补入功能树，而不是只把它当测试细节。

如果生产代码和测试不一致：

1. 确认测试是否仍执行；
2. 确认测试是否覆盖当前实现；
3. 查看相关版本历史；
4. 记录冲突和未知项；
5. 不擅自选择更方便的版本作为事实。

---

## 七、数据库是隐藏功能规则的重要来源

必须检查：

- 主键；
- 唯一约束；
- 非空约束；
- 外键；
- 默认值；
- 检查约束；
- 索引；
- 触发器；
- 存储过程；
- 数据库迁移历史。

例如代码中没有显式幂等逻辑，但数据库业务键有唯一约束，这仍可能是功能行为的重要部分。

数据库发现的重要规则要回写到功能文档和业务规则台账。

---

## 八、配置和运行环境也是功能行为的一部分

检查：

- 超时时间；
- 重试次数；
- 批大小；
- 并发数；
- 队列配置；
- Cron；
- Feature Flag；
- 环境变量；
- 限流；
- 熔断；
- 安全策略。

不要只看默认配置。环境差异可能改变实际功能。

---

## 九、证据记录标准

每个高价值结论尽量记录：

- 功能 / 规则结论；
- 类型：证据 / 推断 / 未知；
- 文件路径；
- 符号名；
- 测试名；
- 表 / 约束；
- 配置项；
- 业务意义；
- 对迁移的要求；
- 如果未确认，下一步如何确认。

不要只依赖容易漂移的绝对行号。

---

## 十、大模块可以并行研究，但功能树只有一份

大模块可以用多个 Research Worker：

- 按用户入口；
- 按业务能力；
- 按数据和状态；
- 按事件 / Job / Consumer；
- 按外部集成。

Worker 负责深挖和提交证据，Supervisor 负责：

- 去重功能；
- 合并跨入口的同一能力；
- 统一功能编号；
- 补齐跨 Workstream 调用；
- 维护最终 `.migration/功能文档.md`。

不要让多个 Worker 各自形成互相冲突的全局功能树。

详见 `references/12-多Agent与多会话编排.md`。

---

## 十一、功能理解完成 Gate

进入迁移语义规格、目标项目设计和正式 Rebuild 前，至少能回答：

1. 这个模块有哪些主要业务能力？
2. 每项能力有哪些真实入口？
3. 每项关键功能的主流程是什么？
4. 代码向下追踪到了哪些子功能？
5. 哪些规则决定业务结果？
6. 核心状态如何变化？
7. 读写哪些关键数据？
8. 调用哪些外部系统？
9. 产生哪些事件、消息和副作用？
10. 异步链路最终走到哪里？
11. 失败和部分成功如何处理？
12. 哪些动作需要幂等？
13. 哪些操作需要事务或并发控制？
14. 权限在哪里判断？
15. 哪些行为由配置控制？
16. 是否存在旁路入口、其他写入者或特殊分支？
17. 每个关键功能是否有代码或测试证据？
18. 当前还有哪些高风险未知项？

如果 `.migration/功能文档.md` 仍主要是 Controller、Service、Repository、函数名称列表，说明研究仍停留在代码表面，不得进入正式迁移设计。
