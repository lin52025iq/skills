# 前端框架与工程迁移策略

本文用于跨框架、Router、渲染模式、状态、样式、组件库、构建工具或 monorepo 边界迁移。它不给出固定版本答案；先以目标仓库锁定版本和官方文档为准。

## 目录

1. 目标原生映射
2. 状态与数据
3. Router 与渲染
4. 表单、样式和组件库
5. 构建与运行时
6. 常见迁移轴
7. Copy-Smell 检查

## 1. 目标原生映射

迁移前分别回答三类问题：

### 1.1 产品语义

- 用户入口和意图是什么；
- 状态、规则、失败和最终结果是什么；
- 哪些视觉与交互必须保持；
- 哪些行为已废弃或批准改变。

### 1.2 源框架事实

- 哪些行为由框架隐式提供；
- 生命周期、watcher/effect、依赖注入、双向绑定如何影响结果；
- Route、store、cache、form、CSS 和 build 的耦合点；
- 哪些抽象只为旧框架存在。

### 1.3 目标项目范例

至少找到 2～5 个真实范例，覆盖：

- Route/Page 边界；
- server/client 数据获取；
- local/global/server state；
- form 和 validation；
- Design System 和 styling；
- error/loading/empty；
- component/E2E/visual test。

目标蓝图引用这些范例。找不到相似页面时，分别寻找每个设计点的最佳范例，不回退到源组件树。

## 2. 状态与数据

### 2.1 先分类状态

| 状态类型 | 典型内容 | 目标落点原则 |
|---|---|---|
| Server state | API 数据、cache、请求状态 | 使用目标项目 query/cache 层 |
| URL state | filter、page、tab、search | Router/search params 优先 |
| Form state | draft、validation、submit | 目标 form 方案或局部状态 |
| Local UI state | modal、expanded、selection | 最近共同 owner |
| Global client state | session、theme、跨页流程 | 仅在真正跨边界时进入全局 |
| Derived state | 可由其他状态计算 | 计算而非复制存储 |
| Persistent state | storage、cookie、indexedDB | 明确版本、迁移和失效策略 |

不要把源 Store module 一对一复制到目标 Store。特别警惕把 server cache、URL 参数和表单草稿全部塞进全局状态。

### 2.2 请求语义

迁移 API 调用时确认：

- 请求取消、竞态和过期响应；
- retry、backoff 和错误分类；
- cache key 与 invalidation；
- pagination/infinite scroll；
- optimistic update 和 rollback；
- auth refresh 与 401/403；
- SSR prefetch、dehydrate/hydrate；
- timezone、locale、精度和序列化；
- loading、partial、stale 和 offline UI。

不要只把 `axios` 调用改成另一种 fetch 语法。

### 2.3 Effect/Watcher 迁移

对每个 watcher、subscription、effect、lifecycle hook 先分类：

- 同步派生：改为计算；
- 用户事件：移到 event handler；
- 数据获取：移到目标 query/router loader/server boundary；
- 外部系统同步：保留 effect，但定义依赖和清理；
- DOM 测量：放到目标布局生命周期并处理 resize；
- 历史补丁：确认是否仍需要。

大量 `useEffect`、deep watcher 或双向同步通常说明状态所有权未重新设计。

## 3. Router 与渲染

### 3.1 Route 契约

每个 Route 记录：

- path、params、query、hash；
- nested layout 和 outlet；
- loader/action 或数据依赖；
- auth/permission guard；
- redirect、404、403；
- metadata/SEO/canonical；
- lazy chunk 和 prefetch；
- scroll restoration；
- direct URL 与刷新；
- analytics page view。

### 3.2 SPA → SSR/SSG/混合渲染

不要把客户端 SPA 页面简单包进 SSR 框架。先决定：

- 哪些数据必须服务端获取；
- 哪些组件需要浏览器 API；
- server/client component 或 island 边界；
- cookie/header/auth 在服务端如何读取；
- cache、revalidation 和用户个性化；
- loading/error/not-found boundary；
- streaming/suspense 是否改变交互；
- hydration 输入是否确定；
- SEO 和 metadata；
- 静态导出是否支持动态需求。

常见 hydration 风险：

- 首屏读取 `window`、storage、随机数或当前时间；
- 服务端和客户端 locale/timezone 不同；
- Flag、auth 或主题在两端不一致；
- 非法 HTML 嵌套；
- 第三方组件仅支持浏览器；
- CSS-in-JS 注入顺序不同。

### 3.3 Router 大版本或架构迁移

- 不混淆旧/new Route API 的数据所有权；
- 不在迁移期建立两套互相不知道的 history；
- 建立 Route 清单和 old→new 映射；
- 先迁移边界清晰且有 Deep Link 测试的 Route；
- 对 redirect、404、permission、query 和 scroll 单独测试；
- 旧 Router adapter 必须有删除 Gate。

## 4. 表单、样式和组件库

### 4.1 表单

保持的不只是字段：

- 初始值、dirty/touched；
- 同步/异步 validation；
- blur/change/submit 时机；
- server error 映射；
- disabled/read-only；
- unsaved changes；
- keyboard 和 autofocus；
- submit 去重、loading、success；
- 动态字段和数组；
- locale 数字、日期和时区。

目标组件库的 Form 默认行为可能不同，必须用用户路径验证。

### 4.2 组件库 / Design System 替换

建立组件语义矩阵：

| 源组件 | 用户语义 | 目标组件 | 不等价点 | Adapter/样式 | 验证 |
|---|---|---|---|---|---|
| Select | 搜索、清空、键盘 |  |  |  |  |
| Modal | focus trap、关闭规则 |  |  |  |  |
| Table | sort、page、overflow |  |  |  |  |

检查：

- DOM 和 accessible name；
- controlled/uncontrolled 模型；
- event 顺序和值结构；
- portal 和 z-index；
- focus trap/return；
- default spacing/size；
- responsive 行为；
- virtualization；
- locale 和 timezone；
- error/disabled/loading。

不要为了视觉相近忽略交互和 Accessibility 差异。

### 4.3 样式体系

允许重建 CSS 架构，但保持可观察结果。迁移前识别：

- reset、global element rules；
- cascade、specificity 和 import order；
- theme/token；
- CSS variable；
- font loading 和 fallback；
- container/viewport breakpoint；
- portal/overlay；
- animation/reduced motion；
- print、RTL、高对比度；
- asset path 和 base URL。

从 Less/Sass/CSS-in-JS 转到 CSS Modules/Tailwind 等方案时，不要逐条转写旧选择器。先重建组件边界、Token 和布局，再用截图与交互验证。

## 5. 构建与运行时

### 5.1 构建工具迁移

记录 old/new：

- entry 和 HTML 模板；
- alias、extensions、conditions；
- env 前缀和注入时机；
- public/base path；
- CSS、PostCSS、preprocessor；
- SVG、图片、字体和 worker；
- dynamic import 与 chunk naming；
- dev proxy；
- polyfill 和 browser target；
- test transform；
- Storybook/E2E integration；
- production source map；
- deploy output 和 server adapter。

不得把所有旧 bundler plugin 无条件搬到新工具；先确认它解决的能力是否仍需要、是否已有原生替代。

### 5.2 环境变量

- 只记录变量名、owner、环境和是否公开，不复制密钥值；
- 区分 build-time 与 runtime；
- 客户端可见变量必须视为公开数据；
- SSR 两端读取方式一致；
- 缺失变量应尽早失败并给出明确错误；
- 删除旧前缀和重复变量时检查部署配置。

### 5.3 Monorepo

检查：

- workspace package 边界和依赖方向；
- shared UI/domain/tooling 的所有权；
- build graph、cache 和 affected commands；
- TypeScript project references/path alias；
- package exports 和 server/client 条件；
- versioning/release；
- duplicate React/Vue/runtime；
- 测试 fixture 与 Storybook 位置。

不要把源应用的内部目录直接提升成共享 package；只有稳定、被多个真实调用方使用的边界才值得共享。

## 6. 常见迁移轴

## 6.1 Vue → React

重点转换的是语义，不是语法：

- `computed` → 派生值；
- `watch` → 事件、数据层或必要 effect；
- `provide/inject` → 目标项目 context/依赖边界；
- Pinia/Vuex → 重新分类 server、URL、form、local、global state；
- slot → composition/children/render API；
- directive → 组件、Hook 或 DOM 行为；
- transition/keep-alive → 目标 Router 和生命周期方案。

警惕：把每个 `.vue` 变成一个 `.tsx`，把所有 watcher 变成 `useEffect`。

## 6.2 React → Vue

- 不把 Hook 调用图机械转成大量 composable；
- 区分 props、emit、slot、provide/inject 和 store；
- 确认 controlled component 语义；
- effect cleanup、ref 和 DOM 生命周期需显式映射；
- 目标 Vue 项目现有 composable 和 Pinia/query 惯例优先。

## 6.3 Angular → React/Vue

先拆开 Angular 隐式能力：

- DI 与 provider scope；
- Router guard/resolver；
- RxJS stream 和 cancellation；
- reactive form；
- zone/change detection；
- template directive/pipe；
- service singleton；
- module/lazy boundary。

不要复制 Controller/Service/Module 层级。为 observable 明确消费、错误和取消语义。

## 6.4 JavaScript → TypeScript

渐进策略优先：

- 先固定 compiler/bundler/test 集成；
- 从公共边界、数据契约和高变更模块开始；
- 为真实不确定性建模，不用 `any` 掩盖；
- runtime validation 与 static type 分工；
- 删除重复 JSDoc/PropTypes 前确认调用方；
- 逐步提高 strictness，并记录暂时例外和删除条件。

编译通过不等于运行时数据可靠。

## 6.5 CRA/Webpack → Vite 或其他现代构建

重点核查：

- 环境变量、HTML 和 public path；
- CommonJS/ESM 兼容；
- Node polyfill；
- SVG/import 语义；
- proxy；
- Jest transform 与 test environment；
- chunk 和 lazy loading；
- service worker/PWA；
- production deploy 路径。

先跑一条代表性生产构建和浏览器流程，再批量删除旧配置。

## 6.6 旧 SPA → Next/Nuxt/SvelteKit 等

不要先把所有页面放进 client-only wrapper。逐页决定：

- server/client 边界；
- data loading 与 cache；
- auth/session；
- metadata；
- mutation/action；
- error/not-found/loading；
- streaming 与交互；
- static/dynamic rendering；
- edge/node runtime；
- deployment adapter。

## 7. Copy-Smell 检查

出现以下信号时重新检查蓝图：

- 目标目录和源目录高度同构；
- 源组件、Store、mixin、service 和 CSS 文件一对一出现；
- 新代码保留源框架术语或生命周期；
- 大量 adapter 没有统一边界；
- 目标项目已有 query/form/router/design system 却另建一套；
- server state 被复制进全局 store；
- 为模拟旧框架写大量 effect/watch；
- 同一数据在 URL、store、form 和 local state 多份同步；
- SSR 页面大面积退化为 client-only；
- 目标测试、错误、日志和目录风格与同仓模块不一致。

发现后先回答：

```text
这是必须保持的产品语义，还是源框架偶然结构？
目标项目已经怎样解决同类问题？
短期兼容层能否隔离，而不是污染永久架构？
哪个上游文档或切片规则导致了复制？
```
