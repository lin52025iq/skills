# `.migration/` 目录边界与迁移辅助代码

## 一、定位

`.migration/` 是一次系统迁移的专用工作区，但必须区分**控制面**与**执行面**。

```text
.migration/
├── 控制面：事实、状态、决策、计划、风险、证据
└── 执行面：仅限迁移专用的脚本、测试和测试数据
```

根目录首先是迁移知识库和状态存储，不应演变成随手堆放临时代码的目录。

## 二、推荐目录结构

```text
.migration/
├── 迁移上下文.md
├── 当前状态.md
├── 源系统理解.md
├── 业务规则台账.md
├── 能力迁移矩阵.md
├── 迁移边界.md
├── 目标架构映射.md
├── 技术栈迁移规则.md
├── 设计改进台账.md
├── 迁移计划.md
├── 风险与未知项.md
├── 差异与失败队列.md
├── 验证报告.md
│
├── scripts/              # 必要的迁移辅助脚本
├── tests/                # 迁移专用验证、对照和契约测试
├── fixtures/             # 可选：脱敏测试输入、黄金样本、固定数据
└── results/              # 可选：机器生成的验证结果，不作为源代码
```

不要求创建全部子目录。只有存在真实需要时才创建。

## 三、根目录硬规则

`.migration/` 根目录只保存声明式迁移资料和状态。

根目录允许：

- `.md`；
- `.yaml` / `.yml`；
- `.json`；
- `.csv` 等确有必要的静态迁移数据。

根目录禁止直接创建：

- `.js`、`.cjs`、`.mjs`、`.ts`；
- `.py`；
- `.sh`、`.bash`、`.zsh`；
- `.ps1`、`.bat`、`.cmd`；
- Java、Go、Rust、C# 等可执行源码；
- `package.json`、`pyproject.toml`、`requirements.txt` 等工具依赖清单；
- 可执行二进制；
- 构建产物、依赖目录和缓存。

例如以下结构属于违规：

```text
.migration/
├── 当前状态.md
├── compare.cjs          # 禁止
├── scan.py              # 禁止
└── package.json         # 禁止
```

应该改成：

```text
.migration/
├── 当前状态.md
├── scripts/
│   ├── compare.cjs
│   └── scan.py
└── tests/
    └── order-parity.test.ts
```

## 四、什么时候允许创建 `scripts/`

默认仍然**不为理解代码而创建脚本**。优先使用宿主 Agent 已有的文件搜索、符号导航、Git、构建、测试、Schema 和代码阅读能力。

只有脚本能够明显提高确定性、可重复性或验证质量时才创建，例如：

- 新旧系统输出对照；
- 数据一致性比较；
- Schema 或契约差异检查；
- 大量确定性迁移结果的批量校验；
- 数据回填前后的验证；
- 可重复的迁移操作或回滚辅助；
- 人工执行容易出错的确定性步骤。

不要因为“写脚本方便”就为一次简单搜索或文件读取创建脚本。

## 五、`scripts/` 的约束

每个脚本必须满足：

1. **目的明确**：解决具体迁移问题，而不是通用实验；
2. **可追踪**：在迁移计划、验证报告或任务中说明用途；
3. **输入输出明确**：避免隐式修改生产数据或源代码；
4. **默认安全**：危险写操作应显式、可审查，优先提供 dry-run；
5. **尽量复用项目现有依赖**：不要轻易为一个小脚本引入独立生态；
6. **结果可记录**：关键执行结果应回写到 `.migration/` 的验证或状态文档；
7. **有生命周期**：明确迁移结束后删除、保留还是迁入正式工具目录。

脚本不能承载目标系统正式业务实现。正式业务代码必须进入目标项目正常源码目录。

## 六、什么时候使用 `tests/`

`.migration/tests/` 用于**迁移专用、可能在迁移结束后删除的验证测试**，例如：

- 新旧行为 parity test；
- 迁移期间的契约兼容测试；
- 特征测试和黄金样本测试；
- 临时数据一致性测试；
- 只在新旧系统并存阶段成立的对照测试；
- 用于证明验证裁判有效的故障注入测试。

如果某个测试对目标系统长期质量仍有价值，例如核心业务规则回归测试、长期契约测试，则迁移稳定后应该移动到项目正常的测试目录，而不是永久留在 `.migration/tests/`。

## 七、`fixtures/` 与 `results/`

### `fixtures/`

只保存迁移验证所需的最小固定输入或黄金样本。

要求：

- 不提交密码、Token、密钥；
- 不提交未经脱敏的生产用户数据；
- 不复制大规模生产数据集；
- 说明样本代表的业务场景。

### `results/`

可用于保存机器生成的对照结果、差异摘要或测试结果，但应优先保存**可复核摘要**，而不是大量无价值日志。

如果结果体积大或可随时重建，可以不提交 Git，只在 `验证报告.md` 中记录生成方式和关键结论。

## 八、依赖管理

优先使用目标项目或源项目已有运行环境和依赖。

不要在 `.migration/` 根目录创建新的依赖体系。

确实需要独立依赖时：

1. 先判断能否使用项目已有工具实现；
2. 不能实现时，依赖清单只能跟随对应迁移工具放在 `.migration/scripts/` 内；
3. 记录为什么必须引入；
4. 不提交 `node_modules/`、虚拟环境、编译缓存；
5. 迁移结束后按生命周期规则清理。

## 九、禁止把 `.migration/` 当成源码副本

不要把整个源模块、目标模块或第三方代码复制到 `.migration/` 形成第二份源码树。

需要比较源、目标代码时，直接读取原项目位置。

只有无法稳定重现的少量输入、输出或契约样本，才适合进入 `fixtures/`。

这可以避免：

- 副本与真实源码漂移；
- AI 修改错误副本；
- 重复维护；
- 迁移完成后遗留大量无主代码。

## 十、控制面与执行面必须关联

任何 `scripts/` 或 `tests/` 中的辅助代码都不应成为孤立文件。

至少在下列一个迁移产物中引用它：

- `迁移计划.md`；
- `技术栈迁移规则.md`；
- `试迁移报告.md`；
- `差异与失败队列.md`；
- `验证报告.md`；
- `切换与回滚.md`。

推荐记录：

```text
工具：.migration/tests/order-parity.test.ts
用途：验证 CAP-001 创建订单在新旧实现中的行为等价。
覆盖规则：BR-003、BR-007、BR-011。
运行方式：使用目标项目现有测试命令执行。
生命周期：切换稳定后，将 BR-003/007/011 的长期回归用例迁入 tests/order/，删除临时 parity 部分。
```

## 十一、迁移完成后的清理规则

进入清理阶段时，对 `.migration/scripts/` 和 `.migration/tests/` 中每个文件做一次去向决策：

- **删除**：仅用于一次性迁移；
- **迁入正式 tests/**：具有长期回归价值；
- **迁入正式 tools/ 或 scripts/**：具有长期运维或工程价值；
- **保留在 `.migration/`**：仅适用于仍处于观察期、迁移尚未真正结束的临时工具。

迁移已经宣布完成后，不应长期遗留没有所有者、没有用途说明的 `.migration` 可执行代码。

## 十二、发现违规时怎么处理

如果 Agent 已经在 `.migration/` 根目录创建了 `.cjs`、`.py`、`.sh` 等文件：

1. 判断该工具是否真的必要；
2. 不必要则删除；
3. 必要则移动到 `.migration/scripts/` 或 `.migration/tests/`；
4. 在迁移计划或验证报告中补充用途；
5. 明确生命周期；
6. 检查是否还存在其他无归属临时代码。

不要因为文件已经创建就把违规结构合理化。
