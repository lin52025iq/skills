# 切换、回滚与清理

## 一、切换不是部署

新代码部署成功不等于迁移完成。迁移还需要确认真实业务是否已经安全转移到新实现。

## 二、选择切换方式

根据风险选择：

### 一次性切换

适合低风险、无共享状态、易回退的功能。

### 特性开关

适合需要快速在新旧实现之间切换的场景。

### 灰度流量

可以按：

- 比例；
- 用户；
- 租户；
- 地区；
- 业务类型；
- 内部用户。

逐步扩大。

### 影子流量

旧实现仍负责真实结果，新实现只接收复制流量用于行为对照。

### 双读或双写

适合数据迁移，但必须明确主数据来源、冲突处理和停止条件。

## 三、切换前必须定义观测

至少明确：

- 技术错误率；
- 延迟；
- 超时；
- 资源使用；
- 消息积压；
- 数据差异；
- 关键业务成功率；
- 关键业务金额或数量；
- 外部依赖失败率；
- 权限或安全异常。

业务指标往往比 HTTP 200 更能发现迁移错误。

## 四、明确回滚触发条件

不要只写“有问题就回滚”。

应尽量定义可执行条件，例如：

- 关键业务成功率低于既定阈值；
- 新旧行为差异连续超过允许范围；
- 数据校验出现不可解释差异；
- 特定错误码异常上升；
- 消息积压超过安全范围；
- 出现无法自动补偿的数据写入失败。

具体阈值应由项目实际基线或用户要求决定，不要凭空编造。

## 五、代码回滚不等于数据回滚

切换前回答：

- 新系统已经写入的数据，旧系统是否能读取；
- 新字段或新表回滚后如何处理；
- 双写产生冲突时谁是权威；
- 消息已经发送后能否撤销；
- 第三方副作用是否可补偿；
- 数据格式变更是否向后兼容。

如果代码可以回滚但数据不能，应在迁移风险中明确标注。

## 六、新旧并行期间的数据所有权

必须明确：

- 谁是主写方；
- 谁是主读方；
- 哪一份数据是权威；
- 同步方向；
- 延迟允许范围；
- 冲突处理；
- 何时停止同步。

禁止长时间保持“双主写但没有冲突规则”。

## 七、切换后的稳定观察

切换到新实现后继续验证：

- 业务成功率；
- 数据一致性；
- 外部依赖；
- 消息；
- 定时任务；
- 关键性能；
- 用户反馈；
- 告警质量。

达到项目定义的稳定条件后才进入清理。

## 八、清理旧实现

清理范围可能包括：

- 旧路由；
- 旧服务；
- 旧表、字段和索引；
- 临时同步逻辑；
- 旧消息消费者；
- 临时适配层；
- 特性开关；
- 旧配置；
- 旧权限；
- 旧告警；
- 兼容代码。

清理本身也应作为独立任务并验证，避免误删仍有调用者的旧能力。
