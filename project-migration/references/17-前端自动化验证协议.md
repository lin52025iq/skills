# 前端自动化验证协议

本文件把“需要验证”变成可重复的执行协议。它不要求所有项目使用同一种测试框架，但要求源、目标和审查者能够理解：验证了什么、在什么环境运行、证据在哪里、失败意味着什么。

## 一、验证从 manifest 开始

`.migration/manifest.json` 中每项需要迁移的能力至少包含：

- 稳定 ID；
- 生命周期；
- 源证据；
- 目标处理；
- 验收场景；
- 适用角色、Flag、locale、theme、viewport；
- 功能、视觉、Accessibility 和运行时要求。

自动化用例、截图和报告优先使用同一个稳定 ID，避免“文档说订单页，测试叫 test3，截图叫 final-final.png”。

推荐命名：

```text
CAP-ORDER-001
ROUTE-ORDER-LIST
SCN-ORDER-EMPTY
VIS-ORDER-LIST-MOBILE
A11Y-ORDER-FILTER
```

先运行清单校验：

```bash
python project-migration/scripts/validate_migration_manifest.py .migration/manifest.json --strict
```

清单不完整时，测试数量再多也不能证明迁移覆盖完整。

## 二、证据目录

Program 和高风险 Slice 推荐：

```text
.migration/
├── manifest.json
├── fixtures/
│   ├── users/
│   ├── api/
│   └── time/
├── tests/
│   ├── source/
│   ├── target/
│   └── shared/
└── results/
    └── <run-id>/
        ├── environment.json
        ├── commands.log
        ├── source/
        ├── target/
        ├── diffs/
        ├── console.json
        ├── network.json
        ├── accessibility.json
        ├── performance.json
        └── summary.json
```

`run-id` 使用时间戳或 commit SHA，但文件内部同时记录：

- source commit；
- target commit；
- browser 和版本；
- OS / container image；
- Node 和 package manager；
- locale、timezone、theme；
- viewport 和 device scale；
- fixture 版本；
- Flag 和角色；
- 测试命令。

不得只提交截图而不记录产生截图的环境。

## 三、先验证裁判本身

### 3.1 源实现基准

新写的迁移裁判必须先在源实现上运行，确认：

- 场景可以稳定进入；
- fixture 足以触发目标状态；
- 断言描述用户可观察结果；
- screenshot 基线来自确认过的页面；
- console / network 收集没有把已知噪声当产品失败。

### 3.2 故障注入

条件允许时，暂时注入一个小回归，例如：

- 隐藏关键按钮；
- 改错 redirect；
- 删除 Empty 状态；
- 破坏 focus restore；
- 改变分页参数；
- 调整明显 spacing；
- 让请求失败不显示错误。

确认裁判能够失败，再还原故障。无法发现代表性回归的测试，不是可靠迁移 Gate。

### 3.3 公共行为优先

优先断言：

- 用户能否到达和完成流程；
- 可见文本、角色、状态和 URL；
- 请求契约和最终结果；
- keyboard / focus；
- 页面或组件截图；
- console、network 和 hydration。

避免把源组件名称、内部 hook、私有 state shape 或旧 DOM 层级作为跨框架裁判。

## 四、固定环境，消除伪差异

视觉和交互对照尽量固定：

- browser family 和版本；
- OS / container；
- device scale；
- viewport；
- font 文件和加载完成状态；
- locale、timezone、date/number format；
- light / dark theme；
- auth、tenant、role、Feature Flag；
- API fixture；
- 当前时间、随机数和 ID；
- network latency；
- animation / transition；
- reduced motion；
- scrollbar 行为。

### 4.1 时间和随机性

对日期、倒计时、随机 ID、排序和实验分流使用固定 fixture。不要在基线中依赖“今天”“当前用户”或真实随机值。

### 4.2 动画

截图前禁用无功能含义的动画；有功能含义的 transition 单独验证开始、进行和结束状态。不能用任意 sleep 替代明确的稳定条件。

### 4.3 字体和图片

等待 `document.fonts.ready`，固定图片响应和尺寸。外部图片、头像、广告或动态图可以使用稳定 fixture，或在明确记录后 mask。

### 4.4 网络

优先 mock 不稳定第三方，保留对本次迁移关键 API 契约的验证。记录 request method、URL、query、关键 header、body schema、status、retry 和 cancellation。

## 五、场景矩阵

每个关键 Route / 组件根据风险选择：

| 维度 | 代表值 |
|---|---|
| 生命周期 | Active、Conditional、Hidden / Disabled（如需确认） |
| 数据 | Default、Loading、Empty、Error、Partial、Long Content |
| 权限 | Allowed、Denied、Read-only |
| 操作 | Create、Edit、Delete、Retry、Cancel、Back/Forward |
| Form | Pristine、Dirty、Invalid、Submitting、Success、Server Error |
| Viewport | 源项目真实支持的 desktop / tablet / mobile |
| Theme | Light、Dark 或项目实际主题 |
| Locale | 默认 locale，加高风险长文本 / RTL（如产品支持） |
| Network | Normal、Slow、Timeout、Offline（如适用） |

不要把笛卡尔积全部执行。按 manifest 选择会改变产品行为或布局的组合，并写明未覆盖组合的理由。

## 六、功能与导航验证

至少覆盖适用项：

- Route path、params、query、hash；
- deep link 直接进入；
- redirect、404、not-found；
- guard、permission、tenant、Flag；
- Menu / Tab / breadcrumb active state；
- browser back / forward；
- scroll restore；
- modal route 和 close 后 URL；
- 表单 validation、dirty、duplicate submit；
- pagination / infinite scroll；
- optimistic update 和失败回滚；
- retry、cancellation、timeout；
- analytics / exposure event；
- persistence 和版本升级。

源和目标无法运行同一测试代码时，保持相同 `SCN-*` ID 和相同可观察断言，分别实现薄适配层。

## 七、运行时错误协议

页面“看起来正常”仍可能包含阻断问题。每个关键场景收集：

### Console

阻断候选：

- uncaught exception；
- unhandled rejection；
- React/Vue/Angular runtime error；
- hydration mismatch；
- key、controlled/uncontrolled、effect cleanup 等高价值 warning；
- CSP、resource、deprecation warning（按迁移目标判断）。

为已知无害噪声维护精确 allowlist，包含原因和删除条件。禁止使用宽泛正则忽略所有 warning/error。

### Network

记录并检查：

- 4xx / 5xx；
- request aborted；
- 重复请求；
- waterfall；
- 错误 query、body、header；
- CORS / CSP；
- 静态资源 404；
- source map 或 chunk 加载失败。

### Hydration / SSR

SSR、SSG、RSC 或 hydration 相关任务额外检查：

- 服务端 HTML 是否包含预期内容；
- hydration 前后是否闪烁或丢状态；
- browser-only API 是否越界；
- 请求间状态是否隔离；
- serialized props 是否可控；
- loading / error / not-found boundary 是否生效。

## 八、视觉回归协议

### 8.1 基线来源优先级

```text
源项目可运行页面
→ 源 Storybook / component example
→ 已批准产品截图 / 设计稿
→ DOM + CSS + component structure
```

### 8.2 截图命名

推荐：

```text
<VIS-ID>__<route-or-component>__<state>__<viewport>__<theme>__<locale>.png
```

示例：

```text
VIS-ORDER-001__orders-list__empty__390x844__light__zh-CN.png
```

### 8.3 截图前稳定条件

- 页面进入目标 URL；
- 关键请求完成或被 fixture 拦截；
- 字体加载完成；
- skeleton/transition 达到指定状态；
- layout 不再变化；
- animation 按协议禁用；
- 临时 toast、光标、时间等已稳定。

不要默认使用 `networkidle` 作为唯一稳定条件；持续轮询、WebSocket 和 analytics 会让它不可靠。等待与场景相关的可观察条件。

### 8.4 Mask 和阈值

只 mask 明确不属于产品裁判的动态区域，并在基线文档中记录 selector、原因和负责人。

阈值规则：

- 页面和组件可设置不同阈值；
- 阈值必须在首次基线时确定；
- 新差异出现后不能只为通过而提高阈值；
- 大面积布局变化即使像素比例不高也要人工审查；
- text antialiasing 噪声与字体/字号/line-height 变化分开判断。

### 8.5 差异分类

每个 diff 写入：

```json
{
  "id": "VD-001",
  "scenarioId": "VIS-ORDER-001",
  "classification": "fix | approved | environment-noise | unknown",
  "evidence": [],
  "owner": "",
  "decision": "",
  "status": "open | closed"
}
```

Unknown 不得自动更新 golden。

## 九、Accessibility 验证

自动化至少检查适用项：

- axe / 项目现有规则集；
- accessible name；
- form label 和 error association；
- landmark 和 heading；
- dialog / menu / tab ARIA；
- color contrast（工具可覆盖的部分）；
- duplicate ID；
- invalid ARIA。

人工或浏览器自动化检查：

- 只用键盘完成关键流程；
- focus 顺序；
- focus-visible；
- dialog 打开、trap、关闭和 restore；
- dynamic error / success announcement；
- zoom、text resize、long content；
- reduced motion；
- screen reader 关键路径（高风险或法规要求时）。

迁移可以修复明显 Accessibility 缺陷，但重要体验变化必须作为批准差异记录，不能悄悄改变产品流程。

## 十、性能和包体

只有源基线或目标预算明确时才做定量结论，不凭感觉声明“性能更好”。

按任务风险选择：

- initial JS / CSS；
- route chunk；
- image / font；
- request waterfall；
- SSR TTFB 和 streaming；
- hydration cost；
- interaction latency；
- long list / table rendering；
- memory leak；
- duplicate framework / shared dependency。

记录测量环境、样本数和容差。对 bundler、SSR、Design System 和 micro-frontend 迁移，包体与 runtime duplication 通常是必要 Gate。

---

## 十一、残留扫描

迁移完成前搜索：

- 旧框架 import；
- deprecated API；
- compat package；
- 旧 Router / Store / Form / UI library；
- 旧 CSS class、Less/Sass entry；
- 旧 env prefix 和 config；
- 旧 Route、Menu、Feature Flag；
- 旧 asset、font、icon；
- TODO、temporary adapter、dual-write；
- skip / only test；
- 宽泛 lint disable、`any`、suppressed hydration warning。

残留分为：必须删除、迁移期保留、批准永久兼容、Unknown。迁移期保留项必须有 owner 和删除条件。

---

## 十二、命令与报告

验证报告必须记录真实执行过的命令和结果，不写“理论上可运行”。最低命令集由项目决定，常见为：

```text
install / lockfile check
build
typecheck
lint
unit / component
integration / e2e
storybook / visual
accessibility
bundle / performance
residual scan
```

每条命令记录：

- working directory；
- command；
- exit code；
- start/end；
- source / target commit；
- artifact path；
- 是否有重试和原因。

最终结论至少包含：

```text
PASS       所有适用 Gate 通过
CONDITIONAL 只有明确批准、可接受且有 owner 的遗留项
PARTIAL    仅部分范围完成，不能代表全量
BLOCKED    关键未知、裁判或发布安全缺失
FAIL       已确认存在阻断回归
```

Build 通过、截图相似或单个 E2E 通过，都不能单独升级为 PASS。
